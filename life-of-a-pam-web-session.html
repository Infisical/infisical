Life of a PAM Web Session

A design walkthrough for a proposed PAM account type that opens internal web apps in the user's browser, with no client software, extension or VPN. Pick an architecture, a gateway login and a recording mode below to follow one click through that combination. The sections after the walkthrough compare both designs, lists how the gateway can log in to the app, and ends with the questions to settle before building.       A or B
      
        
      The real question is where the app's HTML and JavaScript run: in the user's browser (A) or in a browser next to the gateway (B). Teleport and StrongDM do A and record only HTTP requests; Keeper's remote browser isolation does B and records graphically.
      
      
      
      
      
        
      
          
      ConcernA · Reverse proxyB · Remote browser

      Gateway cost per sessionNegligibleA Chromium context: memory and CPU for encoding (not measured)

      Recommendation
      
        
      Build B first, then add A as a lightweight per-account mode if customers ask for native speed. B keeps PAM's two promises for every auth method: credentials never reach the endpoint, and the recording can't be tampered with. The broker, the account type, the event schema and the log viewer are shared, so the second design costs much less than the first.

      Idle
      
            
      10 min
      
            
        
              
      • Today the timer resets on any message from the browser. For this type it should count user input only, since pages keep producing traffic.

      Disconnect
      
            
      proposed
      
            
        
              
      • Today a closed WebSocket ends the session. B could keep the browser context for a grace window and reattach with a fresh ticket.
