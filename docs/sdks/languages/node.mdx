If you're working with Node.js, the official Infisical Node.js SDK package is the easiest way to fetch and work with secrets for your application. 

## Requirements

Starting from **v5**, the Node.js SDK requires **Node.js 20 or higher**.

| SDK version | Node.js version |
|-------------|-----------------|
| `>= v5`     | `>= 20`         |
| `<= v4`     | `>= 14`         |

## Deprecation notice

Please be aware that all versions prior to `4.0.0` are officially fully unsupported.
Please upgrade to version 4.0.0 or newer in order to receive the latest updates.

## Installation

```bash
npm install @infisical/sdk
```

## Getting started

```typescript
import { InfisicalSDK } from '@infisical/sdk'

const client = new InfisicalSDK({
  siteUrl: "your-infisical-instance.com" // Optional, defaults to https://app.infisical.com
});

// Authenticate with Infisical
await client.auth().universalAuth.login({
  clientId: "<machine-identity-client-id>",
  clientSecret: "<machine-identity-client-secret>"
});

const allSecrets = await client.secrets().listSecrets({
  environment: "dev", // stg, dev, prod, or custom environment slugs
  projectId: "<your-project-id>"
});

console.log("Fetched secrets", allSecrets)
```

## Core methods

The SDK methods are organized into the following high-level categories:

1. `auth`: Handles authentication methods.
2. `secrets`: Manages CRUD operations for secrets.
3. `dynamicSecrets`: Manages dynamic secrets and leases.
4. `projects`: Creates and manages projects.
5. `environments`: Creates and manages environments.
6. `folders`: Creates and manages folders.
7. `kms`: Manages KMS keys and encryption/signing operations.
8. `agentVault`: Manages [Agent Vault](/documentation/platform/agent-vault/overview) sessions, proxies, access bundles, and delegations.

### `auth`

The `Auth` component provides methods for authentication:

#### Universal auth

#### Authenticating
```typescript
await client.auth().universalAuth.login({
  clientId: "<machine-identity-client-id>",
  clientSecret: "<machine-identity-client-secret>"
});
```

**Parameters:**
- `options` (object):
  - `clientId` (string): The client ID of your Machine Identity.
  - `clientSecret` (string): The client secret of your Machine Identity.

#### Renewing
You can renew the authentication token that is currently set by using the `renew()` method.
```typescript
await client.auth().universalAuth.renew();
```

#### Manually set access token
By default, when you run a successful `.login()` method call, the access token returned will be auto set for the client instance. However, if you wish to set the access token manually, you may use this method.

```typescript
client.auth().accessToken("<your-access-token>")
```

**Parameters:**
- `accessToken` (string): The access token to be used for authentication. _This shouldn't include "Bearer"._


#### AWS IAM

<Note>
  AWS IAM auth only works when the SDK is being used from within an AWS service, such as Lambda, EC2, etc.
</Note>

#### Authenticating
```typescript
await client.auth().awsIamAuth.login({
  identityId: "<your-identity-id>"
})
```

**Parameters:**
- `options` (object):
  - `identityId` (string): The ID of your identity

#### Renewing
You can renew the authentication token that is currently set by using the `renew()` method.
```typescript
await client.auth().awsIamAuth.renew();
```


### `secrets`

This sub-class handles operations related to secrets:

#### List secrets

```typescript
const allSecrets = await client.secrets().listSecrets({
  environment: "dev",
  projectId: "<your-project-id>",
  expandSecretReferences: true,
  viewSecretValue: true,
  includeImports: false,
  recursive: false,
  secretPath: "/prod/backend",
});
```

**Parameters:**
- `projectId` (string): The ID of your project.
- `environment` (string): The environment in which to list secrets (e.g., "dev").
- `secretPath` (str): The path to the secrets.
- `expandSecretReferences` (bool, optional): Whether to expand secret references.
- `viewSecretValue` (bool, optional): Whether or not to reveal the secret value of the secrets. If set to `false`, the `secretValue` is masked with `<hidden-by-infisical>`. Defaults to `true`.
- `recursive` (bool, optional): Whether to list secrets recursively.
- `includeImports` (bool, optional): Whether to include imported secrets.
- `tagFilters` (string[], optional): Tags to filter secrets.

**Returns:**
- `ListSecretsResponse`: The response containing the list of secrets.

#### List secrets with imports

The `listSecretsWithImports` method makes it easier to get all your secrets at once. The imported secrets will automatically be added to the secrets returned. The secrets in the selected environment will take precedence over the imported secrets. This means if you have secrets with conflicting names, the secret from the environment the import was imported into, will take precedence. 

```typescript
const allSecrets = await client.secrets().listSecretsWithImports({
  environment: "dev",
  projectId: "<your-project-id>",
  expandSecretReferences: true,
  viewSecretValue: true,
  recursive: false,
  secretPath: "/prod/backend"
});
```

**Parameters:**
- `projectId` (string): The ID of your project.
- `environment` (string): The environment in which to list secrets (e.g., "dev").
- `secretPath` (str): The path to the secrets.
- `expandSecretReferences` (bool, optional): Whether to expand secret references.
- `viewSecretValue` (bool, optional): Whether or not to reveal the secret value of the secrets. If set to `false`, the `secretValue` is masked with `<hidden-by-infisical>`. Defaults to `true`.
- `recursive` (bool, optional): Whether to list secrets recursively.
- `tagFilters` (string[], optional): Tags to filter secrets.

**Returns:**
- `Secret[]`: Returns the list of secrets objects, with imports.



#### Create secret

```typescript
	const newSecret = await client.secrets().createSecret("SECRET_NAME", {
		environment: "dev",
		projectId: "<your-project-id>",
		secretValue: "SECRET_VALUE",
		secretComment: "This is a new secret",          // Optional
		secretPath: "/prod/backend",                         // Optional
		secretReminderNote: "This is a reminder note",  // Optional
		secretReminderRepeatDays: 7,                    // Optional
		skipMultilineEncoding: false,                   // Optional
		tagIds: ["tagId1", "tagId2"],                   // Optional
		type: "personal"                                // Optional
	});
```

**Parameters:**
- `secretName` (string): The name of the secret to create
- `options` (object):
  - `projectId` (string): The ID of your project.
  - `environment` (str): The environment in which to create the secret.
  - `secretValue` (str): The value of the secret.
  - `secretPath` (string, optional): The path to the secret.
  - `secretComment` (str, optional): A comment associated with the secret.
  - `skipMultilineEncoding` (bool, optional): Whether to skip encoding for multiline secrets.
  - `secretReminderNote` (string, optional): A note for the secret reminder.
  - `secretReminderRepeatDays` (number, optional): Number of days after which to repeat secret reminders.
  - `tagIds` (string[], optional): Array of tags to assign to the new secret.
  - `type` (personal | shared, optional): Which type of secret to create.

**Returns:**
- `CreateSecretResponse`: The response after creating the secret.

#### Update secret

```typescript
const updatedSecret = await client.secrets().updateSecret("SECRET_TO_UPDATE", {
  environment: "dev",                                     
  projectId: "<your-project-id>",                                  
  secretValue: "UPDATED_SECRET_VALUE",                    
  newSecretName: "NEW_SECRET_NAME2",                      // Optional
  secretComment: "This is an updated secret",             // Optional
  secretPath: "/prod/backend",                                 // Optional
  secretReminderNote: "This is an updated reminder note", // Optional
  secretReminderRepeatDays: 14,                           // Optional
  skipMultilineEncoding: false,                           // Optional
  tagIds: ["tagId1", "tagId2"],                           // Optional
  type: "personal",                                       // Optional
  metadata: {                                             // Optional
    extra: "metadata"
  }
});
```

**Parameters:**
- `secretName` (string): The name of the secret to update.`
- `options` (object):
  - `environment` (str): The environment in which to update the secret.
  - `projectId` (str): The ID of your project.
  - `secretValue` (str, optional): The new value of the secret.
  - `newSecretName` (str, optional): A new name for the secret.
  - `secretComment` (str, optional): An updated comment associated with the secret.
  - `secretPath` (str): The path to the secret.
  - `secretReminderNote` (str, optional): An updated note for the secret reminder.
  - `secretReminderRepeatDays` (number, optional): Updated number of days after which to repeat secret reminders.
  - `skipMultilineEncoding` (bool, optional): Whether to skip encoding for multiline secrets.
  - `tagIds` (string[], optional): Array of tags to assign to the secret.
  - `type` (personal | shared, optional): Which type of secret to create.
  - `metadata` (object, optional): Assign additional details to the secret, accessible through the API.

**Returns:**
- `UpdateSecretResponse`: The response after updating the secret.

#### Get secret by name

```typescript
	const singleSecret = await client.secrets().getSecret({
    environment: "dev",
		projectId: "<your-project-id>",
		secretName: "DATABASE_URL",
		expandSecretReferences: true, // Optional
    viewSecretValue: true,        // Optional
		includeImports: true,         // Optional
		secretPath: "/prod/backend",       // Optional
		type: "shared",               // Optional
		version: 1                    // Optional
	});
```

**Parameters:**
- `environment` (str): The environment in which to retrieve the secret.
- `projectId` (str): The ID of your project.
- `secretName` (str): The name of the secret.
- `secretPath` (str, optional): The path to the secret.
- `expandSecretReferences` (bool, optional): Whether to expand secret references.
- `viewSecretValue` (bool, optional): Whether or not to reveal the secret value of the secret. If set to `false`, the `secretValue` is masked with `<hidden-by-infisical>`. Defaults to `true`.
- `includeImports` (bool): Whether to include imported secrets.
- `version` (str, optional): The version of the secret to retrieve. Fetches the latest by default.
- `type` (personal | shared, optional): The type of secret to fetch.


**Returns:**
- `Secret`: Returns the secret object.

#### Delete secret by name

```typescript

  environment: "dev",
  projectId: "<your-project-id>",
  secretPath: "/prod/backend", // Optional

});
```

**Parameters:**
- `secretName` (string): The name of the secret to delete.
- `options` (object): 
  - `projectId` (str): The ID of your project.
  - `environment` (str): The environment in which to delete the secret.
  - `secret_path` (str, optional): The path to the secret.
  - `type` (personal | shared, optional): The type of secret to delete.

**Returns:**
- `DeleteSecretResponse`: The response after deleting the secret.




### `dynamicSecrets`


#### Create a new dynamic secret

Creating a new dynamic secret can be done by using the `.dynamicSecrets().create({})` function. More details below.


The input for creating new dynamic secret varies greatly between secret types.
For a more in-depth description of each input type for each dynamic secret type, please refer to [our API documentation](https://infisical.com/docs/api-reference/endpoints/dynamic-secrets/create)


##### Example for creating a new Redis dynamic secret

```typescript
import { InfisicalSDK, DynamicSecretProviders } from "@infisical/sdk";
	const client = new InfisicalSDK();

	await client.auth().universalAuth.login({
		// For localhost
		clientId: "CLIENT_ID",
		clientSecret: "CLIENT_SECRET"
	});
const dynamicSecret = await client.dynamicSecrets().create({
  provider: {
    type: DynamicSecretProviders.Redis,
    inputs: {
      host: "<redis-host>",
      port: 6479,
      username: "<redis-username>",
      password: "<redis-password>", // Only required if your Redis instance uses authentication (recommended)
      creationStatement: "ACL SETUSER {{username}} on >{{password}} ~* &* +@all",
      revocationStatement: "ACL DELUSER {{username}}"
    }
  },
  defaultTTL: "1h",
  maxTTL: "24h",
  name: "dynamic-secret-name",
  projectSlug: "project-slug",
  environmentSlug: "dev"
});
console.log(dynamicSecret);
```

**Returns:**
- `DynamicSecret`: The created dynamic secret.


#### Delete a dynamic secret

Note: Deleting a dynamic secret will also delete it's associated leases.

```typescript
const deletedDynamicSecret = await client.dynamicSecrets().delete("dynamic-secret-name", {
  environmentSlug: "dev",
  projectSlug: "project-slug"
});
```

**Parameters:**
- `secretName` (string): The ID of the dynamic secret to delete
- `options` (object):
  - `projectSlug` (str): The ID of your project.
  - `environment` (str): The environment in which to delete the secret.

**Returns:**
- `DynamicSecret`: The deleted dynamic secret.

### `dynamicSecrets.leases`
In this section you'll learn how to work with dynamic secret leases


#### Create a new lease

```typescript
const lease = await client.dynamicSecrets().leases.create({
  dynamicSecretName: "dynamic-secret-name",
  environmentSlug: "dev",
  projectSlug: "your-project-slug",
  path: "/prod/backend",
  ttl: "5m" // Optional
});

console.log(lease);
```

**Your dynamic secret credentials will be contained user `lease.data` in this example.**

**Parameters:**
- `dynamicSecretName` (string): The name of the dynamic secret you wish to create a lease for.
- `projectSlug` (string): The slug of the project where the secret is located.
- `environmentSlug` (string): The environment where the dynamic secret is located.
- `path` (string, optional): The path of where the dynamic secret is located. 
- `ttl` (string, optional): A [vercel/ms](https://github.com/vercel/ms) encoded string representation of how long the lease credentials should be valid for. This will default to the dynamic secret's default TTL if not specified.

**Returns:**
- `CreateLeaseResponse`: The dynamic secret lease result.


#### Delete a lease
```typescript
const deletedLease = await client.dynamicSecrets().leases.delete(newLease.lease.id, {
  environmentSlug: "dev",
  projectSlug: "test-zb-3a",
  path: "/prod/backend",
  isForced: false // Whether or not to forcefully delete the lease. This can't guarantee that the lease will be deleted from the external provider.
});
```

**Parameters:**
- `leaseId` (string): The ID of the lease you want to delete.
- options:
  - `projectSlug` (string): The slug of the project where the secret is located.
  - `environmentSlug` (string): The environment where the dynamic secret is located.
  - `path` (string, optional): The path of where the dynamic secret is located. 
  - `isForced` (bool, optional): Whether or not to forcefully delete the lease. This can't guarantee that the lease will be deleted from the external provider, and is potentially unsafe for sensitive dynamic secrets.

**Returns:**
- `DeleteLeaseResponse`: The deleted lease result.

#### Renew a lease

Please note that renewals must happen **before** the lease has fully expired. After renewing the lease, you won't be given new credentials. Instead the existing credentials will continue to live for the specified TTL

```typescript
const renewedLease = await client.dynamicSecrets().leases.renew(newLease.lease.id, {
		environmentSlug: "dev",
		projectSlug: "project-slug",
		path: "/prod/backend", // Optional
		ttl: "10m" // Optional
	});
```

**Parameters:**
- `leaseId` (string): The ID of the lease you want to delete.
- `options` (object):
  - `projectSlug` (string): The slug of the project where the secret is located.
  - `environmentSlug` (string): The environment where the dynamic secret is located.
  - `path` (string, optional): The path of where the dynamic secret is located. 
  - `ttl` (string, optional): A [vercel/ms](https://github.com/vercel/ms) encoded string representation of how long the lease credentials should be valid for. This will default to the dynamic secret's default TTL if not specified.

**Returns:**
- `RenewLeaseResponse`: The renewed lease response _(doesn't contain new credentials)_.

### `kms`

The Key Management Service (KMS) module allows you to create and manage cryptographic keys for encryption and digital signing operations.

#### Create a new KMS key

Creating a new KMS key can be done by using the `.kms().keys().create({})` function. Keys can be created for either encryption/decryption or signing/verification operations.

##### Example for creating an encryption key

```typescript
import { InfisicalSDK, KeyUsage, EncryptionAlgorithm } from "@infisical/sdk";
const client = new InfisicalSDK();

await client.auth().universalAuth.login({
	clientId: "CLIENT_ID",
	clientSecret: "CLIENT_SECRET"
});

const encryptionKey = await client.kms().keys().create({
	projectId: "your-project-id",
	name: "my-encryption-key",
	description: "Key for encrypting sensitive data",
	keyUsage: KeyUsage.ENCRYPTION,
	encryptionAlgorithm: EncryptionAlgorithm.AES_256_GCM
});

console.log(encryptionKey);
```

##### Example for creating a signing key

```typescript
const signingKey = await client.kms().keys().create({
	projectId: "your-project-id",
	name: "my-signing-key",
	description: "Key for signing documents",
	keyUsage: KeyUsage.SIGNING,
	encryptionAlgorithm: EncryptionAlgorithm.RSA_4096
});

console.log(signingKey);
```

**Parameters:**
- `projectId` (string): The ID of your project.
- `name` (string): The name of the KMS key.
- `description` (string, optional): A description of the key's purpose.
- `keyUsage` (KeyUsage): Either `KeyUsage.ENCRYPTION` for encrypt/decrypt operations or `KeyUsage.SIGNING` for sign/verify operations.
- `encryptionAlgorithm` (EncryptionAlgorithm): The algorithm to use. Options include:
  - For encryption: `AES_256_GCM`, `AES_128_GCM`, `RSA_4096`, `ECC_NIST_P256`
  - For signing: `RSA_4096`, `ECC_NIST_P256`

**Returns:**
- `KmsKey`: The created KMS key object.

#### Get a KMS key by name

```typescript

```

**Parameters:**

**Returns:**


### `kms.encryption`

The encryption module provides operations for encrypting and decrypting data using KMS keys created with `KeyUsage.ENCRYPTION`.

#### Encrypt data

```typescript
const encrypted = await client.kms().encryption().encrypt({
	keyId: "<kms-key-id>",
	plaintext: "<base64-encoded-data>"
});

console.log(encrypted); // Returns the ciphertext string
```

**Parameters:**
- `keyId` (string): The ID of the encryption key.
- `plaintext` (string): The data to encrypt. This must be base64 encoded.

**Returns:**
- `string`: The encrypted ciphertext.

#### Decrypt data

```typescript
const decrypted = await client.kms().encryption().decrypt({
	keyId: "<kms-key-id>",
	ciphertext: "<encrypted-data>"
});

console.log(decrypted); // Returns the original plaintext
```

**Parameters:**
- `keyId` (string): The ID of the encryption key used to encrypt the data.
- `ciphertext` (string): The encrypted data to decrypt.

**Returns:**
- `string`: The decrypted plaintext.

### `kms.signing`

The signing module provides operations for digitally signing data and verifying signatures using KMS keys created with `KeyUsage.SIGNING`.

#### Sign data

```typescript
import { SigningAlgorithm } from "@infisical/sdk";

const signature = await client.kms().signing().sign({
	keyId: "<kms-key-id>",
	data: "<base64-encoded-data>",
	signingAlgorithm: SigningAlgorithm.RSASSA_PSS_SHA_256,
	isDigest: false // Optional: set to true if data is already a hash digest
});

console.log(signature);
```

**Parameters:**
- `keyId` (string): The ID of the signing key.
- `data` (string): The data to sign.
- `signingAlgorithm` (SigningAlgorithm): The signing algorithm to use. Available algorithms:
  - **RSA PSS** (non-deterministic): `RSASSA_PSS_SHA_256`, `RSASSA_PSS_SHA_384`, `RSASSA_PSS_SHA_512`
  - **RSA PKCS#1 v1.5** (deterministic): `RSASSA_PKCS1_V1_5_SHA_256`, `RSASSA_PKCS1_V1_5_SHA_384`, `RSASSA_PKCS1_V1_5_SHA_512`
  - **ECDSA** (non-deterministic): `ECDSA_SHA_256`, `ECDSA_SHA_384`, `ECDSA_SHA_512`
- `isDigest` (boolean, optional): Whether the data is already a hash digest. Defaults to `false`.

**Returns:**
- `KmsSignDataResponse`: Object containing the signature, keyId, and signingAlgorithm.

#### Verify a signature

```typescript
const verification = await client.kms().signing().verify({
	keyId: "<kms-key-id>",
	data: "<base64-encoded-original-data>", // Must be base64 encoded
	signature: "<data-signature>",
	signingAlgorithm: SigningAlgorithm.RSASSA_PSS_SHA_256,
	isDigest: false // Optional: set to true if data is already a hash digest
});

console.log(verification.signatureValid); // true or false
```

**Parameters:**
- `keyId` (string): The ID of the signing key used to create the signature.
- `data` (string): The original data that was signed (must be base64 encoded).
- `signature` (string): The signature to verify.
- `signingAlgorithm` (SigningAlgorithm): The same signing algorithm used to create the signature.
- `isDigest` (boolean, optional): Whether the data is already a hash digest. Defaults to `false`.

**Returns:**
- `KmsVerifyDataResponse`: Object containing `signatureValid` (boolean), `keyId`, and `signingAlgorithm`.

#### Get supported signing algorithms for a key

```typescript
const algorithms = await client.kms().signing().listSigningAlgorithms({
	keyId: "<kms-key-id>"
});

console.log(algorithms); // Array of supported SigningAlgorithm values
```

**Parameters:**
- `keyId` (string): The ID of the KMS signing key.

**Returns:**
- `SigningAlgorithm[]`: Array of supported signing algorithms for the key.

#### Get public key

Retrieve the public key for signature verification operations.

```typescript
const publicKey = await client.kms().signing().getPublicKey({
	keyId: "<kms-key-id>"
});

console.log(publicKey); // Returns the public key string
```

**Parameters:**

### `agentVault.sessions`

`client.agentVault().sessions` manages [Agent Vault sessions](/documentation/platform/agent-vault/sessions). A session lets an AI agent use the [services](/documentation/platform/agent-vault/services) in one [access bundle](/documentation/platform/agent-vault/access-bundles), the [inline services](/documentation/platform/agent-vault/inline-services) sent with the session, or both, until the session expires or someone revokes it.

What the client can do with sessions depends on the [role](/documentation/platform/agent-vault/access-control#product-membership) that the user or machine identity the client logs in as has in the Agent Vault project:

| Role | Can create sessions with | Can list, get, label, and revoke |
| --- | --- | --- |
| **Admin** | Any access bundle (on behalf of a user, [only access bundles that the user can use too](#create-a-session-on-behalf-of-a-user)), and [inline services](#create-a-session-with-inline-services) | Every session |
| **Member** | The access bundles [granted](/documentation/platform/agent-vault/access-bundles#grant-access) to the member | The member's own sessions |

<Note>
  `agentVault` requires `@infisical/sdk` version 5.3.0 or newer.
</Note>

#### List sessions

```typescript
import { AgentVaultSessionScope, AgentVaultSessionStatus } from "@infisical/sdk";

const { sessions, totalCount } = await client.agentVault().sessions.list({
  projectId: "<project-id>",
  scope: AgentVaultSessionScope.Mine, // Optional
  statuses: [AgentVaultSessionStatus.Active], // Optional
  search: "nightly deploy", // Optional
  limit: 20, // Optional
  offset: 0 // Optional
});
```

**Parameters:**
- `options` (object):
  - `projectId` (string): the ID of the [Agent Vault project](/documentation/platform/agent-vault/projects#find-the-project-id) to list sessions from
  - `scope` (AgentVaultSessionScope, optional): whose sessions to list, either `AgentVaultSessionScope.Mine` (`"mine"`) for your own sessions or `AgentVaultSessionScope.All` (`"all"`) for every session if you're an admin (defaults to `AgentVaultSessionScope.Mine`)
  - `statuses` (AgentVaultSessionStatus[], optional): the statuses to include, from `AgentVaultSessionStatus.Active` (`"active"`), `AgentVaultSessionStatus.Revoked` (`"revoked"`), and `AgentVaultSessionStatus.Expired` (`"expired"`) (defaults to all three)
  - `search` (string, optional): text to find in each session's [label](/documentation/platform/agent-vault/sessions#label-a-session), owner name, owner email, access bundle name, or the name or email of the user that the session was [created on behalf of](/documentation/platform/agent-vault/sessions-on-behalf-of-users)
  - `limit` (number, optional): the maximum number of sessions to return, from 1 to 100 (defaults to `20`)
  - `offset` (number, optional): the number of sessions to skip (defaults to `0`)

**Returns:**
- `ListAgentVaultSessionsResponse`: the sessions in `sessions`, and the total number of matching sessions in `totalCount`

#### Get session

```typescript
const session = await client.agentVault().sessions.get("<session-id>");
```

**Parameters:**

**Returns:**
- `AgentVaultSession`: the session

#### Create session

```typescript
const session = await client.agentVault().sessions.create({
  projectId: "<project-id>",
  accessBundle: "<access-bundle-name>",
  ttl: "1h", // Optional
  label: "nightly deploy" // Optional
});
```

**Parameters:**
- `options` (object):
  - `projectId` (string): the ID of the [Agent Vault project](/documentation/platform/agent-vault/projects#find-the-project-id) to create the session in
  - `accessBundle` (string, optional): the name of the access bundle that the agent can use during the session (pass `accessBundle`, `services`, or both)
  - `services` (AgentVaultInlineServiceInput[], optional): [inline services](#create-a-session-with-inline-services) to send with the session (Agent Vault admins only, up to 20)
  - `ttl` (string, optional): how long the session lasts, as a duration of at least one minute such as `30m`, `8h`, or `7d`, or as `never` for a session that doesn't expire (defaults to `7d`, or to `1h` for a session on behalf of a user)
  - `label` (string, optional): a short description of what the session is for, such as `nightly deploy` (up to 128 characters, without line breaks, tabs, or invisible characters)
  - `onBehalfOfUserEmail` (string, optional): the email address of the user that the session is [created on behalf of](#create-a-session-on-behalf-of-a-user) (throws an `InfisicalSDKError` if you also pass `onBehalfOfUserId`)
  - `onBehalfOfUserId` (string, optional): the ID of the user that the session is created on behalf of (throws an `InfisicalSDKError` if you also pass `onBehalfOfUserEmail`)

**Returns:**
- `CreatedAgentVaultSession`: the new session, with the session token in `token` (Infisical returns the token only once)

To pass `session.token` to the agent, follow the steps in [Start the agent with the session token](/documentation/platform/agent-vault/sessions-api#step-4-start-the-agent-with-the-session-token).

#### Create a session on behalf of a user

If the client logs in as a machine identity with a [delegation](/documentation/platform/agent-vault/sessions-on-behalf-of-users#set-up-a-delegation), the client can create sessions on behalf of the users that the delegation covers. For each of those sessions, the proxy uses the user's [personal values](/documentation/platform/agent-vault/http-apis#member-provided-values) instead of the machine identity's.

```typescript
const session = await client.agentVault().sessions.create({
  projectId: "<project-id>",
  accessBundle: "<access-bundle-name>",
  onBehalfOfUserEmail: "<user-email>"
});
```

- The session can use an access bundle only if both the user and the machine identity [can use the bundle](/documentation/platform/agent-vault/sessions-on-behalf-of-users#what-the-session-can-reach)
- The session belongs to the machine identity, so the user can't see the session unless they're an Agent Vault admin
- In each session that the `get`, `list`, `update`, and `revoke` methods return, `onBehalfOf` is the user, or `null` if the session is the machine identity's own

To find the access bundles that a session on behalf of the user can use, pass the user's email address or ID to [`accessBundles.list`](#list-access-bundles). The proxy refuses a session's requests to services that still need the user's personal values, so also pass `requiresSetup: false` to leave out the access bundles with those services.

#### Create a session with inline services

If the client logs in as a user or machine identity with the **Admin** role in the Agent Vault project, the client can send inline services with a session, instead of or beside an access bundle. Inline services let you pass along credentials that your code already holds, without setting anything up in Agent Vault in advance.

```typescript
const session = await client.agentVault().sessions.create({
  projectId: "<project-id>",
  ttl: "1h",
  services: [
    {
      type: "http",
      name: "github",
      hostPattern: "api.github.com",
      allowedMethods: ["GET"],
      credential: { type: "bearer", value: "<github-token>" }
    }
  ]
});
```

- Each service is an HTTP API (`type: "http"`), an MCP server (`type: "mcp"`), or a [database or SSH server](/documentation/platform/agent-vault/databases-and-ssh) (`type: "postgres"`, `"mysql"`, or `"ssh"`)
- Credentials, custom header values, and substitution values can't contain text in double braces, such as `{{GITHUB_TOKEN}}`, because inline services can't use [variables](/documentation/platform/agent-vault/variables)
- A session can have up to 20 inline services, and no two of its services can have the same name or host pattern, including the services in its access bundle
- If a machine identity creates the session on behalf of a user, the machine identity needs the **Admin** role and the user doesn't, and the inline services don't use the user's personal values
- In each session that the `create`, `get`, `list`, and `update` methods return, `services` lists the inline services without their secrets

For the fields that each type of service takes, and for when Infisical deletes the services' secrets, see [Inline services](/documentation/platform/agent-vault/inline-services).

#### Update session label

Add, change, or remove a session's label, for example to record what the agent is working on. You can change the label after the session expires or is revoked, unless someone deleted the session's owner or the user that the session was created on behalf of.

```typescript
const session = await client.agentVault().sessions.update("<session-id>", {
  label: "support ticket triage"
});
```

**Parameters:**
- `sessionId` (string): the ID of the session
- `options` (object):
  - `label` (string | null): the new label, or `null` to remove the label (up to 128 characters, without line breaks, tabs, or invisible characters)

**Returns:**
- `AgentVaultSession`: the updated session

#### Revoke session

Revoke a session when its agent finishes, even if the agent fails. The proxy stops attaching credentials to the session's requests within one [poll interval](/documentation/platform/agent-vault/proxies#poll-interval).

If the agent can run longer than the client's access token lasts, log in again before you revoke the session, because the SDK doesn't renew the access token on its own. Set `ttl` close to how long the agent runs, so that the session expires soon after the agent finishes even if revoking the session fails.

```typescript
const session = await client.agentVault().sessions.create({
  projectId: "<project-id>",
  accessBundle: "<access-bundle-name>",
  ttl: "1h"
});

try {
  await runAgent(session.token); // Your code that starts the agent with the session token
} finally {
  await client.agentVault().sessions.revoke(session.id);
}
```

**Parameters:**
- `sessionId` (string): the ID of the session

**Returns:**
- `Omit<AgentVaultSession, "accessBundle" | "services">`: the revoked session, without its access bundle and inline services (call `get` for them)

- `RevokeAgentVaultAccessBundleResponse`: the revoked grants in `members`, and the users, machine identities, and groups that didn't have the access bundle in `skipped`

### `agentVault.delegations`

`client.agentVault().delegations` manages [delegations](/documentation/platform/agent-vault/sessions-on-behalf-of-users), which let a machine identity [create sessions on behalf of users](#create-a-session-on-behalf-of-a-user).

To use any method in this section, the client must log in as a user or machine identity with the **Admin** role in the [Agent Vault project](/documentation/platform/agent-vault/access-control#product-membership). A machine identity without the role can still get its own delegation.

<Note>
  `agentVault` requires `@infisical/sdk` version 5.3.0 or newer.
</Note>

#### List delegations

```typescript
const { delegations, totalCount } = await client.agentVault().delegations.list({
  projectId: "<project-id>",
  machineIdentityIds: ["<machine-identity-id>"], // Optional
  limit: 100, // Optional
  offset: 0 // Optional
});
```

**Parameters:**
- `options` (object):
  - `projectId` (string): the ID of the [Agent Vault project](/documentation/platform/agent-vault/projects#find-the-project-id) to list delegations from
  - `machineIdentityIds` (string[], optional): the IDs of the machine identities whose delegations to list (up to 100)
  - `limit` (number, optional): the maximum number of delegations to return, from 1 to 100 (defaults to `100`)
  - `offset` (number, optional): the number of delegations to skip (defaults to `0`)

**Returns:**
- `ListAgentVaultDelegationsResponse`: the delegations in `delegations`, and the total number of matching delegations in `totalCount` (without `missingAccessBundles`, which `get` returns)

#### Get delegation

Get which users a machine identity can create sessions on behalf of. If the machine identity has no delegation, `get` throws an `InfisicalSDKRequestError` whose `statusCode` is `404`.

```typescript
const delegation = await client.agentVault().delegations.get("<machine-identity-id>", {
  projectId: "<project-id>"
});
```

**Parameters:**
- `machineIdentityId` (string): the ID of the machine identity
- `options` (object):
  - `projectId` (string): the ID of the [Agent Vault project](/documentation/platform/agent-vault/projects#find-the-project-id) to get the delegation from

**Returns:**
- `AgentVaultDelegationDetail`: the delegation, including `missingAccessBundles`

`missingAccessBundles` lists the access bundles that the delegation's users can use and the machine identity can't. A session on behalf of a user can use only an access bundle that both the user and the machine identity can use, so the machine identity can't create sessions with those access bundles. If a machine identity without the **Admin** role gets its own delegation, `missingAccessBundles` is empty.

#### Set delegation

Set which users a machine identity can create sessions on behalf of. The new delegation replaces any delegation that the machine identity has.

```typescript
import { AgentVaultDelegationScope } from "@infisical/sdk";

const delegation = await client.agentVault().delegations.set("<machine-identity-id>", {
  projectId: "<project-id>",
  scope: AgentVaultDelegationScope.Selected,
  userIds: ["<user-id>"], // Optional
  groupIds: ["<group-id>"] // Optional
});
```

**Parameters:**
- `machineIdentityId` (string): the ID of the machine identity, which must be a member of the Agent Vault project
- `options` (object):
  - `projectId` (string): the ID of the [Agent Vault project](/documentation/platform/agent-vault/projects#find-the-project-id) to set the delegation in
  - `scope` (AgentVaultDelegationScope): either `AgentVaultDelegationScope.Selected` (`"selected"`) for only the users and groups that you pass, or `AgentVaultDelegationScope.AllMembers` (`"all-members"`) for every member of the Agent Vault project, admins included
  - `userIds` (string[], optional): with `AgentVaultDelegationScope.Selected`, the IDs of the users that the machine identity can act on behalf of (up to 100)
  - `groupIds` (string[], optional): with `AgentVaultDelegationScope.Selected`, the IDs of the groups whose members the machine identity can act on behalf of (up to 100)

**Returns:**
- `AgentVaultDelegationDetail`: the delegation, with `missingAccessBundles`

With `AgentVaultDelegationScope.Selected`, pass at least one user or group. With `AgentVaultDelegationScope.AllMembers`, pass no users or groups. To stop the machine identity from acting on behalf of anyone, [delete the delegation](#delete-delegation).

Each user and group must be a member of the Agent Vault project. If a user is in the Agent Vault project only through a group, pass the group instead.

#### List available users and groups

List the users and groups in the Agent Vault project that you can add to a machine identity's delegation.

```typescript
import { AgentVaultMemberType } from "@infisical/sdk";

const { members, totalCount } = await client.agentVault().delegations.listAvailableSubjects("<machine-identity-id>", {
  projectId: "<project-id>",
  actorType: AgentVaultMemberType.User, // Optional
  search: "jsmith", // Optional
  limit: 20, // Optional
  offset: 0 // Optional
});
```

**Parameters:**
- `machineIdentityId` (string): the ID of the machine identity
- `options` (object):
  - `projectId` (string): the ID of the [Agent Vault project](/documentation/platform/agent-vault/projects#find-the-project-id) to list users and groups from
  - `actorType` (AgentVaultMemberType, optional): either `AgentVaultMemberType.User` (`"user"`) to list only users or `AgentVaultMemberType.Group` (`"group"`) to list only groups (defaults to listing both)
  - `search` (string, optional): text to find in user names, usernames, email addresses, and group names
  - `limit` (number, optional): the maximum number of users and groups to return, from 1 to 100 (defaults to `20`)
  - `offset` (number, optional): the number of users and groups to skip (defaults to `0`)

**Returns:**
- `ListAgentVaultMembersResponse`: the users and groups in `members`, and the total number of matching users and groups in `totalCount`

#### Add users and groups

Add users and groups to a machine identity's delegation. The users and groups that are already in the delegation stay in it. Pass at least one ID.

- If the machine identity has no delegation, `addSubjects` creates one with the `AgentVaultDelegationScope.Selected` scope
- If the delegation covers all members, you can't add users or groups to it

```typescript
const delegation = await client.agentVault().delegations.addSubjects("<machine-identity-id>", {
  projectId: "<project-id>",
  userIds: ["<user-id>"], // Optional
  groupIds: ["<group-id>"] // Optional
});
```

**Parameters:**
- `machineIdentityId` (string): the ID of the machine identity
- `options` (object):
  - `projectId` (string): the ID of the [Agent Vault project](/documentation/platform/agent-vault/projects#find-the-project-id) that the delegation is in
  - `userIds` (string[], optional): the IDs of the users to add (up to 100)
  - `groupIds` (string[], optional): the IDs of the groups to add (up to 100)

**Returns:**
- `AgentVaultDelegationDetail`: the delegation after the change, with `missingAccessBundles`

#### Remove users and groups

Remove users and groups from a machine identity's delegation. Pass at least one ID.

- If the delegation no longer covers a user, the proxy refuses the sessions that the machine identity created on behalf of the user until the delegation covers the user again (to end those sessions for good, [revoke them](#revoke-session))
- If you remove the last user or group, Infisical deletes the delegation

```typescript
const delegation = await client.agentVault().delegations.removeSubjects("<machine-identity-id>", {
  projectId: "<project-id>",
  userIds: ["<user-id>"], // Optional
  groupIds: ["<group-id>"] // Optional
});
```

**Parameters:**
- `machineIdentityId` (string): the ID of the machine identity
- `options` (object):
  - `projectId` (string): the ID of the [Agent Vault project](/documentation/platform/agent-vault/projects#find-the-project-id) that the delegation is in
  - `userIds` (string[], optional): the IDs of the users to remove (up to 100)
  - `groupIds` (string[], optional): the IDs of the groups to remove (up to 100)

**Returns:**
- `AgentVaultDelegationDetail | null`: the delegation after the change, with `missingAccessBundles`, or `null` if Infisical deleted the delegation

#### Delete delegation

Stop a machine identity from creating sessions on behalf of users. The proxy refuses the sessions that the machine identity already created on behalf of users until a delegation covers those users again. To end those sessions for good, [revoke them](#revoke-session).

```typescript
const delegation = await client.agentVault().delegations.delete("<machine-identity-id>", {
  projectId: "<project-id>"
});
```

**Parameters:**
- `machineIdentityId` (string): the ID of the machine identity
- `options` (object):
  - `projectId` (string): the ID of the [Agent Vault project](/documentation/platform/agent-vault/projects#find-the-project-id) to delete the delegation from

**Returns:**
- `AgentVaultDelegation`: the deleted delegation, without `missingAccessBundles`
