A machine identity lets an application, script, or other workload use Infisical without a user account. A machine identity works like an IAM user in AWS or a service account in Google Cloud.

Each machine identity has a [role](/documentation/platform/access-controls/role-based-access-controls) that controls what the identity can access, and one or more [auth methods](#authentication-methods). Your workload logs in with an auth method, gets a short-lived access token, and sends the token with each request to the Infisical API.

![Organization Identities](/images/platform/organization/organization-machine-identities.png)

## Organization and project identities

You can create a machine identity either in an organization or in a project. Both work the same way, except for where you manage them and what they can access:

| | Project identity | Organization identity |
|---|---|---|
| **Managed in** | The project | The organization |
| **Can access** | Only its own project | Each project you add the identity to, and organization-level actions |
| **Use it when** | Each team manages its own project | A workload works across several projects |

## Set up a machine identity

<Tabs>
  <Tab title="Project identity">
    <Steps>

      </Step>
      <Step>

        <Note>

        </Note>
      </Step>
      <Step>
        From your workload, log in with the auth method to get a short-lived access token.
      </Step>
      <Step>
        Send the access token with each request to the Infisical API.
      </Step>
    </Steps>
  </Tab>
  <Tab title="Organization identity">
    <Steps>
      <Step>

      </Step>
      <Step>
        Set up the [auth method](#authentication-methods) that matches where your workload runs, such as AWS Auth for a workload on AWS.

        <Note>

        From your workload, log in with the auth method to get a short-lived access token.

## Identity lockout

Lockout protects [Universal Auth](/documentation/platform/identities/universal-auth) and [LDAP Auth](/documentation/platform/identities/ldap-auth/general) from brute-force attacks. By default, after 3 consecutive failed login attempts within 30 seconds, Infisical blocks logins with that auth method on the identity for 5 minutes.

To change these limits or turn lockout off, edit the auth method on the identity.

## Revoke access tokens

An access token expires after the Access Token TTL set on the auth method, which is 30 days by default. You can revoke the token before it expires. Infisical revokes an access token when you:

- Revoke the token through the API, such as with [Revoke access token](/api-reference/endpoints/universal-auth/revoke-access-token) for Universal Auth or [Revoke token](/api-reference/endpoints/token-auth/revoke-token) for Token Auth
- Delete the identity, which revokes all of its access tokens
- Remove the credential that Infisical issued the token for, such as a Universal Auth client secret, or remove the auth method from the identity

After Infisical revokes a token, it rejects requests that use the token, and the token can't be renewed.

<Note>
  If Infisical's cache (Redis) is briefly unavailable when you revoke a token, Infisical can keep
  accepting that token for up to 12 minutes. To make sure a token stops working right away, delete
  the credential that Infisical issued the token for, such as the Universal Auth client secret, or
  delete the identity.
</Note>

## Alerts

An alert on a machine identity sends a notification to your team through the [channels](#notification-channels) you choose. Each alert watches one of these events:

| Event | When the alert fires |
|-------|----------------------|
| **Credential Expiration** | A set number of days before a Universal Auth client secret or Token Auth access token expires (Infisical checks once a day) |
| **Auth Method Change** | As soon as someone adds, updates, or removes an auth method, or creates, updates, or revokes a Universal Auth client secret or Token Auth token |

### Credential expiration

This alert notifies your team before a credential on the identity expires, so you can replace the credential before your workload loses access to Infisical. The alert skips revoked credentials, and checks each credential type against a different expiry date:

| Credential | Expiry date the alert checks |
|------------|------------------------------|
| Universal Auth client secret | The time the secret was created plus its TTL. If the TTL is `0` (the default), the secret never expires, and the alert ignores it. |
| Token Auth access token | The time the token was created plus its access token TTL. If the TTL is `0`, the alert ignores the token. |

If you renew a Token Auth token, the alert still checks the token's original expiry date, and doesn't fire again after that date passes. Removing the alert and creating it again doesn't change the date. To get alerts for a later expiry date, create a new token.

<Note>
  For Universal Auth, the alert checks the client secret, not the access tokens that an identity
  gets by logging in with the secret. Those access tokens are short-lived and renewed by your
  application. See [Universal Auth](/documentation/platform/identities/universal-auth) for the
  difference between Client Secret TTL, Access Token TTL, and Access Token Max TTL.
</Note>

### Auth method change

This alert tells your team when someone changes how the identity can log in. The alert fires each time:

- Someone adds, updates, or removes an auth method on the identity
- Someone creates or revokes a Universal Auth client secret
- Someone creates, renames, or revokes a Token Auth token

<Note>
Logging in doesn't count as a change, so the alert doesn't fire each time your workload gets an access token.
</Note>

Each notification names the auth method, the kind of change, the credential if one changed, who made the change (a user's email or a machine identity's name), and when the change happened.

### Create an alert

An identity can have one alert for each event.

<Steps>
  <Step>
    Open the machine identity and select **Alerts** at the top right of the page. If the identity already has alerts, select **Add Alert** at the bottom of the list.
  </Step>
  <Step>
    Fill in the alert's fields.

    ![Create Machine Identity Alert](/images/platform/organization/mi-create-alert.png)

    | Field | Description |
    |-------|-------------|
    | **Name** | A name for the alert, such as `ua-secret-expiry` |
    | **Description** | Optional notes about what the alert is for |
    | **Event** | **Credential Expiration** or **Auth Method Change** (you can't change the event later) |
    | **Enabled** | Whether Infisical sends notifications for the alert (on by default) |
    | **Condition** | For **Credential Expiration** only: how many days before a credential expires to send the notification, from `1` to `90` |
    | **Repeat daily until the secret is rotated** | For **Credential Expiration** only: if selected, Infisical sends the notification every day until the credential expires or is replaced, instead of once |
  </Step>
  <Step>
    Select **Add channel** and set up at least one [notification channel](#notification-channels).
  </Step>
  <Step>
    Select **Create Alert**.
  </Step>
</Steps>

### Manage alerts

Select **Alerts** on the machine identity to see its alerts. Use the toggle next to an alert to turn it on or off, or open the menu next to the toggle and select **Edit** or **Remove**.

### Notification channels

Each alert sends notifications to between 1 and 10 channels:

| Channel | Configuration |
|---------|---------------|
| **Email** | Users and groups in your organization, up to 20 per channel. If someone joins a group after you add the group, they also get the notifications. |
| **Slack** | An [Incoming Webhook](https://api.slack.com/messaging/webhooks) URL that uses HTTPS and has the exact hostname `hooks.slack.com` |
| **PagerDuty** | An [Events API v2](https://developer.pagerduty.com/docs/events-api-v2-overview) integration key (a 32-character hex string). Infisical opens one incident per expiring credential, and adds repeated changes of the same kind to the same auth method to one open incident. |
| **Webhook** | An HTTPS URL, with an optional [signing secret](#verify-webhook-signatures) |

### Webhook payload

Infisical sends each webhook as a [CloudEvents](https://cloudevents.io/) 1.0 JSON document. The value of the `type` field depends on the event that fired the alert:

- `com.infisical.identity.authentication.expiration` for credential expiration
- `com.infisical.identity.authentication.auth-method-changed` for an auth method change

For credential expiration, `data.items` lists each credential that the daily check found:

### Verify webhook signatures

If you set a signing secret on a webhook channel, Infisical signs each request and sends the signature in the `x-infisical-signature` header:

```
x-infisical-signature: t=1786924804512,v1=9f8c1d...e3
```

- `t` is the time Infisical sent the request, as a Unix timestamp in milliseconds
- `v1` is `HMAC-SHA256("<t>.<raw-request-body>", <signing-secret>)`, as a hex string

To verify a request before you trust its payload:

<Steps>
  <Step>
    Compute the HMAC over the raw request body, not over a copy you parsed and serialized again.
  </Step>
  <Step>
    Compare the result with `v1`.
  </Step>
  <Step>
    Reject the request if `t` is older than you allow, such as five minutes.
  </Step>
</Steps>

## FAQ

<AccordionGroup>
<Accordion title="Can I use machine identities with the CLI?">

Yes. To log in to the CLI as a machine identity, see [CLI usage](/cli/usage).

</Accordion>

<Accordion title="What's the difference between a machine identity and a service token?">
  A [service token](/documentation/platform/token) is a project-level authentication method scoped to select environments and paths within a single project.

  Compared with a service token, a machine identity:

  - Can call more of the Infisical API
  - Uses the same permission system as users
  - Supports more auth methods and security settings, such as [lockout](#identity-lockout)

  If you want a single token that works like a service token, add [Token Auth](/documentation/platform/identities/token-auth) to a machine identity.
</Accordion>
<Accordion title="Why can't I create, read, update, or delete an identity?">
  Infisical blocks the action if:

  - Your organization role doesn't have permission to manage identities
  - The identity you're reading, updating, or deleting has more privileges than you
  - The role you're giving the identity has more privileges than your role
</Accordion>
<Accordion title="Why didn't I get an alert for a credential expiring in a few hours?">
  Infisical checks for expiring credentials once a day, so a credential that lasts less than a day can expire before a check finds it. Use expiration alerts for credentials with TTLs of several days or more.
</Accordion>
<Accordion title="What happens to an alert after I rotate the credential?">
  Nothing changes on the alert. The alert checks the new client secret against the new secret's TTL, and stops checking the old secret once you revoke it or it expires.
</Accordion>
<Accordion title="Does the auth method change alert fire when I rotate a client secret?">
  Yes. Infisical sends one notification when you create the new client secret and another when you revoke the old one. Each notification names the secret by its description or prefix.
</Accordion>
</AccordionGroup>
