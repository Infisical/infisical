A webhook channel on a certificate [alert](/documentation/platform/pki/applications/alerting/overview) sends an HTTP POST request to your endpoint whenever the alert fires. Use a webhook to connect certificate alerts to your own systems or to services Infisical doesn't support directly.

<Info>
  Webhook channels are available under Infisical's [Enterprise](https://infisical.com/pricing) plan. If you're self-hosting Infisical, contact sales@infisical.com to purchase an enterprise license.
</Info>

## Prerequisites

- The Certificate Management **Admin** role to create a Certificate Management alert, or the **Admin** [application role](/documentation/platform/pki/applications/overview#application-roles) to create an application alert
- An HTTPS endpoint that accepts POST requests

## Step 1: Start an alert

<StartAlert />

## Step 2: Add the webhook channel

<Steps>
  <Step>
    Select **Add Channel** > **Webhook** and enter your endpoint's **URL**. The URL must use HTTPS.
  </Step>
  <Step>
    If your endpoint requires authentication, under **Authentication**, select **Bearer Token**, **Basic Auth**, or **API Key**, and enter the [credentials](#authentication) it expects.
  </Step>
  <Step>
    Optionally, select **Add Signing Secret** and enter a secret, so your endpoint can [verify the signature](#verify-the-signature) of each request.
  </Step>
  <Step>
    Optionally, select **Add Header** to send [custom headers](#custom-headers) with each request.
  </Step>
  <Step>
    Optionally, select **Send test** to send a test request to your endpoint.
  </Step>
  <Step>
    Select **Continue**, check the **Review** step, and select **Create Alert**.
  </Step>
</Steps>

<Check>
  Your alert is set up. Infisical sends a POST request to your endpoint whenever the alert fires.
</Check>

## Authentication

A channel can have one authentication method, which Infisical sends as a header on each request:

| Type | What you enter | Header that Infisical sends |
|------|----------------|-----------------------------|
| **Bearer Token** | A token | `Authorization: Bearer <token>` |
| **Basic Auth** | A username and a password | `Authorization: Basic <base64 of username:password>` |
| **API Key** | A header name, such as `X-API-Key`, and the key | `<header name>: <key>` |

For an `Authorization` scheme other than `Bearer`, such as `GenieKey <key>`, select **API Key**, enter `Authorization` as the header name, and enter the full value, including the scheme.

Infisical doesn't show saved credentials again. When you edit the channel, leave a field blank to keep its saved value. If you change the URL, enter the credentials again, because Infisical only sends them to the URL they were saved with.

## Custom headers

Infisical sends custom headers with each request, such as an `X-Env` header your endpoint uses to route alerts:

- Anyone who can view the alert can see header values, so put credentials, including any `Authorization` header, in [authentication](#authentication)
- A channel can have up to 20 custom headers, and header names, values, and authentication credentials can total up to 4,096 characters
- Infisical sets `Content-Type`, `Content-Length`, `Transfer-Encoding`, `Connection`, `Host`, and `x-infisical-signature` itself, so you can't add them

## Webhook event types

Each request is a [CloudEvents](https://cloudevents.io/) JSON payload. The `type` field names the event, and application alerts and Certificate Management alerts use different values:

| Event | Application alert `type` | Certificate Management alert `type` |
|-------|--------------------------|----------------------------------|
| Expiration | `com.infisical.cert-manager.application.certificate.expiry` | `com.infisical.cert-manager.certificate.expiry` |
| Issuance | `com.infisical.cert-manager.application.certificate.issuance` | `com.infisical.cert-manager.certificate.issuance` |
| Renewal | `com.infisical.cert-manager.application.certificate.renewal` | `com.infisical.cert-manager.certificate.renewal` |
| Revocation | `com.infisical.cert-manager.application.certificate.revocation` | `com.infisical.cert-manager.certificate.revocation` |
| Signer certificate expiration | Not available | `com.infisical.cert-manager.signer.certificate.expiry` |

The `subject` field is the same value without the `com.infisical.` prefix.

## Webhook payload format

`data.items` lists the certificates the alert fired for. Each item has the certificate's ID, a `title` (its common name, or its first SAN or serial number when it has none), a one-line `summary`, a `severity`, and a list of display `fields`. To act on a certificate in code, read `resource` instead of `fields`: it holds the certificate's typed values, with ISO 8601 dates and the raw revocation reason code. An expiration request can include several certificates, and `data.alert.condition` holds the alert's lead time as you entered it, such as `30d` or `2w`. Issuance, renewal, and revocation requests include the one certificate the event was about.

To find out which kind of alert sent a request, read `data.alert.resourceType`:

- `cert-manager.application`: an application alert, with the application's ID in `data.alert.resourceId`
- `cert-manager`: a Certificate Management alert
- `cert-manager.signer`: a signer certificate expiration alert, whose items list the signers in `resource.signerIds` and `resource.signerNames`

<Note>
  Alerts created before certificate alerts moved to applications keep sending the older `com.infisical.pki.certificate.*` event types with a `data.certificates` list. If one endpoint receives both, check the `type` field to tell them apart.
</Note>

## Webhook signature verification

If you set a signing secret, each request carries an `x-infisical-signature` header:

```
x-infisical-signature: t=<timestamp>,v1=<signature>
```

| Component | Description |
|-----------|-------------|
| `t=<timestamp>` | Unix timestamp in milliseconds when Infisical signed the request |
| `v1=<signature>` | Hex-encoded HMAC SHA256 signature |

### Verify the signature

1. Read the timestamp and the signature from the header
2. Join the timestamp and the raw request body with a dot: `{timestamp}.{raw-body}`
3. Compute the HMAC SHA256 of that string with your signing secret
4. Compare the result with the signature from the header

```javascript
const crypto = require('crypto');

function verifyWebhookSignature(header, body, secret) {
  const parts = header.split(',');
  const timestamp = parts[0].replace('t=', '');
  const signature = parts[1].replace('v1=', '');

  const signaturePayload = `${timestamp}.${body}`;
  const expectedSignature = crypto
    .createHmac('sha256', secret)
    .update(signaturePayload)
    .digest('hex');

  return crypto.timingSafeEqual(
    Buffer.from(signature),
    Buffer.from(expectedSignature)
  );
}
```
