Approval workflows add a human review step before certificates are issued or revoked. Use them to enforce separation of duties, ensure oversight of sensitive certificates, or meet compliance requirements.

## When to use approvals

<CardGroup cols={2}>
  <Card title="Separation of duties" icon="users">
    Different people must request and approve certificate issuance or revocation.
  </Card>
  <Card title="Sensitive certificates" icon="shield-check">
    Production or customer-facing certificates need additional review.
  </Card>
  <Card title="Compliance requirements" icon="clipboard-check">
    Regulatory frameworks require documented approval before issuance or revocation.
  </Card>
  <Card title="Prevent unauthorized issuance" icon="lock">
    Ensure certificates are only issued after proper validation.
  </Card>
</CardGroup>

<Note>
  For fully automated workloads (e.g., using [Infisical Agent](/documentation/platform/pki/reference/infisical-agent)), enable the **machine identity bypass** option so automated systems can issue certificates without waiting for approval.
</Note>

## How approval policies work

An approval policy defines the workflow that must be completed before a certificate is issued or revoked. Policies are configured per Application and can be scoped to specific profiles attached to that Application. Each policy covers one of two actions:

- **Issuance:** new certificates and renewals
- **Revocation:** revoking certificates

When a certificate request is made through an enrollment method:

1. Request enters **pending** state
2. Approvers receive an in-app notification and an email with a link to the request (if configured)
3. Each approval step must be completed in sequence
4. Once all steps are approved, the certificate is issued

### Renewals

If an approval policy covers the certificate's profile, a [renewal](/documentation/platform/pki/applications/certificate-renewal) waits for approval in these cases:

- The certificate was imported or discovered, including when it renews automatically
- The renewal changes the certificate, such as its common name, SANs, validity, or custom extensions, or uses a CSR

If you renew a certificate that Infisical issued and don't change it, the renewal doesn't need approval. The machine identity bypass applies to renewals the same way it applies to issuance. Automatic renewals don't run as a machine identity, so the bypass doesn't apply to them.

While a renewal is waiting for approval, you can't submit another renewal that needs approval for the same certificate. If an approver rejects the renewal of an imported or discovered certificate, automatic renewal stops for that certificate. Renew it manually to request approval again. Automatic renewal continues on the new certificate once that renewal is approved.

### Revocation

If a revocation policy covers a certificate's profile, revoking the certificate creates an approval request instead of revoking it, whether you revoke it in Infisical or with the [Revoke](/api-reference/endpoints/certificates/revoke) endpoint. The endpoint then responds with `202 Accepted`, a `pending_approval` status, and the approval request's ID. Infisical doesn't revoke the certificate for that request until the request is approved. While the request is pending, the Application's certificate list marks an active certificate **Revocation Pending**.

- If the request gets the required approvals at every step, Infisical revokes the certificate with the reason the requester chose
- If an approver rejects the request, or it's cancelled or expires, Infisical doesn't revoke the certificate
- If [Microsoft Intune asks Infisical to revoke the certificate](/documentation/platform/pki/guides/applications/microsoft-intune-scep#how-revocation-works) for a device, Infisical revokes the certificate right away, even while the request is pending

A certificate can have only one revocation request pending at a time. Sometimes too few of a pending request's approvers can still approve it, for example because they were demoted to Auditor, removed from the Application or its group, or deactivated in the organization. Once the revocation policy has approvers who can approve, revoking the certificate again cancels that request and creates a new one from the current policy.

If a revocation policy covers the certificate's profile, Application Admins and Operators can request a revocation, and machine identities can't skip the approval. If no revocation policy covers the profile, only Application Admins can revoke the certificate, and Infisical revokes it right away.

## Create an approval policy

In your Application, go to the **Settings** tab and find the **Approval Policies** section. Select **Create Policy**.

<Steps>
  <Step title="Configure basic settings">
    | Field | Description |
    |-------|-------------|
    | **Policy Name** | A descriptive name like `production-cert-approval` |
    | **Max. Request TTL** | How long a request can remain pending before expiring |
    | **Policy Type** | **Issuance** or **Revocation** (you can't change it after you create the policy) |
    | **Certificate Profiles** | Which profiles require approval |
    | **Bypass approval for machine identities** | Allow automated systems to skip approval (issuance policies only) |
  </Step>
  <Step title="Configure approval steps">
    Each step defines who can approve and how many approvals are required:
    
    | Field | Description |
    |-------|-------------|
    | **Step Name** | Optional name like `Security Team Review` |
    | **Approvers** | Users or groups eligible to approve. A revocation policy's approvers need the Admin or Operator role in the Application, since Auditors can't approve. |
    | **Required Approvals** | How many must approve (e.g., 2 of 5) |
    | **Notify Approvers** | Send an in-app notification and email when approval is needed |
    
    **Example multi-step workflow:**
    1. **Team Lead Review** — Requires 1 approval from team leads
    2. **Security Review** — Requires 2 approvals from security team
  </Step>
  <Step title="Review and create">
    Review your configuration and select **Create**.
  </Step>
</Steps>

## Managing approval requests

### View requests

In the Certificate Manager sidebar, go to **Approval Requests** to see all pending and completed requests:

| Status | Meaning |
|--------|---------|
| **Open** | Pending approval |
| **Approved** | The approvers at every step approved the request, and the certificate was [issued or revoked, or Infisical recorded why it couldn't be](#approve-a-request) |
| **Rejected** | An approver rejected the request |
| **Cancelled** | The requester cancelled the request, someone deleted its policy, or a new revocation request replaced it |
| **Expired** | Request exceeded max TTL |

### Approve a request

<Steps>
  <Step title="Open the request">
    Select a pending request to view details.
  </Step>
  <Step title="Review certificate details">
    Verify the request information:
    - Requester name and email
    - Certificate profile
    - Common name and SANs
    - Key usages and validity period
  </Step>
  <Step title="Approve">
    If you're an eligible approver for the current step, select **Approve**.
  </Step>
</Steps>

Once the request gets every required approval, Infisical issues the certificate, or revokes the certificate if the request is for a revocation. If issuance fails at that point, for example because the CA is disabled, the certificate request moves to **Failed** and Infisical records a [`certificate-issuance-failed` audit log event](/documentation/platform/audit-logs#certificate-issuance-failures) with the reason.

If revocation fails at that point, for example because the CA can't be reached, Infisical records a [`cert-revocation-failed` audit log event](/documentation/platform/audit-logs#certificate-revocations) with the reason, and sends the requester and the request's approvers an in-app notification with the reason and a link to the request. When the failure came from the CA, the reason names the CA. A CA can revoke a certificate even when its reply never reaches Infisical, so when the CA fails with an unexpected error, such as a timeout, the reason says Infisical couldn't confirm the certificate's state at the CA. After you fix the problem, revoke the certificate again with the same reason. If the CA already revoked it, Infisical records the revocation. Keep the same reason because Microsoft AD CS refuses Certificate Hold for a certificate it already revoked with a permanent reason. If a revocation policy still covers the certificate's profile, Infisical creates a new approval request instead of revoking the certificate right away.

### Reject a request

<Steps>
  <Step title="Open the request">
    Select a pending request.
  </Step>
  <Step title="Reject with reason">
    Select **Reject** and optionally add a comment explaining why.
  </Step>
</Steps>

When a request is rejected, the workflow ends and no certificate is issued or revoked.

## FAQ

<AccordionGroup>
  <Accordion title="I approved a request but the certificate wasn't issued">
    If the policy has multiple steps, your approval may have completed only one step. The certificate is issued only after **all** approval steps are completed. Check the request details to see which step is currently pending.
  </Accordion>
  <Accordion title="I don't see the Approve button">
    The Approve button only appears if:
    - You're listed as an approver for the **current** step
    - The request is still pending (not expired or rejected)
    - Previous steps have been completed
  </Accordion>
  <Accordion title="Can I use approvals with ACME or EST?">
    Yes, approval policies work with any enrollment method. However, automated clients like Certbot typically can't wait for human approval. Consider using the machine identity bypass for automated workloads.
  </Accordion>
  <Accordion title="What happens when a request expires?">
    The request moves to **Expired** status and no certificate is issued. The requester must submit a new request.
  </Accordion>
  <Accordion title="Can requesters approve their own requests?">
    By default, yes — if they're listed as an eligible approver. For separation of duties, configure approver groups that exclude potential requesters.
  </Accordion>
</AccordionGroup>
