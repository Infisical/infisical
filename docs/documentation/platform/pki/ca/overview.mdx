A Certificate Authority (CA) signs and issues X.509 certificates. Before teams can issue certificates through applications, an admin needs to set up at least one CA, either in Infisical or by connecting one you already use.

<CardGroup cols={2}>
  <Card title="Internal CA" icon="lock" href="/documentation/platform/pki/ca/private-ca">
    Create root and intermediate CAs in Infisical for internal services, mTLS, and private networks.
  </Card>
  <Card title="External CA" icon="landmark" href="/documentation/platform/pki/ca/external-ca">
    Issue from a public CA such as Let's Encrypt or DigiCert, or from enterprise PKI such as AWS Private CA, Microsoft ADCS, or Venafi.
  </Card>
  <Card title="HSM connectors" icon="shield-half" href="/documentation/platform/pki/settings/hsm-connectors">
    Keep internal CA and signer keys in your own HSM.
  </Card>
</CardGroup>

## Which should I use?

| Use case | Recommended CA |
|----------|----------------|
| Internal services, mTLS between microservices | Internal CA |
| Public-facing websites needing browser trust | External CA (Let's Encrypt, DigiCert) |
| Enterprise with existing PKI infrastructure | External CA (AWS Private CA, Microsoft ADCS, Venafi) |
| IoT devices, internal device fleet | Internal CA |
| Regulated environments with specific CA requirements | External CA (your approved provider) |

## Internal CA hierarchy

When you use internal CAs, you typically create a hierarchy:

```
Root CA (offline, long-lived)
└── Intermediate CA (online, issues certificates)
    └── Leaf Certificates (TLS, mTLS, devices)
```

<Info>
  Keep your root CA offline or use it as little as possible. Create one or more intermediate CAs to issue day-to-day certificates, so a compromised intermediate CA doesn't expose the root.
</Info>

## Next steps

<Steps>
  <Step>
    Set up an [internal CA](/documentation/platform/pki/ca/private-ca) or connect an [external CA](/documentation/platform/pki/ca/external-ca).
  </Step>
