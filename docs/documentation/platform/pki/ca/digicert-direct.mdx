## Concept

Infisical can issue certificates directly from [DigiCert CertCentral](https://www.digicert.com/) using the [CertCentral Services API](https://dev.digicert.com/en/certcentral-apis/services-api.html). A single DigiCert CA in Infisical is configured for one purpose:

- **SSL/TLS** — issues OV and EV TLS server certificates under an SSL product entitlement on your account (for example `ssl_plus`).
- **Code Signing** — issues OV (`code_signing`) and EV (`code_signing_ev`) code-signing certificates against a CSR. The signing key must live on an HSM.

<Note>
  The product is fixed on the CA and applies to every certificate that CA issues. Each product allows a different range of subject values, and DigiCert checks those values when the order is placed, not when you create the request. For example, `ssl_wildcard` takes only a wildcard common name such as `*.example.com`.
</Note>

## Prerequisites

- A [DigiCert App Connection](/integrations/app-connections/digicert) with a validated CertCentral API key.
- A CertCentral **Organization**. For code signing, DigiCert validates the organization the first time it's used for a code-signing order, which can take up to 3 business days.
- Entitlement to the product you intend to use (`ssl_plus`, `code_signing`, `code_signing_ev`, ...) on your CertCentral account.

<Note>
  Configuring a DigiCert CA requires a CertCentral account with administrator-level access (or a role with permission to manage organizations, products, and API keys). The API key used for the App Connection inherits the permissions of the CertCentral user that created it.
</Note>

## Create a DigiCert certificate authority

<Tabs>
  <Tab title="Infisical UI">
    <Steps>
      <Step title="Create a DigiCert App Connection">
        Follow the [DigiCert App Connection guide](/integrations/app-connections/digicert) to store your CertCentral API key in Infisical.
      </Step>
      <Step title="Create the External CA">
        In **Certificate Manager**, go to **Certificate Authorities**, select **Create CA** in the External Certificate Authorities section, choose **DigiCert CertCentral** as the type, and fill out the form:

        - **App Connection** — the DigiCert connection you created
        - **Organization** — the CertCentral organization that should appear on issued certificates
        - **Purpose** — `SSL / TLS` or `Code Signing`. The product list filters accordingly.
        - **Product** — the CertCentral entitlement this CA will issue under
        - **Verified Contact** (Code Signing only) — full contact info for the person DigiCert emails to approve first-time code-signing orders for this organization. All five fields required: **First Name**, **Last Name**, **Email**, **Job Title**, **Telephone** (E.164, e.g. `+15551234567`). DigiCert requires `job_title` and `telephone` on every verified contact for CS orders; referencing an existing CertCentral user by id alone is not enough. Once the organization has an active CS validation on file, DigiCert ignores this field.
      </Step>
    </Steps>
  </Tab>
  <Tab title="API">
    To create a DigiCert Certificate Authority, make an API request to the [Create DigiCert CA](/api-reference/endpoints/certificate-authorities/digicert/create) API endpoint.

    ```bash Create a DigiCert CA (SSL)
    curl --request POST \
      --url https://app.infisical.com/api/v1/cert-manager/ca/digicert \
      --header 'Authorization: Bearer <access-token>' \
      --header 'Content-Type: application/json' \
      --data '{
        "name": "digicert-ov",
        "status": "active",
        "configuration": {
          "appConnectionId": "<digicert-app-connection-id>",
          "organizationId": 112236,
          "productNameId": "ssl_plus",
          "purpose": "ssl",
          "dnsZones": [
            {
              "provider": "cloudflare",
              "appConnectionId": "<cloudflare-app-connection-id>",
              "hostedZoneId": "<cloudflare-zone-id>"
            }
          ]
        }
      }'
    ```

    ```bash Create a DigiCert CA (Code Signing)

      --url https://app.infisical.com/api/v1/cert-manager/ca/digicert \

      --data '{
        "name": "digicert-cs",
        "status": "active",
        "configuration": {
          "appConnectionId": "<digicert-app-connection-id>",
          "organizationId": 112236,
          "productNameId": "code_signing",
          "purpose": "code_signing",
          "verifiedContact": {
            "firstName": "John",
    ```

## Domain validation with DNS zones

DigiCert issues an OV or EV certificate only after it validates that your organization controls every domain on the certificate. Each validation expires after a set period. If you link the DNS zones that hold your domains to an SSL/TLS DigiCert CA, a persistent DNS TXT record is written for those domains before each order so DigiCert can validate them, and you don't have to redo the validation in DigiCert CertCentral.

### Link a DNS zone

Before you link a zone, allow the persistent DNS TXT record method in DigiCert CertCentral: go to **Settings** > **Preferences** > **Advanced Settings** > **Domain Control Validation (DCV)**, select **Persistent DNS TXT record**, then select **Save Settings**. Without it, DigiCert refuses to switch a domain to the persistent record, and every order waits for validation in CertCentral.

<Tabs>
  <Tab title="Infisical UI">
    <Steps>
      <Step>
        In **Certificate Manager**, go to **Certificate Authorities**, then create a DigiCert CA with the **SSL / TLS** purpose and pick its **Product**, or select **Edit CA** on an existing one. **Domain Validation** appears once a TLS product is selected.
      </Step>
      <Step>
        Under **Domain Validation**, select **Add DNS Zone**, then select the DNS provider that hosts the zone.
      </Step>
      <Step>
        Select the **DNS App Connection** for that provider, such as a [Cloudflare connection](/integrations/app-connections/cloudflare), then select the **Zone**. For Google Cloud DNS, select the **GCP Project** before the zone. For Route 53, enter the **Hosted Zone ID** of a public hosted zone. For DNS Server (RFC 2136), enter the **Zone** name, such as `example.com`.
      </Step>
      <Step>
        Select **Create** or **Update** to save the CA with its linked zones.
      </Step>
    </Steps>
  </Tab>
  <Tab title="API">
    Pass `dnsZones` in the CA's `configuration` to the DigiCert CA [Create](/api-reference/endpoints/certificate-authorities/digicert/create) or [Update](/api-reference/endpoints/certificate-authorities/digicert/update) endpoint. Each zone takes the DNS `provider`, the `appConnectionId` of the DNS App Connection, and the provider's `hostedZoneId`, like the Cloudflare zone in the [SSL example](#create-a-digicert-certificate-authority).

    If you leave out `dnsZones` on an update, the linked zones stay linked, unless the update changes the purpose to code signing. An empty list removes them all.
  </Tab>
</Tabs>

A CA can link up to 20 zones from any mix of DNS providers. The DNS App Connection needs permission to read the zone and its TXT records and to create TXT records in it. For Route 53, that means `route53:GetHostedZone`, `route53:ListResourceRecordSets` and `route53:ChangeResourceRecordSets` on the hosted zone, as in the **DigiCert CA with Route 53** policy on the [AWS connection page](/integrations/app-connections/aws). For DNS Server (RFC 2136), the TSIG key must be allowed to update TXT records at `_validation-persist.<zone>`. Grant that name the same way the [RFC 2136 connection](/integrations/app-connections/rfc2136) setup grants `_acme-challenge` names, such as `grant infisical-acme name _validation-persist.example.com. TXT;` in BIND.

You can't delete an App Connection while a DigiCert CA links a zone through it. Remove the zone from the CA first.

### Validation before each order

Before each new order, renewal, or reissue, each domain on the certificate is checked with DigiCert:

1. If the CA's DigiCert organization already has an active validation for the domain or one of its parent domains, the domain is skipped. A parent validated with an HTTP file only covers its own name, so it doesn't skip its subdomains.
2. If the domain is in a linked zone, such as `example.com`, the zone's domain is validated with DigiCert through a persistent DNS TXT record at `_validation-persist.example.com`. If more than one linked zone holds the domain, the most specific zone is used.
3. Once DigiCert sees the record, the order is placed.

The record stays in the zone after the order, and DigiCert rechecks it on its own, so the zone's domain stays validated. If someone deletes the record and the validation expires, the record is written again before the next order.

The record also stays when you remove the zone from the CA, move the CA to another DigiCert account, or delete the CA, and while it's there that DigiCert account can keep validating the domain. If that account shouldn't validate the domain anymore, remove its value from the `_validation-persist` record in your DNS provider. The record can hold values for more than one DigiCert account, so keep the others.

<Note>
  If a [certificate policy](/documentation/platform/pki/settings/policies#subject-alternative-names-sans) allows a name in a linked zone, anyone who can request a certificate under that policy can have the zone's domain validated in DigiCert, which covers every name in the zone. Link only the zones this CA should issue for, and limit the names the policy allows.
</Note>

### Domains that wait for validation

In the following cases, the order is still placed and waits in **Pending Validation**, as it does without linked zones:

- The domain isn't in any linked zone
- The DNS provider refuses the record, for example because the App Connection can't write to the zone
- DigiCert doesn't see the record after several checks
- DigiCert refuses the request, for example because of its rate limit

The request's status message names each linked zone whose domain wasn't validated when the order was placed, and the cause. It doesn't update when DigiCert later validates one of those domains. If the record was written, the certificate is issued once DigiCert's own recheck validates the domain.

## DigiCert validation workflow

When you request a certificate through a DigiCert CertCentral CA, the request moves through these states:

| State | Description |
|-------|-------------|
| **Pending Validation** | DigiCert has accepted the order. Complete domain control validation in DigiCert CertCentral for each domain that the [linked DNS zones](#domain-validation-with-dns-zones) didn't validate. |
| **Issued** | Infisical polls DigiCert and downloads the certificate once validation completes. Select **Trigger Validation** to force an immediate check. |
| **Failed** | If DigiCert doesn't issue within 24 hours. Complete validation on CertCentral and submit a new request. |

## FAQ

<AccordionGroup>
  <Accordion title="What happens when I revoke a DigiCert-issued certificate in Infisical?">
    Revoking the certificate in Infisical immediately marks it `Revoked` in the local inventory
    **and** asks DigiCert CertCentral to revoke that certificate only, so other certificates on the
    same order stay valid. If the certificate was issued before individual DigiCert certificates were
    tracked and a newer certificate has since replaced it on the order, the revocation is refused, so
    revoke it in DigiCert CertCentral instead.
    Depending on your CertCentral account's revocation policy, DigiCert may queue that request for
    administrator approval before the certificate is actually revoked on their side.
  </Accordion>
  <Accordion title="What happens when a certificate is revoked in DigiCert CertCentral?">
    It's marked `Revoked` in the inventory within a day. That includes a certificate replaced by a
    [reissue](/documentation/platform/pki/applications/certificate-renewal#reissuing-a-digicert-certificate),
    which DigiCert revokes within 72 hours when the reissue removes or changes a name.
  </Accordion>
</AccordionGroup>
