<Info>
  The ServiceNow integration is opt-in and only available on Enterprise plans.
  Contact [sales@infisical.com](mailto:sales@infisical.com) to get access to the
  ServiceNow integration.
</Info>

The ServiceNow integration hands the approval decision for an Infisical [access request](/documentation/platform/access-controls/access-requests) to ServiceNow. Instead of approving in Infisical, your approvers review the request in ServiceNow, where it goes through the approval process you already run there.

Infisical still grants the access. It creates the request, waits for ServiceNow to return a decision, and grants or denies the access itself. ServiceNow never sees your secrets.

## How it works

1. A user requests access in Infisical to an environment and secret path.
2. The request matches an access policy that sends its requests to ServiceNow.
3. Infisical creates an **Infisical Access Request** record on your ServiceNow instance over the [ServiceNow connection](/integrations/app-connections/servicenow). The record includes a callback token that Infisical issued for this request alone.
4. A ServiceNow flow you own routes the record to the right approvers.
5. When the flow reaches a decision, its final step runs the **Infisical - Notify Decision** action. The action records the decision on the record, then sends the callback token to Infisical to say the record has a decision.
6. Infisical reads the decision from the record over the ServiceNow connection, then grants the access on approval or closes the request on rejection.

If the policy sets a request expiration and ServiceNow doesn't return a decision in time, the request expires in Infisical. Infisical never grants access without an approval from ServiceNow.

## Prerequisites

- A Secrets Management project on Infisical with Access Requests available
- A ServiceNow instance where you can install a scoped application, create users, and build flows in Flow Designer (the `flow_designer` role)
- A ServiceNow instance that Infisical can reach (if your instance restricts inbound traffic, allow [Infisical's IP addresses](/documentation/setup/networking) on its IP access control list)
- Outbound HTTPS access from your ServiceNow instance to your Infisical URL
- If you self-host Infisical, a [`SITE_URL`](/self-hosting/configuration/envars) that starts with `https://`, because ServiceNow notifies Infisical at that address

## Step 1: Install the Infisical application

<Steps>
  <Step>
    Install the application package that Infisical provides on your ServiceNow instance.

    The application adds an **Infisical** menu to the navigator with these modules:

    - **Access Requests**: every request Infisical has sent
    - **Pending Requests**: requests waiting for a decision
    - **Admin Console** (admins only): every request, with a **Resend to Infisical** button for a decision that didn't reach Infisical

    You can't approve or reject a request from these modules. Your approvers decide in the approval steps of your flows, which you build in [Step 3](#step-3-build-the-approval-flow).

  </Step>
  <Step>
    Assign the application's roles:

    | Role | Assign it to |
    | --- | --- |
    | `x_infis_approvals.admin` | The people who manage the integration. The role grants full access to every request, including delete, and the **Admin Console**. |
    | `x_infis_approvals.approver` | Every user or group that an **Ask for Approval** step in your flows names as an approver. |
    | `x_infis_approvals.viewer` | People who only need to read requests and their audit trail. |
    | `x_infis_approvals.secret-manager-integration` | Only the integration user that Infisical signs in as, which you create in [Step 2](#step-2-connect-infisical-to-servicenow). |

  </Step>
</Steps>

## Step 2: Connect Infisical to ServiceNow

Create a ServiceNow integration user, then create a ServiceNow connection in Infisical with that user's credentials. Follow the [ServiceNow connection](/integrations/app-connections/servicenow) guide.

Infisical uses this connection to create each record and to read each decision back. If the connection's credentials stop working, Infisical can't complete the requests waiting in ServiceNow.

## Step 3: Build the approval flow

You define approval routing in Flow Designer. Infisical doesn't set approvers, steps, or SLAs. The fastest way to start is to copy the flow template that the Infisical application includes:

<Steps>
  <Step>
    Go to **All** > **Process Automation** > **Flow Designer**.
  </Step>
  <Step>
    Open **Infisical - Single Approval Template** and select **Copy Flow**.
  </Step>
  <Step>
    Set the trigger condition. The flow runs when a record is created in **Infisical Access Request [x_infis_approvals_access_request]**, and the condition sets which requests the flow handles, such as `Environment is prod` or `Secret Path contains /payments`. The template's condition, `Request Type is Secret Access`, matches every request from Infisical.
  </Step>
  <Step>
    On each **Ask for Approval** step, add the approvers and the number of approvals required. Every approver needs the `x_infis_approvals.approver` role.
  </Step>
  <Step>
    Confirm that every branch, approved and rejected alike, ends with the **Infisical - Notify Decision** action.
  </Step>
  <Step>
    Activate your copy of the flow. The template itself stays inactive.
  </Step>
</Steps>

To build a flow from scratch instead, trigger it when a record is created in **Infisical Access Request**, route the record with **Ask for Approval** steps, and end each branch with **Infisical - Notify Decision**. If you have more than one flow, make their trigger conditions mutually exclusive. If two flows match the same record, approvers get duplicate approvals.

### Notify Infisical of the decision

The **Infisical - Notify Decision** action records the decision on the record, updates the record's **State**, and notifies Infisical. It takes two inputs:

| Input                            | Value                    |
| -------------------------------- | ------------------------ |
| **Access Request**               | The trigger record       |
| **Decision (approved/rejected)** | `approved` or `rejected` |

If **Decision (approved/rejected)** has any other value, the action records no decision and moves the record to **Callback Failed**.

The action returns **Success** and **Message** outputs. You can branch on them to raise an incident or notify an admin if the action can't notify Infisical.

<Warning>
  Every branch that ends your flow must call **Infisical - Notify Decision**. If
  a branch ends without it, the request stays pending in Infisical until it
  expires, and the requester gets no answer.
</Warning>

## Step 4: Enable ServiceNow approvals on an access policy

<Steps>
  <Step>
    In your Secrets Management project, select **Approvals** from the sidebar, open the **Policies** tab, and select **Add Policy**. To change an existing access policy instead, edit it from the same tab.

    ![Approvals in the Sidebar](/images/platform/workflow-integrations/servicenow-integration/approvals-sidebar.png)
    ![Policies Tab](/images/platform/workflow-integrations/servicenow-integration/policies-tab.png)

  </Step>
  <Step>
    Set **Policy Type** to **Access Policy**, then fill out **Policy Name**, **Secret Path**, and **Environments** as for any [access policy](/documentation/platform/access-controls/access-requests#policy-configuration-options). Optionally, set **Request Expiration** to how long a request can wait in ServiceNow before Infisical closes it. If you leave it empty, requests never expire.

    Under **Approval Workflow**, select **External Approval System**, then set:

    - **Provider**: **ServiceNow**
    - **App Connection**: the connection you created in [Step 2](#step-2-connect-infisical-to-servicenow)

    Select **Add Policy**.

    ![Create Access Policy](/images/platform/workflow-integrations/servicenow-integration/create-access-policy.png)

  </Step>
  <Step>
    The policy appears on the **Policies** tab.

    ![Access Policy Created](/images/platform/workflow-integrations/servicenow-integration/access-policy-created.png)

  </Step>
</Steps>

Requests that match this policy now go to ServiceNow. Policies that use the **Infisical** workflow keep using approvers in Infisical, so you can move one environment at a time.

A policy that sends its requests to ServiceNow differs from one with Infisical approvers:

- Nobody can approve its requests in Infisical, so the policy has no approvers, bypassers, or self approval
- You can't edit the policy while it has pending requests (cancel them first: open each request in Infisical and select **Cancel Request**)

## Request access

Requesting access under a ServiceNow policy works like any other [access request](/documentation/platform/access-controls/access-requests#creating-a-request):

<Steps>
  <Step>
    In your Secrets Management project, select **Approvals** from the sidebar, open the **Access Requests** tab, and select **Request Access**.
  </Step>
  <Step>
    Choose an **Environment** and **Secret Path** that the policy covers, pick the permissions, fill out **Duration** and **Note**, then select **Request Access**.

    ![Request Access](/images/platform/workflow-integrations/servicenow-integration/request-access.png)

  </Step>
  <Step>
    The request appears on the **Access Requests** tab as **Pending in ServiceNow** while your flow decides.

    ![Access Request Pending in ServiceNow](/images/platform/workflow-integrations/servicenow-integration/access-request-pending-in-servicenow.png)

  </Step>
  <Step>
    Select the request to open it. Under **Status**, it shows the number of its ServiceNow record, such as `INFAR1000043`, so you can find the record in ServiceNow.

    ![ServiceNow Record Number](/images/platform/workflow-integrations/servicenow-integration/access-request-servicenow-record.png)

  </Step>
</Steps>

## Auditing

Both sides keep their own record:

- In ServiceNow, the access request record carries the full approval history, including who approved at each step and when, through the standard approval and audit tables
- In Infisical, the project's [audit log](/documentation/platform/audit-logs) records the request, the decision received from ServiceNow (`access-approval-request-delegated-decision`), and the resulting access grant

If your flow fills in **Approved By** or **Decision Notes** on the record, Infisical copies them into the decision's audit log event.

## Troubleshooting

<AccordionGroup>
  <Accordion title="A request shows Not Submitted in Infisical">
    Infisical couldn't create the record, and the reason on the request says
    why: the integration user's credentials or role, a missing Infisical
    application, or, if you self-host, a missing `SITE_URL`. Fix the cause, then
    select **Retry**. For connection problems, see [ServiceNow connection
    troubleshooting](/integrations/app-connections/servicenow#troubleshooting).
  </Accordion>
  <Accordion title="A request shows Submitting for a long time">
    Infisical can't reach the instance, or the instance returns errors.
    Infisical keeps trying for about an hour, then closes the request. Check
    that the instance is up and reachable from Infisical.
  </Accordion>
  <Accordion title="Record created but nothing happens">
    No active flow matches the record. Verify your flow is activated and its
    trigger condition matches the record's field values.
  </Accordion>
  <Accordion title="Approvers see duplicate approvals">
    Two flows match the same record. Make the trigger conditions mutually
    exclusive and deactivate the one you no longer want. Only the first flow to
    finish notifies Infisical. In the other flow, **Infisical - Notify
    Decision** returns an error.
  </Accordion>
  <Accordion title="State stuck at Notifying Infisical">
    The flow stopped partway through **Infisical - Notify Decision**. Check the
    flow's **Executions** tab in Flow Designer.
  </Accordion>
  <Accordion title="Callback Failed with HTTP 403">
    Infisical refused the notice because it already applied a decision to this
    request or closed it, the request was deleted along with its project, or
    ServiceNow notified Infisical about the request more than five times. Check
    the request's status in Infisical, and create the request again if the
    requester still needs access.
  </Accordion>
  <Accordion title="Callback Failed with a connection error">
    The ServiceNow instance can't reach the **Callback URL** on the record. Fix
    the instance's outbound firewall rules, then select **Resend to Infisical**
    on the request in the **Admin Console**. If the URL itself is wrong, correct
    `SITE_URL` and create the request again.
  </Accordion>
  <Accordion title="Callback Failed with an invalid decision">
    The flow passed a value other than `approved` or `rejected` to **Infisical -
    Notify Decision**. **Resend to Infisical** can't help, because no decision
    was recorded. Fix the flow, then cancel the request in Infisical and create
    it again.
  </Accordion>
  <Accordion title="Callback Failed on a record that has no callback URL, event, or callback token">
    Someone created the record in ServiceNow by hand, so ServiceNow can't notify
    Infisical about it. Test your flows with requests made in Infisical.
  </Accordion>
  <Accordion title="Request expired before approval">
    The policy's **Request Expiration** elapsed while the request sat in
    ServiceNow. Extend it, or shorten your approval SLA.
  </Accordion>
  <Accordion title="Infisical says the request couldn't be completed in ServiceNow">
    Infisical closed the request without granting access. See [Requests closed
    by Infisical](#requests-closed-by-infisical).
  </Accordion>
</AccordionGroup>

### Requests closed by Infisical

Infisical closes a request without granting access in any of these cases, and shows the reason under the request's **Status**:

- Someone changed the **Permissions** field on the record
- Someone deleted the record from ServiceNow
- ServiceNow rejected the integration user's credentials when Infisical read the decision
- The requester's user was deleted, or the requester is no longer a member of the project
- The decision arrived after the request expired or was cancelled in Infisical
- ServiceNow notified Infisical about the request more than five times
- Infisical couldn't create the record after about an hour of trying

Fix the cause, then create the request again.
