title: "Session logs"
description: "Keep an encrypted record of every request, statement, and command an AI agent makes, stored by Infisical or in your own Amazon S3 bucket."
---

A session log is a record of what an agent does during a [session](/documentation/platform/agent-vault/sessions). For each HTTP request, it holds the method, host, path, status code, whether the proxy attached a credential, and for an [MCP server](/documentation/platform/agent-vault/mcp-servers), the tool the agent called. For a [database or SSH service](/documentation/platform/agent-vault/databases-and-ssh), it holds each statement, command, and file transfer. The [proxy](/documentation/platform/agent-vault/proxies) adds every request it receives to the session log, including requests to hosts that no [access bundle](/documentation/platform/agent-vault/access-bundles) covers.

The proxy encrypts the records before they leave your network, and Infisical stores them for you. If you self-host Infisical, session logs need an enterprise license, and your server administrator [sets up where Infisical stores them](/self-hosting/guides/session-log-storage).

To keep session logs longer than 30 days, or in your own AWS account, [store them in an Amazon S3 bucket you own](/documentation/platform/agent-vault/external-log-storage).

## Viewing session logs

You can view a session's logs if you created the session or you're an admin of its Agent Vault project, for up to 30 days after they're recorded if Infisical stores them (see [Retention](#retention)).

You can filter the rows by outcome and search them by host, path, method, tool, or service, or by the text of a database or SSH row, such as a statement or a command's output. <Tab title="Through the API" id="reading-session-logs-through-the-api">
  The API returns a session's logs as chunks. A chunk is one encrypted batch of [records](#log-contents) that a proxy uploaded.

  <Steps>
    <Step>
      Call [the endpoint that lists session logs](/api-reference/endpoints/agent-vault-session-logs/list). It returns the newest chunks first. To get older chunks, call it again with the response's `nextCursor` as `cursor`.

      <Note>
        If Infisical can't read session logs, the request fails with the error `AgentVaultSessionLogStorageUnavailable`, and the message says why.
      </Note>
    </Step>
    <Step>
      Download each chunk from its `presignedGetUrl` within 5 minutes, before the URL expires.
    </Step>
    <Step>
      Decrypt the chunk with AES-256-GCM. The key is `sessionLogs.sessionKey`, base64 decoded. The first 12 bytes of the chunk are the IV, and the last 16 bytes are the authentication tag. The associated data is the SHA-256 digest of `<sessionId>|<chunkId>|v1`.
    </Step>
    <Step>
      Parse the decrypted bytes as JSON. Each chunk holds an array of records, and `decision` holds the [outcome](#log-contents) in lowercase (`discovery` for **Listed Services**, and `skills` for **Fetched Skills**):

      ```json
      {
        "ts": "2026-09-16T10:31:04.221Z",
        "seq": 8412,
        "proxyId": "<proxy-id>",
        "method": "POST",
        "host": "api.github.com",
        "port": "443",
        "path": "/repos/acme/web/issues",
        "status": 201,
        "decision": "brokered",
        "service": "github",
        "accessBundle": "code-review"
      }
      ```

      If a request matched an MCP service, its record has `serviceType` set to `mcp`. If the request was a JSON `POST`, the record also has an `mcp` object with the [calls](#mcp-tool-calls) in the request:

      ```json
      {
        "serviceType": "mcp",
        "mcp": {
          "calls": [{ "method": "tools/call", "tool": "create_issue" }],
          "parsed": true
        }
      }
      ```

      - `serviceType`: `http`, `mcp`, `postgres`, `mysql`, or `ssh`, or `null` if no service matched the request
      - `mcp`: left out for other requests to an MCP service, such as the `GET` that opens an event stream
      - `mcp.parsed`: `false` if the proxy couldn't read the calls from the request body, such as a compressed body, or if a method or tool name holds characters other than letters, digits, and `_ . : / -` or is longer than 128 characters
      - `mcp.truncated`: `true` if the request held more than 8 calls and the rest weren't recorded (left out otherwise)

      If a record is for a database or SSH service, `method` is `POSTGRES`, `MYSQL`, or `SSH`, `path` is empty, `status` is `0`, and the record has a `native` object with what the connection did:

      ```json
      {
        "method": "POSTGRES",
        "host": "analytics-db.internal",
        "port": "5432",
        "path": "",
        "status": 0,
        "decision": "brokered",
        "service": "analytics",
        "serviceType": "postgres",
        "native": {
          "statement": "SELECT count(*) FROM orders",
          "result": "SELECT 1"
        }
      }
      ```

      Each field of `native` is left out if it's empty:

      - `native.statement`: A PostgreSQL or MySQL statement
      - `native.result`: The statement's result, such as `SELECT 1`, or the error PostgreSQL returned
      - `native.command`: An SSH command, in the record written when the command starts
      - `native.stdin`: Input the agent piped into an SSH command
      - `native.output`: Output from an SSH command or shell
      - `native.file`: An `scp` or `sftp` file operation
      - `native.shell`: `true` for output from an interactive SSH shell
      - `native.note`: A message from the proxy, such as that the agent forwarded a port, or how many records the proxy dropped because the session log was full
      - `native.truncated`: `true` if the proxy cut the text short
    </Step>
  </Steps>

  This Node.js script reads the newest page of a session's logs:

  ```javascript expandable
  import { createDecipheriv, createHash } from "node:crypto";

  const token = "<your-access-token>";
  const sessionId = "<session-id>".toLowerCase();

  const res = await fetch(`https://app.infisical.com/api/v1/agent-vault/sessions/${sessionId}/logs`, {
    headers: { Authorization: `Bearer ${token}` }
  });
  const { sessionLogs, chunks } = await res.json();

  for (const chunk of chunks) {
    const body = Buffer.from(await (await fetch(chunk.presignedGetUrl)).arrayBuffer());

    const aad = createHash("sha256").update(`${sessionId}|${chunk.chunkId}|v1`).digest();
    const decipher = createDecipheriv(
      "aes-256-gcm",
      Buffer.from(sessionLogs.sessionKey, "base64"),
      body.subarray(0, 12)
    );
    decipher.setAAD(aad);
    decipher.setAuthTag(body.subarray(-16));
    const plaintext = Buffer.concat([decipher.update(body.subarray(12, -16)), decipher.final()]);

    console.log(JSON.parse(plaintext.toString("utf8")));
  }
  ```

  <Note>
  The script runs outside a browser, so CORS rules don't apply to it.
  </Note>

  To receive new logs as they arrive, call [the endpoint that tails session logs](/api-reference/endpoints/agent-vault-session-logs/tail) without a cursor, then call it every few seconds with the previous response's `nextCursor`. Any response can repeat a chunk you already read, so skip any chunk whose `chunkId` and `proxyId` you've already read. If a chunk's download returns 404, the proxy may still be uploading it, so try again a few seconds later. If the download still returns 404 after about 2 minutes, stop retrying. If the proxy finishes the upload later, [the endpoint that lists session logs](/api-reference/endpoints/agent-vault-session-logs/list) returns the chunk.

  To export every chunk, page through [the endpoint that lists session logs](/api-reference/endpoints/agent-vault-session-logs/list). The tail is for following new logs as they arrive.
</Tab>
</Tabs>

## Log contents

Each HTTP request produces one record with:

| Field | What it holds |
| --- | --- |
| **Time** | When the request was made |
| **Method**, **Host**, **Path** | Where the request went, for example `POST api.github.com/repos/acme/web/issues` |
| **Upstream status** | The HTTP status code the API returned, such as `201`. For **Blocked** and **Error** requests, it's the status code the proxy returned, such as `403` or `502`. For **Listed Services** and **Fetched Skills** requests, it's the status code Infisical returned |
| **Outcome** | What the proxy did with the request |
| **Service** | The service that matched the request, if any |

The outcome is one of six:

| Outcome | What happened |
| --- | --- |
| **Brokered** | A service matched and the proxy attached its credential to the request |
| **Passthrough** | No service matched, or the matching service has no credential. The proxy forwarded the request without a credential |
| **Blocked** | The proxy refused the request, for one of the reasons in [Blocked requests](/documentation/platform/agent-vault/proxies#blocked-requests), or the service's [hook](/documentation/platform/agent-vault/hooks) denied it |
| **Error** | The proxy couldn't reach the destination host, or the service's hook didn't give a usable answer |
| **Listed Services** | The agent asked the proxy for the [services the session can use](/documentation/platform/agent-vault/service-discovery), and the proxy got the list from Infisical |
| **Fetched Skills** | The proxy got the session's [skills](/documentation/platform/agent-vault/skills) from Infisical, such as when `infisical agent-vault run` installs them |

For HTTP requests, the proxy doesn't record bodies, headers, or query strings. For a request to an MCP server, the proxy reads only the method and tool name of each call from the request body.

If the session log fills up before the proxy uploads it, the proxy drops rows, then adds a row that says how many it dropped.

### MCP tool calls

If a request matched an MCP service, its row shows an **MCP** badge and the call the agent made, in place of the path:

- For a tool call, the tool's name, such as `create_issue`
- For any other call, the method, such as `initialize` or `tools/list`

The proxy never records a tool's arguments or results.

If the agent sent several calls in one request, the row shows the first one. If the proxy can't read the calls, such as from a compressed body, the row shows the request path.

### Database and SSH connections

For a [database or SSH service](/documentation/platform/agent-vault/databases-and-ssh), each row is one thing the connection did, shown with the service type, such as **PostgreSQL**, in place of the method. Select a row to see everything it recorded and copy it.

- **PostgreSQL and MySQL:** A statement and its result, such as `SELECT 42` when PostgreSQL returns 42 rows, but never the rows themselves
- **SSH commands:** A row with the command when it starts, then rows with the input the agent piped into it and its output, written every minute while it runs
- **SSH file transfers:** One `scp` or `sftp` file operation
- **SSH shells:** What the shell printed, in rows of up to 64 KB or one minute

Each statement and command is recorded up to 8 KB, its result or output up to 64 KB, and an SSH command's piped input up to 8 KB. A row that was cut short says so. If an agent forwards a port through an SSH service, a row says so, but the forwarded traffic isn't recorded.

#### Sensitive values in the log

The proxy records statements, commands, and piped input as the agent wrote them, without hiding anything:

- If the agent puts a password in a statement or command, such as in `ALTER USER`, `IDENTIFIED BY`, or input piped to `sudo -S`, the log holds the password
- In an SSH shell, the log holds typed input only if the shell didn't echo it, so a password typed at a prompt is recorded
- For PostgreSQL, the values bound to a prepared statement are recorded with the statement, so the log can hold values from your database (MySQL records the statement without them)

### Turning session logs off

Session logs are on unless an admin turns them off. To stop recording, turn off **Enable** in the **Session Logs** dialog and select **Save**.

Turning session logs off also hides the logs already recorded:

- With default storage, turning session logs back on shows those logs again, as long as they're less than 30 days old
- With external storage, Infisical forgets the bucket and its AWS connection (to see the logs again, set up the same bucket and key prefix)

### Changing the storage location

Infisical doesn't copy existing records when you switch storage or change the bucket or key prefix. Records written before the change don't show in Infisical until you switch back.

If you switch away from default storage, logs already in default storage still expire after 30 days.

### Retention

How long session logs are kept depends on where they're stored:

- **Default storage**: you can look back at the last 30 days of session logs, unless your plan sets a different period
- **External storage**: Infisical never deletes session logs from your bucket (to delete older logs automatically, add an [S3 Lifecycle rule](https://docs.aws.amazon.com/AmazonS3/latest/userguide/object-lifecycle-mgmt.html) to the bucket)

If you use external storage, don't modify or add files in the folder that session logs use. Restrict who in your AWS account can delete or overwrite these files.

## Troubleshooting

If you use default storage and session logs can't be read, contact Infisical support, or your server administrator if you self-host.
