title: "Proxies"
description: "Run the proxy that attaches credentials, set its traffic policy, and understand how agents trust it."
---

A proxy intercepts your agents' requests to the APIs they call, then attaches the necessary API credential to each request that matches a [service](/documentation/platform/agent-vault/services). Run the proxy where agent traffic leaves your network, either on its own host that several agents share, or on the same machine as one agent.

You create a proxy in Infisical, start it from the CLI, and change its settings in Infisical afterwards. A proxy runs in one of two modes, which you pick when you create it.

## Choose where to run the proxy

While you can technically run the agent and the proxy on a single machine, we recommend running the proxy on a different machine from the agent. If the agent and the proxy run on the same machine, the agent could read the proxy's [state directory](#state-directory), which contains sensitive values like the proxy's access token and the private key of its certificate authority.

<Tip>
We also recommend keeping both machines on the same private network. This is because every request the agent makes goes through the proxy, and a round trip between networks adds latency to every request.
</Tip>

## Choose a mode

You pick a proxy's mode when you create it, and you can't change the mode afterwards:

| Mode | Runs as | How it starts | Where it keeps its state |
|------|---------|---------------|--------------------------|
| **Standard** | One machine | Enrolls once with a one-time enrollment token | A [state directory](#state-directory) on the machine |
| **HA** | Any number of copies, such as several machines behind a load balancer, containers, or a sidecar next to each agent | Every copy starts from the same proxy token | Nothing on disk: each copy loads its settings and certificate authority from Infisical when it starts |

Use HA if the proxy needs to keep running when one machine goes down, or if you start a new proxy alongside each agent, such as in a sandbox that gets deleted after every run.

## Supported connections

The proxy attaches credentials to HTTP/1.1 requests, over both HTTPS and plain HTTP. These connections fail through the proxy:

- WebSocket connections, such as to a `wss://` URL
- Clients that only speak HTTP/2, such as gRPC clients

If an API offers both, configure the agent to use its plain HTTPS requests. Many SDKs fall back to HTTPS when a WebSocket connection fails.

## Create and enroll a proxy

<Steps>
  <Step>
    In Agent Vault, go to **Proxies** and select **Create Proxy**.
  </Step>
  <Step>
    Enter a **Name**. To create an [HA proxy](#choose-a-mode), or to set the [traffic policy](#traffic-policy), [exceptions](#exceptions), or [poll interval](#poll-interval) now, expand **Advanced Options**. You can change the settings later, but not the mode.

    <Frame>
      <img src="/images/platform/agent-vault/proxy-create.png" alt="The Create Proxy dialog with the two traffic policy options and the poll interval" />
    </Frame>
  </Step>
  <Step>
    Select **Create**. For a Standard proxy, the **Enrollment Token** dialog shows a one-time token that expires in an hour, and commands for the CLI, Docker, and systemd with your token and instance filled in. For an HA proxy, the **Proxy Token** dialog opens instead, as described in [Run an HA proxy](#run-an-ha-proxy).

    <Frame>
      <img src="/images/platform/agent-vault/proxy-enrollment-token.png" alt="The Enrollment Token dialog with CLI, Docker, and systemd tabs and the one-hour countdown" />
    </Frame>
  </Step>
  <Step>
    Run one of the commands on the machine where the proxy will run.
  </Step>
</Steps>

The commands look like this:

<Tabs>
  <Tab title="CLI">
    ```bash
    infisical agent-vault proxy \
      --enrollment-token <enrollment-token> \
      --domain <your-instance-url>
    ```
  </Tab>
  <Tab title="Docker">
    ```bash
    docker run -d --name agent-vault-proxy \
      -p 17323:17323 \
      -v agent-vault-proxy:/etc/infisical/agent-vault \
      infisical/cli agent-vault proxy \
      --enrollment-token <enrollment-token> \
      --domain <your-instance-url>
    ```

    The volume holds the state directory, so a re-created container resumes instead of needing a new token.
  </Tab>
  <Tab title="systemd">
    ```ini
    [Unit]
    Description=Infisical Agent Vault proxy
    After=network-online.target

    [Service]
    ExecStart=/usr/local/bin/infisical agent-vault proxy --enrollment-token <enrollment-token> --domain <your-instance-url>
    Restart=always

    [Install]
    WantedBy=multi-user.target
    ```

    Save it as `/etc/systemd/system/agent-vault-proxy.service`, then run `sudo systemctl enable --now agent-vault-proxy`.
  </Tab>
</Tabs>

### Command flags

The enrollment command uses these flags:

- `--enrollment-token` is the one-time token from the **Enrollment Token** dialog. Instead of passing the flag, you can set the token in the `INFISICAL_AGENT_VAULT_ENROLLMENT_TOKEN` environment variable.
- `--domain` is your Infisical instance URL. It defaults to Infisical Cloud (US), so you need it for EU Cloud or a self-hosted instance. If you prefer, you can set the URL in the `INFISICAL_DOMAIN` environment variable instead of passing the flag

<Note>
  Other users on the machine can read anything on a command line. To keep the enrollment token off it, put `INFISICAL_AGENT_VAULT_ENROLLMENT_TOKEN=<enrollment-token>` in a file with mode `0600`, and pass the file with `--env-file` for Docker or `EnvironmentFile=` for systemd. You can delete the file once the proxy has enrolled.
</Note>

<Info>
  For the proxy's other flags, such as the port and the state directory, check out the [`agent-vault proxy` CLI reference](/cli/reference#agent-vault-proxy).
</Info>

### State directory

When a Standard proxy enrolls, Infisical gives it a new certificate authority, and the proxy saves the certificate authority with its enrollment in a state directory at `~/.infisical/agent-vault` (or `/etc/infisical/agent-vault` if you run the proxy as the root user on the machine).

The enrollment token only works once. After the first run, the proxy reads its enrollment from the state directory, so you can restart the proxy without `--enrollment-token`:

```bash
infisical agent-vault proxy --domain <your-instance-url>
```

If the state directory is empty, the proxy can't start without a new token. Select **New Enrollment Token** on the proxy's menu and [enroll again](#re-enroll-a-proxy).

## Run an HA proxy

Every copy of an HA proxy starts from the same proxy token. The **Proxy Token** dialog shows the token once, right after you create the proxy, with commands for the CLI, Docker, and Kubernetes:

<Tabs>
  <Tab title="CLI">
    ```bash
    INFISICAL_AGENT_VAULT_PROXY_TOKEN=<proxy-token> \
    infisical agent-vault proxy \
      --domain <your-instance-url>
    ```
  </Tab>
  <Tab title="Docker">
    ```bash
    docker run -d --name agent-vault-proxy \
      -p 17323:17323 \
      -e INFISICAL_AGENT_VAULT_PROXY_TOKEN=<proxy-token> \
      infisical/cli agent-vault proxy \
      --domain <your-instance-url>
    ```

    The container needs no volume, because the proxy saves nothing to disk.
  </Tab>
  <Tab title="Kubernetes">
    ```yaml expandable
    apiVersion: v1
    kind: Secret
    metadata:
      name: agent-vault-proxy
    type: Opaque
    stringData:
      INFISICAL_AGENT_VAULT_PROXY_TOKEN: <proxy-token>
    ---
    apiVersion: apps/v1
    kind: Deployment
    metadata:
      name: agent-vault-proxy
    spec:
      replicas: 2
      selector:
        matchLabels:
          app: agent-vault-proxy
      template:
        metadata:
          labels:
            app: agent-vault-proxy
        spec:
          containers:
            - name: agent-vault-proxy
              image: infisical/cli
              args: ["agent-vault", "proxy", "--domain", "<your-instance-url>"]
              envFrom:
                - secretRef:
                    name: agent-vault-proxy
              ports:
                - containerPort: 17323
    ```
  </Tab>
</Tabs>

Run the same command for each copy you need. Each copy loads the proxy's settings and certificate authority from Infisical when it starts, so every copy serves the same certificate authority and agents can reach any of them. If a copy can't reach Infisical, it retries for 60 seconds and then exits without serving any requests.

<Note>
  Store the proxy token somewhere safe when the dialog shows it. Infisical doesn't show it again, and the only way to get a new token is to [rotate it](#rotate-an-ha-proxys-token), which stops every running copy.
</Note>

You can also pass the token with `--proxy-token`, but other users on the machine can read anything on a command line, so prefer the environment variable.

## Settings

To change a setting, select **Edit Settings** on the proxy's menu. If the proxy is running, it applies the change within one [poll interval](#poll-interval) (60 seconds by default).

### Traffic policy

The **Traffic Policy** setting controls which hosts agents can reach through the proxy:

- **Any host** (default): the proxy forwards every request, and attaches a credential only for hosts covered by a service
- **Access bundle hosts only**: the proxy refuses requests to hosts that no service in the session's access bundle covers, unless the host is an [exception](#exceptions)

<Tip>
Use **Access bundle hosts only** if the proxy can reach systems that agents shouldn't have access to, such as internal services on the same network.
</Tip>

#### Blocked requests

If the policy blocks a request, the proxy still accepts the connection and completes the TLS handshake, so the agent gets a 403 response instead of a connection error:

```text
HTTP/1.1 403 Forbidden

no service covers host "internal.example.com": host blocked by policy
```

The proxy also returns a 403 for:

- A request to a port the service's [host pattern](/documentation/platform/agent-vault/services#host-patterns) doesn't name, such as `example.com:8443` for a service on `example.com`, which only covers port `443`
- A request that breaks the service's [method or path rules](/documentation/platform/agent-vault/services#methods-and-paths), under either traffic policy

### Exceptions

Exceptions allow your agents to access hosts that aren't covered by any service in an access bundle, even when your proxy uses **Access bundle hosts only**. Use exceptions for hosts every agent needs, such as a package registry or a documentation site.

To add exceptions, select the policy and enter the hosts in **Exceptions** as a comma-separated list. The field doesn't appear under **Any host**, because that policy already lets every host through.

Exception hosts behave differently from hosts that are covered by services:

- **Credentials:** The proxy never attaches a credential to requests to an exception host
- **Ports:** An exception with no port matches the host on every port, while a [service's host pattern](/documentation/platform/agent-vault/services#default-port) with no port only matches port `443`
- **Interception:** The proxy still decrypts requests to an exception host, but doesn't block them
- **Scope:** An exception applies to every agent that uses the proxy

<Tip>
To let only one access bundle reach a host, add a [pass-through service](/documentation/platform/agent-vault/services#pass-through) to that bundle instead of adding an exception to the proxy.
</Tip>

### Poll interval

The poll interval is how often, in seconds, the proxy re-checks each active session with Infisical and applies settings changes. It defaults to 60 and can be set from 10 to 300.

If the proxy can't reach Infisical:

- The proxy keeps using the session data it last fetched for five poll intervals
- After that, the proxy refuses the affected requests with a 502 until it reaches Infisical again, instead of forwarding them without their credentials
- The **Proxies** page marks the proxy **Unreachable** after three missed check-ins

## Certificate trust

The proxy decrypts HTTPS traffic to attach the credential, so each agent has to trust the proxy's certificate authority (CA). Infisical generates a self-signed CA for each proxy: when a Standard proxy enrolls, and when you create an HA proxy or rotate its token.

<Tabs>
  <Tab title="With the CLI">
    If you start the agent with `infisical agent-vault run`, the CLI sets up trust for you. On every run, it fetches the certificate from the proxy and sets these variables for the agent: `SSL_CERT_FILE`, `NODE_EXTRA_CA_CERTS`, `REQUESTS_CA_BUNDLE`, `CURL_CA_BUNDLE`, `GIT_SSL_CAINFO`, and `DENO_CERT`.

    On macOS, if you run the CLI in a terminal, it also adds the certificate to your login keychain for tools such as `gh` and `docker` that read the system trust store. macOS asks you to approve the change. To skip this step on a machine that already trusts the proxy, pass `--no-ca-trust`.
  </Tab>
  <Tab title="Without the CLI">
    If you start the agent another way, such as in a container that sets `HTTPS_PROXY` itself, set up trust yourself:

    <Steps>
      <Step>
        Download the certificate from the proxy:

        ```bash
        curl -s http://<proxy-address>/_agent-vault/ca | jq -r .certificate > ca.pem
        ```
      </Step>
      <Step>
        Mount `ca.pem` where the agent can read it, and point the agent's CA variables at it, such as `SSL_CERT_FILE` and `NODE_EXTRA_CA_CERTS`.
      </Step>
      <Step>
        Route the agent through the proxy, with the session token as the password:

        ```bash
        export HTTPS_PROXY="http://x-agent-vault:<session-token>@<proxy-address>"
        export HTTP_PROXY="$HTTPS_PROXY"
        ```
      </Step>
    </Steps>

    To set the proxy and the certificate in your own agent's code instead, see [Connect your own agent](/documentation/platform/agent-vault/guides/custom-agent).
  </Tab>
</Tabs>

<Warning>
Agents send their session token to the proxy unencrypted with every request. If someone can read that traffic and reach the proxy, they can use the token to call every API in the session's access bundle with its real credentials. The token keeps working until the session expires or you [revoke it](/documentation/platform/agent-vault/sessions#revoke-a-session).

For this reason, we recommend running the proxy where only your agents can reach it, such as on the same host, a private network, or a container network.
</Warning>

### Pin the proxy's certificate

If the agent runs on a network you don't fully control, pin the proxy's certificate so the agent only talks to your proxy. Copy the fingerprint from the **Certificate Authority** column on the **Proxies** page, and pass it with `--ca-fingerprint`:

```bash
infisical agent-vault run --session-token <session-token> --proxy <proxy-address> --ca-fingerprint SHA256:9F:2C:... -- claude
```

If the proxy's certificate doesn't match, the CLI stops before starting the agent.

  <img src="/images/platform/agent-vault/proxies-list.png" alt="The Proxies page showing two healthy proxies with their traffic policy and certificate authority fingerprints" />
</Frame>

### Use your own certificate authority

To serve your own CA instead of the one Infisical generates, pass it to the proxy with `--ca-cert` and `--ca-key`, or with the `INFISICAL_AGENT_VAULT_CA_CERT` and `INFISICAL_AGENT_VAULT_CA_KEY` environment variables. Each value can be the PEM text, the PEM encoded as base64, or the path to a PEM file. The key has to be an ECDSA key.

```bash
infisical agent-vault proxy --enrollment-token <enrollment-token> --ca-cert ./ca.crt --ca-key ./ca.key
```

- **Standard proxy:** pass the CA when you enroll. Infisical keeps only its fingerprint, and on later starts the proxy serves the CA from its state directory
- **HA proxy:** pass the same CA to every copy. Each copy reports the CA it serves when it starts, and the **Proxies** page shows the fingerprint that the most recent copy reported

To go back to a CA that Infisical generates, re-enroll a Standard proxy without the flags, or start the copies of an HA proxy without them.

### APIs with a private certificate authority

The proxy checks the certificate of each API it connects to, the way any HTTPS client does. If an API uses a private certificate authority, the machine running the proxy has to trust that authority. The agent's machine doesn't need to trust it.

### Re-enroll a proxy

To re-enroll a Standard proxy, select **New Enrollment Token** on the proxy's menu and run the new command. The proxy keeps its name, settings, and history, but gets a new certificate authority.

### Rotate an HA proxy's token

To get a new token for an HA proxy, select **Rotate Proxy Token** on the proxy's menu. Rotating replaces both the token and the certificate authority:

1. Every running copy stops within about two minutes, because Infisical no longer accepts the old token
2. The **Proxy Token** dialog shows the new token and the new CA fingerprint
3. Start the copies again with the new token

### After the certificate authority changes

After you re-enroll a Standard proxy or rotate an HA proxy's token:

- Restart every agent that uses the proxy, because those agents still trust the old certificate
- Update any `--ca-fingerprint` pin
- Replace any mounted copy of the certificate
- On macOS, replace the certificate in your login keychain

## Revoke or delete a proxy

Both actions are on the proxy's menu:

| Action | What happens |
|--------|--------------|
| **Revoke Access** | The proxy's token stops working right away. Every agent using the proxy loses its credentials, and the proxy answers requests with a 503. The proxy process exits after two failed check-ins in a row (one to two [poll intervals](#poll-interval)). For an HA proxy, every copy stops |
| **Delete** | Infisical removes the proxy. If the proxy is running, it stops working and exits the same way as a revoked proxy |

Revoke access if you think the proxy's host is compromised. To bring a revoked proxy back, [re-enroll it](#re-enroll-a-proxy), or for an HA proxy, [rotate its token](#rotate-an-ha-proxys-token).
