A proxy is the process that attaches credentials. It runs where agent traffic leaves your network: on a server that many agents share, or as a sidecar next to one agent. You create it in the dashboard, enroll it once from the CLI, and change its settings from the dashboard afterwards.

<Info>
  This page is for the people who run proxies. Members see the Proxies page too, with each proxy's name, health, and certificate fingerprint, because that's where a fingerprint for pinning comes from.
</Info>

## Enrolling

Go to **Proxies**, select **Create Proxy**, name it, and select **Create Proxy** again to confirm. The dialog shows a one-time enrollment token, valid for an hour, and the command to run where the proxy will live:

```bash
infisical av proxy --enrollment-token <enrollment-token>
```

The proxy generates its own certificate authority, sends the certificate to Infisical, and starts serving on port `17323`. It writes its state to `~/.infisical/agent-vault`, or `/etc/infisical/agent-vault` when run as root, and reads it back on the next start. Passing the same enrollment token again on a restart is fine: the proxy recognizes it and serves without re-enrolling. That only holds while the state directory survives, so run the proxy somewhere its filesystem persists. An enrollment token is good for one enrollment, and a proxy that starts with an empty state directory has to enroll again with a new one.

The same dialog has snippets for Docker and systemd. Select **New Enrollment Token** on a proxy's menu if the token expired before you used it.

### Keeping the token off the command line

Anything on a command line is readable by other users on the machine: `docker inspect` prints a container's arguments, a systemd unit file is world-readable, and both show up in `ps`. Pass the token through the environment instead, and give the file holding it mode `0600`:

```bash
# av.env
INFISICAL_AGENT_VAULT_ENROLLMENT_TOKEN=<enrollment-token>
```

Docker reads it with `--env-file ./av.env`, and a systemd unit with `EnvironmentFile=/etc/infisical/av.env`. Drop `--enrollment-token` from the command in both cases. The token is single-use and short-lived, so this matters most on a shared machine, and you can delete the file once the proxy has enrolled.

<Note>
  Run `infisical av proxy --port 18000` to listen elsewhere. The default `17323` is chosen so that an Agent Vault proxy and a Secrets Management [Agent Proxy](/documentation/platform/agent-proxy/overview), which listens on `17322`, can share a machine.
</Note>

## Settings

Every setting lives in Infisical and reaches a running proxy on its next poll, so there are no traffic flags on the command line. Select **Edit Settings** on the proxy's menu to change them.

### Unmatched hosts

What the proxy does with a request to a host no connection in the session covers.

- **Allow**, the default: the request passes through with no credential attached. The proxy still terminates TLS on it, so the agent trusts the proxy's certificate for that host too.
- **Deny**: the request is rejected with `403`. The agent reaches the hosts in its bundles, the bypass list, and nothing else.

Under **Allow**, a pass-through connection changes nothing, since the host would pass anyway. Under **Deny**, a pass-through connection is how you make a host reachable without giving it a credential.

Addresses on a private network are reachable, so an internal API inside your own network can be a connection like any other. Under **Deny** the proxy reaches only the hosts you configure, which is what to use when the proxy sits somewhere it could reach more than you intend.

### Bypass hosts

A comma-separated list of hosts that stay reachable under **Deny**. They're handled like every other host, with the proxy's certificate and no credential attached, so this is the proxy-wide equivalent of giving each of them a pass-through connection.

Use it when the hosts are a property of the deployment rather than of one bundle, such as a documentation site or a package registry every agent needs. It's set by whoever runs the proxy; pass-through connections are set by whoever owns the bundle.

Under **Allow** the list changes nothing, since those hosts are reachable anyway. A host one of your bundles covers still gets its credential.

### Poll interval

How often, in seconds, the proxy re-checks each active session with Infisical and picks up settings changes. The default is 60, and the range is 10 to 300. Everything on this page and on [Sessions](/documentation/platform/agent-vault/sessions) that says "within one poll interval" means this number.

If Infisical is unreachable, the proxy keeps serving what it last knew for five poll intervals, then stops serving those sessions until it can check again. A session that comes back revoked, expired, or removed is dropped on the poll that says so.

The Proxies page marks a proxy unhealthy sooner than that, after three missed check-ins. The two counts measure different things: three is when the dashboard stops believing the proxy is up, five is how long the proxy itself keeps working without an answer.

## Certificate trust

The proxy terminates TLS to see the request it's attaching a credential to, so each agent has to trust the proxy's certificate authority. Every proxy has its own; nothing is shared across proxies or with Infisical.

`infisical av run` fetches the certificate from the proxy on every run, writes it to `~/.infisical/agent-vault/ca.pem`, and sets `SSL_CERT_FILE`, `NODE_EXTRA_CA_CERTS`, `REQUESTS_CA_BUNDLE`, `CURL_CA_BUNDLE`, `GIT_SSL_CAINFO`, and `DENO_CERT` for the agent. On macOS it also adds the certificate to your login keychain, because Go programs such as `gh` and `docker` read the system trust store rather than those variables. You can decline the keychain prompt; only those programs are affected. The prompt is skipped where nothing can answer it, such as CI, and `--no-ca-trust` skips the step entirely.

Run the proxy where only your agents can reach it: the same host, a private network, or a container network. The agent trusts whatever answers at the proxy's address, so pin the fingerprint when the agent runs somewhere you don't fully control.

### Pinning

To rule out a stand-in proxy, pass the fingerprint from the Proxies page:

```bash
infisical av run --token <session-token> --proxy <proxy-address> --ca-fingerprint SHA256:9F:2C:... -- claude
```

The CLI aborts before writing anything if the served certificate doesn't match. Pin when the agent runs on a network you don't fully control, or when the token would be costly to lose. Most deployments inside a private network don't need to.

An agent that isn't launched by the CLI, such as a container that sets `HTTPS_PROXY` itself, needs the certificate mounted and those variables set by whoever builds the container. Fetch it from `http://<proxy-address>/_agent-vault/ca`.

### Re-enrolling

Selecting **New Enrollment Token** and enrolling again replaces the proxy's certificate authority. The proxy keeps its name, settings, and history, and `infisical av run` picks up the new certificate on its next run. Three things hold a copy and break until updated: an explicit `--ca-fingerprint` pin, any file or image that carries the old certificate, and a macOS keychain entry that `av run` created earlier.

## Revoking and deleting

**Revoke Access** on a proxy's menu invalidates its token within one poll interval. Every agent routed through it loses credentials until the proxy is enrolled again. Use it when you believe the proxy host is compromised. **Delete** removes the proxy record; a running process for it stops being able to resolve sessions.

## What the proxy can't carry

Two kinds of traffic don't work through the proxy in this release. Each fails with an explicit error rather than hanging.

- **WebSockets.** Connections that upgrade from HTTP, such as MCP servers over WebSocket, Slack Socket Mode, the OpenAI Realtime API, and `kubectl exec`.
- **HTTP/2-only clients.** Clients that refuse to speak HTTP/1.1, including gRPC, Google Cloud SDKs, and Temporal.

Streaming responses are carried for as long as they keep producing, so server-sent events and other long-lived streams stay open. A response that produces nothing for five minutes is closed.

Point clients that need any of these at the upstream directly, outside the proxy, until it supports them.
