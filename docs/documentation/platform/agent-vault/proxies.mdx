A proxy intercepts your agents' requests to the APIs they call, then attaches the necessary API credential to each request that matches a [service](/documentation/platform/agent-vault/services). You can run one proxy on its own host that several agents share, or a separate proxy for each agent, such as in a sidecar container.

You create a proxy in an [Agent Vault project](/documentation/platform/agent-vault/projects), start it with the proxy token that Infisical shows you, and change its settings in Infisical afterwards. You can run the same proxy on as many machines as you need with one token, such as several machines behind a [load balancer](#high-availability).

A proxy only serves sessions from its own project, so if you have more than one project, each project needs its own proxy. Each project can have up to 10 proxies.

## Choose where to run the proxy

You can run the proxy in one of two ways:

- **[One proxy for several agents](/documentation/platform/agent-vault/how-it-works#common-proxy):** one proxy runs on its own machine or as a [Kubernetes Deployment](/documentation/platform/agent-vault/guides/kubernetes), and every agent sends its requests to it. Agents send their session token to the proxy over plain HTTP, so this is suitable only for agents on a private network that you control
- **[One proxy per agent](/documentation/platform/agent-vault/how-it-works#one-proxy-per-agent):** the orchestrator starts a proxy in a separate container with each agent, such as a [Modal sidecar](/documentation/platform/agent-vault/guides/modal) or a [linked Daytona sandbox](/documentation/platform/agent-vault/guides/daytona), and stops the proxy when the agent finishes. This is suitable for a managed sandbox platform, where a shared proxy would have to accept connections from the internet

If your agents run in [E2B sandboxes](/documentation/platform/agent-vault/guides/e2b), run one proxy for several agents on a public machine, with the [SOCKS5 port](/documentation/platform/agent-vault/socks5) turned on. E2B connects to the proxy from its own servers, so the proxy can't be on a private network.

Either way, we recommend running the proxy separately from the agent, either in its own container or on its own machine. If the agent and the proxy run in the same environment, the agent can read the proxy token and the private key of the proxy's certificate authority.

<Tip>
If you run a shared proxy, we recommend keeping it on the same private network as your agents. Every request the agent makes goes through the proxy, and a round trip between networks adds latency to every request.
</Tip>

## Supported connections

Agents connect to the proxy as an HTTP proxy. If you turn on the [SOCKS5 port](/documentation/platform/agent-vault/socks5), clients such as E2B can also connect over SOCKS5 over TLS. To reach [databases and SSH servers](/documentation/platform/agent-vault/databases-and-ssh), agents run `infisical agent-vault connect`, which connects to the proxy's HTTP port over TLS.

Over either connection, the proxy attaches credentials to HTTP/1.1 requests, over both HTTPS and plain HTTP. These connections fail through the proxy:

- WebSocket connections, such as to a `wss://` URL
- Clients that only speak HTTP/2, such as gRPC clients
- Other TCP traffic through the SOCKS5 port, such as an `ssh` or `psql` client that connects directly

If an API offers both WebSocket connections and plain HTTPS requests, configure the agent to use the HTTPS requests. Many SDKs fall back to HTTPS when a WebSocket connection fails.

## Create a proxy and start it

<Steps>
  <Step>
    In your Agent Vault project, go to **Proxies** and select **Create Proxy**.
  </Step>
  <Step>
    Enter a **Name**. Optionally, add a **Description**. To set the [traffic policy](#traffic-policy), [exceptions](#exceptions), or [poll interval](#poll-interval) now, expand **Advanced Options**. You can change these settings later.

    <Frame>
      <img src="/images/platform/agent-vault/proxy-create.png" alt="The Create Proxy dialog with egress-1 as the name, a description, and Advanced Options expanded to show the Any host and Service hosts only traffic policies and a poll interval of 60" />
    </Frame>
  </Step>
  <Step>
    Select **Create**. The **Proxy Token** dialog shows the proxy token, and commands for the CLI, systemd, Docker, and Kubernetes with your token and instance filled in.

    <Frame>
      <img src="/images/platform/agent-vault/proxy-token.png" alt="The Proxy Token dialog showing the proxy token once, with CLI, systemd, Docker, and Kubernetes tabs and the CLI command to start the proxy" />
    </Frame>
  </Step>
  <Step>
    Run one of the commands on each machine where the proxy will run.
  </Step>
</Steps>

The commands look like this:

<Tabs>
  <Tab title="CLI">
    ```bash
    INFISICAL_AGENT_VAULT_PROXY_TOKEN=<proxy-token> \
    infisical agent-vault proxy \
      --domain <your-instance-url>
    ```
  </Tab>
  <Tab title="Docker">
    ```bash
    docker run -d --name agent-vault-proxy \
      -p 17323:17323 \
      -v agent-vault-proxy:/etc/infisical/agent-vault \
      -e INFISICAL_AGENT_VAULT_PROXY_TOKEN=<proxy-token> \
      infisical/cli agent-vault proxy \
      --domain <your-instance-url>
    ```

    The volume keeps the proxy's [cache](#command-flags), so the proxy can start even if Infisical is unreachable.
  </Tab>
  <Tab title="Kubernetes">
    ```yaml expandable
    apiVersion: v1
    kind: Secret
    metadata:
      name: agent-vault-proxy
    type: Opaque
    stringData:
      INFISICAL_AGENT_VAULT_PROXY_TOKEN: <proxy-token>
    ---
    apiVersion: apps/v1
    kind: Deployment
    metadata:
      name: agent-vault-proxy
    spec:
      replicas: 2
      selector:
        matchLabels:
          app: agent-vault-proxy
      template:
        metadata:
          labels:
            app: agent-vault-proxy
        spec:
          containers:
            - name: agent-vault-proxy
              image: infisical/cli
              args: ["agent-vault", "proxy", "--domain", "<your-instance-url>"]
              envFrom:
                - secretRef:
                    name: agent-vault-proxy
              ports:
                - containerPort: 17323
    ---
    apiVersion: v1
    kind: Service
    metadata:
      name: agent-vault-proxy
    spec:
      selector:
        app: agent-vault-proxy
      ports:
        - port: 17323
          targetPort: 17323
    ```

    The manifest in the dialog has no Service. Add the Service from the end of this example so that agents in the cluster can reach the proxy at `agent-vault-proxy:17323`.
  </Tab>
  <Tab title="systemd">
    Save the token in `/etc/infisical/agent-vault-proxy.env`:

    ```bash
    INFISICAL_AGENT_VAULT_PROXY_TOKEN=<proxy-token>
    ```

    Run `sudo chmod 600 /etc/infisical/agent-vault-proxy.env` so that only root can read the file. Then save this unit as `/etc/systemd/system/agent-vault-proxy.service`:

    ```ini
    [Unit]
    Description=Infisical Agent Vault proxy
    After=network-online.target
    Wants=network-online.target

    [Service]
    EnvironmentFile=/etc/infisical/agent-vault-proxy.env
    ExecStart=/usr/local/bin/infisical agent-vault proxy --domain <your-instance-url>
    Restart=always

    [Install]
    WantedBy=multi-user.target
    ```

    Run `sudo systemctl enable --now agent-vault-proxy` to start the proxy now and every time the machine boots.
  </Tab>
</Tabs>

### Command flags

The commands use these settings:

- `INFISICAL_AGENT_VAULT_PROXY_TOKEN` or `--proxy-token`: the proxy token (prefer the environment variable, because other users on the machine can read anything on a command line)
- `--domain` or `INFISICAL_DOMAIN`: your Infisical instance URL (required for EU Cloud and self-hosted instances, because the default is Infisical Cloud in the US)

The HTTP port listens on all interfaces. To make it listen on one address only, such as `127.0.0.1`, pass `--listen-host` or set `INFISICAL_AGENT_VAULT_LISTEN_HOST`. To also accept SOCKS5 connections, see [SOCKS5](/documentation/platform/agent-vault/socks5).

Each time the proxy starts, it loads its settings and certificate authority from Infisical and, if it can, saves a copy in its data directory (`~/.infisical/agent-vault`, or `/etc/infisical/agent-vault` as root, or `--data-dir`). If it can't reach Infisical for 60 seconds, it starts from that copy, or exits if there isn't one.

<Info>
  For the proxy's other flags, such as the port and the data directory, check out the [`agent-vault proxy` CLI reference](/cli/reference#agent-vault-proxy).
</Info>

### Traffic policy

The **Traffic Policy** setting controls which hosts agents can reach through the proxy:

- **Any host** (default): the proxy forwards every request, and attaches a credential only for hosts covered by a service
- **Service hosts only**: the proxy refuses requests to hosts that none of the session's services cover, unless the host is an [exception](#exceptions) (the session's services are the ones in its access bundle and its [inline services](/documentation/platform/agent-vault/inline-services))

<Tip>
Use **Service hosts only** if the proxy can reach systems that agents shouldn't have access to, such as internal services on the same network.
</Tip>

#### Blocked requests

If the policy blocks a request, the proxy still accepts the connection and completes the TLS handshake, so the agent gets a 403 response instead of a connection error. The response body is JSON with an error code, the reason, and a hint for the agent:

```text
HTTP/1.1 403 Forbidden
Content-Type: application/json
X-Agent-Vault-Decision: blocked

{"error":"host_not_allowed","message":"no service covers host \"internal.example.com\": host blocked by policy","hint":"This is the Agent Vault proxy, not the API: it only lets through hosts a service in this session covers. https://app.infisical.com/api/v1/agent-vault/session/services lists them."}
```

Every response that goes through the proxy has an [`X-Agent-Vault-Decision` header](#responses-from-the-proxy), so an agent can tell the proxy's responses apart from the API's.

The proxy also returns a 403 for:

- A request to a port the service's [host pattern](/documentation/platform/agent-vault/http-apis#host-patterns) doesn't name, such as `example.com:8443` for a service on `example.com`, which only covers port `443`
- A request that breaks the service's [method or path rules](/documentation/platform/agent-vault/http-apis#methods-and-paths), under either traffic policy
- A request to a service whose [personal values](/documentation/platform/agent-vault/access-bundles#set-up-your-personal-values) aren't set up yet for the session's owner, or, for a session [on behalf of a user](/documentation/platform/agent-vault/sessions-on-behalf-of-users), for that user
- A request that the service's [hook](/documentation/platform/agent-vault/hooks) denies
- On Infisical Cloud, a request after the organization used its free requests for the month (an admin can add a payment method in **Usage & Billing**)

For an [MCP service that allows only some tools](/documentation/platform/agent-vault/mcp-servers#allowed-tools), the proxy also blocks:

- A call to a tool the service doesn't allow. The agent gets an MCP error that names the tool
- A request the proxy can't read to check which tools it calls, such as a compressed body, a body in a character set other than UTF-8, or JSON that isn't a valid MCP message or doesn't match its `Mcp-Method` and `Mcp-Name` headers. The proxy also blocks a request with a body that isn't a `POST`. The agent gets a 400
- A request with a body larger than 32 MiB. The agent gets a 413

### Exceptions

Exceptions allow your agents to access hosts that none of the session's services cover, even when your proxy uses **Service hosts only**. Use exceptions for hosts every agent needs, such as a package registry or a documentation site.

To add exceptions, select the policy and enter the hosts in **Exceptions** as a comma-separated list. The field doesn't appear under **Any host**, because that policy already lets every host through.

Exception hosts behave differently from hosts that are covered by services:

- **Credentials:** The proxy never attaches a credential to requests to an exception host
- **Ports:** An exception with no port matches the host on every port, while a [service's host pattern](/documentation/platform/agent-vault/http-apis#default-port) with no port only matches port `443`
- **Interception:** The proxy still decrypts requests to an exception host, but doesn't block them
- **Scope:** An exception applies to every agent that uses the proxy

<Tip>
To let only one access bundle reach a host, add a [pass-through service](/documentation/platform/agent-vault/http-apis#pass-through) to that bundle instead of adding an exception to the proxy.
</Tip>

### Poll interval

The poll interval is how often, in seconds, the proxy re-checks each active session with Infisical and applies settings changes. It defaults to 60 and can be set from 10 to 300.

If the proxy can't reach Infisical:

- The proxy keeps using the session data it last fetched for five poll intervals
- After that, the proxy refuses the affected requests with a 502 until it reaches Infisical again, instead of forwarding them without their credentials
- The **Proxies** page marks the proxy **Unreachable** after three missed check-ins

## Responses from the proxy

Every response that goes through the proxy has an `X-Agent-Vault-Decision` header, so an agent can tell a response from the proxy apart from a response from the API:

| Value | What the proxy did |
| --- | --- |
| `brokered` | Added a service's credential to the request. If the API still answers `401` or `403`, the service's stored [credential](/documentation/platform/agent-vault/http-apis#credential-types) is wrong or lacks a permission |
| `passthrough` | Sent the request on without a credential, because no service covers the host |
| `blocked` | Refused the request, for one of the reasons in [Blocked requests](#blocked-requests) |
| `error` | Couldn't complete the request, such as when it can't reach the host |
| `discovery` | Got the [list of services](/documentation/platform/agent-vault/service-discovery#get-the-list) from Infisical for the session |
| `skills` | Got the session's [skills](/documentation/platform/agent-vault/skills) from Infisical, such as when `infisical agent-vault run` installs them |

If a service matched the request, the `X-Agent-Vault-Service` header names the service. If the proxy refuses a request, the response body is JSON with an error code, a message, and a hint that tells the agent what to do next.

## Rotate a proxy's token

Rotate the token if it leaked, or to bring back a proxy whose access you revoked:

<Steps>
  <Step>
    On the **Proxies** page, select **Rotate Proxy Token** on the proxy's menu, then select **Rotate**.
  </Step>
  <Step>
    Store the new token from the **Proxy Token** dialog somewhere safe.
  </Step>
  <Step>
    Restart the proxy with the new token on every machine where it runs.
  </Step>
</Steps>

The current token will stop working, and the proxy gets a new certificate authority. After you rotate the token:

- Restart every agent that uses the proxy, because those agents still trust the old certificate
- Update any `--ca-fingerprint` pin
- Replace any `ca.pem` file you mounted for an agent
- Download the CA again for any SOCKS5 client you gave it to
- On macOS, replace the certificate in your login keychain

If you [use your own certificate authority](/documentation/platform/agent-vault/certificate-trust#use-your-own-certificate-authority), only the token changes, so your agents don't need these updates.

## Revoke or delete a proxy

Both actions are on the proxy's menu:

| Action | What happens |
|--------|--------------|
| **Revoke Access** | The proxy will stop adding credentials to requests. To bring it back, [rotate its token](#rotate-a-proxy’s-token) |
| **Delete** | Infisical removes the proxy, and the proxy will stop adding credentials to requests. You can't undo this |

Revoke access if you think a machine running the proxy is compromised.

## High availability

To keep the proxy available when one machine goes down, run it on several machines with the same proxy token and put a load balancer in front of them. Every machine serves the same certificate authority, so agents trust whichever machine they reach.

- **Load balancer type:** use a TCP (layer 4) load balancer, because agents send `CONNECT` requests that most HTTP load balancers don't forward. You don't need sticky sessions
- **Health checks:** send an HTTP `GET` to `/_agent-vault/ca` on each machine, which returns `200` while the proxy is serving (if the HTTP port only listens locally, open a TCP connection to the SOCKS5 port instead)
- **Your own certificate authority (optional):** if you want to [use your own](/documentation/platform/agent-vault/certificate-trust#use-your-own-certificate-authority), pass the same `--ca-cert` and `--ca-key` to every machine

Point agents at the load balancer's address instead of a single machine.

On Infisical Cloud, every machine running a proxy shares that proxy's [rate limits](/api-reference/overview/rate-limits).
