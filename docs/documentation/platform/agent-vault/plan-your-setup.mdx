## Your setup

<AgentVaultSetupSummary />

### Sessions

<AgentVaultSetupBranch building="personal">
  You create each session in the Infisical dashboard (steps 1 and 2 in the diagram), then start the agent with the session token (step 3). The agent only gets the session token, never your Infisical login or the real API credentials.

  When you create the session, set **Expires** to **8 hours**, so that the session ends with your working day. Create a new session the next time you start working.
</AgentVaultSetupBranch>

<AgentVaultSetupBranch building="assistant">
  You create one session in the Infisical dashboard with **Expires** set to **Never** (steps 1 and 2 in the diagram), and start the assistant with the session token on the assistant's host (step 3). The assistant uses that session for as long as it runs, so the [session logs](/documentation/platform/agent-vault/session-logs) for that one session show every request the assistant makes.

  <ul>
    <li>The assistant's host only holds the session token, not an Infisical login or a machine identity's credentials</li>
    <li>To stop the assistant from using the real credentials, [revoke the session](/documentation/platform/agent-vault/sessions#revoke-a-session)</li>
  </ul>
</AgentVaultSetupBranch>

<AgentVaultSetupBranch building="scheduled">
  The job's host holds the credentials of a [machine identity](/documentation/platform/identities/machine-identities). Each time the job runs, the Infisical CLI logs in as the machine identity and creates a session (steps 1 and 2 in the diagram), starts the agent (step 3), and revokes the session when the agent exits (step 7).

  <ul>
    <li>Grant the machine identity only the access bundle that this agent uses: the agent can read the machine identity's credentials from its environment, and use them to create a session for any access bundle the machine identity has</li>
    <li>Set the session length a little longer than the longest run you expect, because the agent loses access to the APIs if a run outlasts its session</li>
  </ul>
</AgentVaultSetupBranch>

<AgentVaultSetupBranch building="platform">
  An orchestrator, such as a job runner or a backend service, holds the credentials of a [machine identity](/documentation/platform/identities/machine-identities). For each task, the orchestrator creates a session through the Infisical API (steps 1 and 2 in the diagram), starts an agent on a separate host with only the session token (step 3), and revokes the session when the task ends (step 7).

  <ul>
    <li>Run the orchestrator on a different host from the agents: the machine identity that the orchestrator uses can create sessions for every access bundle it's granted, so an agent that reads its credentials could reach every service in those access bundles</li>
    <li>Create an access bundle for each kind of task, and choose the access bundle when the orchestrator creates the session</li>
    <li>Create one session for each task, not one for each turn of a conversation: a revoked session keeps working for up to one [poll interval](/documentation/platform/agent-vault/proxies#poll-interval), so creating a session for each turn doesn't shorten the agent's access and only splits one task's requests across many sessions</li>
  </ul>
</AgentVaultSetupBranch>

<AgentVaultSetupBranch runs="computer">
  <Warning>
    The agent runs as your user account. If you're logged in to the Infisical CLI on the same computer, the agent can run Infisical CLI commands with your login. Run `infisical logout` before you start the agent, or run the agent on a separate server or VM instead.
  </Warning>
</AgentVaultSetupBranch>

### Proxy

The agent sends each API request to the proxy with its session token (step 4 in the diagram). The proxy gets the session's credentials from Infisical (step 5), attaches the real credential, and sends the request on to the API (step 6).

<ul>
  <li>Run the proxy on a different machine from the agent, on the same private network: if the proxy runs on the agent's machine, the agent can read the proxy's [state directory](/documentation/platform/agent-vault/proxies#state-directory), which holds the proxy's access token</li>
  <AgentVaultSetupBranch runs="computer">
    <li>If you don't have a second machine, run the proxy on a small VM on your network</li>
  </AgentVaultSetupBranch>
  <AgentVaultSetupBranch building="scheduled,platform">
    <li>Run one proxy that stays running, and point every agent at it, instead of starting a proxy for each job</li>
  </AgentVaultSetupBranch>
  <AgentVaultSetupBranch runs="container">
    <li>Don't mount the proxy's state directory into an agent's container</li>
  </AgentVaultSetupBranch>
  <AgentVaultSetupBranch runs="ci">
    <li>If the proxy is on a private network, run the job on a [self-hosted runner](https://docs.github.com/en/actions/hosting-your-own-runners) in that network, so that the runner can reach the proxy</li>
  </AgentVaultSetupBranch>
</ul>
