## Your setup

<AgentVaultSetupSummary />

<AgentVaultSetupLayout aside={<AgentVaultSetupDiagram reveal />}>

<AgentVaultSetupStep step="before">
  Before running an agent, you set up two things:

  <ul>
    <li>An [access bundle](/documentation/platform/agent-vault/access-bundles) in Infisical: a list of the [services](/documentation/platform/agent-vault/services) (the external APIs or MCP servers) that the agent can use, each with its real credential</li>
    <li>A running [proxy](/documentation/platform/agent-vault/proxies): a program outside the agent's environment that every request from the agent goes through</li>
  </ul>

  <AgentVaultSetupBranch building="scheduled">
    <Note>
    One proxy stays running and handles the requests from every agent and every job, so you don't need a separate proxy for each job or each host.
    </Note>
  </AgentVaultSetupBranch>

  <AgentVaultSetupBranch building="platform" runs="none,server,kubernetes,e2b,cursor">
    <Note>
    One proxy stays running and handles the requests from every agent, so you don't need a separate proxy for each task.
    </Note>
  </AgentVaultSetupBranch>

  <AgentVaultSetupBranch building="platform" runs="container,modal,daytona">
    <Note>
    Each agent run starts its own proxy beside the agent. Every proxy starts from the same proxy token, so you create the proxy in Infisical once.
    </Note>
  </AgentVaultSetupBranch>
</AgentVaultSetupStep>

<AgentVaultSetupStep step="create">
  A [session](/documentation/platform/agent-vault/sessions) gives an agent access to the services in one access bundle, until the session expires or someone [revokes it](/documentation/platform/agent-vault/sessions#revoke-a-session).

  <AgentVaultSetupBranch building="personal">
    You [create the session in the Infisical dashboard](/documentation/platform/agent-vault/sessions#create-a-session) and choose when it expires. If the agent keeps running, such as a chat assistant, set the session to never expire.
  </AgentVaultSetupBranch>

  <AgentVaultSetupBranch building="scheduled">
    Each time the job runs, the [Infisical CLI](/cli/overview) logs in as a [machine identity](/documentation/platform/identities/machine-identities) and creates a session. [Each session lasts](/documentation/platform/agent-vault/sessions-cli#choose-how-long-each-session-lasts) a little longer than the longest run you expect, because the agent loses access to the APIs if a run outlasts its session.
  </AgentVaultSetupBranch>

  <AgentVaultSetupBranch building="platform">
    For each task, the [orchestrator](/documentation/platform/agent-vault/how-it-works#orchestrators) logs in as a [machine identity](/documentation/platform/identities/machine-identities) and creates a session through the [Infisical API](/api-reference/endpoints/agent-vault-sessions/create). Each kind of task has its own access bundle, and the orchestrator chooses the access bundle when it creates the session.
  </AgentVaultSetupBranch>
</AgentVaultSetupStep>

<AgentVaultSetupStep step="token">
  The session token only works for the services in the session's access bundle, and only until the session expires or is revoked.

  <AgentVaultSetupBranch building="personal">
    The dashboard shows the token in a command that starts the agent with it. If the session never expires, revoking the session is what stops the agent from using the real credentials.
  </AgentVaultSetupBranch>

  <AgentVaultSetupBranch building="scheduled">
    The CLI keeps the token and passes it to the agent in the next step, so you never handle the token yourself.
  </AgentVaultSetupBranch>

  <AgentVaultSetupBranch building="platform">
    The orchestrator receives the token in the API response.
  </AgentVaultSetupBranch>
</AgentVaultSetupStep>

<AgentVaultSetupStep step="start">
  The agent gets the session token instead of real API keys.

  <AgentVaultSetupBranch runs="none,server,container,kubernetes,modal,daytona,ci">
    [`infisical agent-vault run`](/cli/reference#agent-vault-run) starts the agent with its requests set to go through the proxy.
  </AgentVaultSetupBranch>

  <AgentVaultSetupBranch building="platform" runs="cursor">
    Cursor's worker controller runs your spawn hook, which starts a worker pod with the session token. The worker sends the agent's commands through the proxy, while the worker itself connects to Cursor directly.
  </AgentVaultSetupBranch>

  <AgentVaultSetupBranch building="personal">
    You run the command from the dashboard on the agent's host.
  </AgentVaultSetupBranch>

  <AgentVaultSetupBranch building="scheduled">
    The CLI starts the agent right after it creates the session. The agent can read the machine identity's credentials [from its environment](/documentation/platform/agent-vault/sessions-cli#step-2-start-the-agent), and could use them to create a session for any access bundle the machine identity has. That's why the machine identity only has the access bundle that this agent uses.
    
    <Tip>
    To keep the machine identity's credentials off the agent's host, choose **A service that starts agents for tasks** instead, where the orchestrator gives the agent only the session token.
    </Tip>
  </AgentVaultSetupBranch>

  <AgentVaultSetupBranch building="platform" runs="none,server">
    The orchestrator starts the agent on a different host and passes it only the session token.
  </AgentVaultSetupBranch>

  <AgentVaultSetupBranch building="platform" runs="container">
    The orchestrator creates a new container for the task, starts the agent in it, and passes it only the session token.
  </AgentVaultSetupBranch>

  <AgentVaultSetupBranch building="platform" runs="kubernetes">
    The orchestrator creates a new pod for the task, starts the agent in it, and passes it only the session token.
  </AgentVaultSetupBranch>

  <AgentVaultSetupBranch building="platform" runs="modal,daytona">
    The orchestrator creates a new sandbox for the task, starts the agent in it, and passes it only the session token.
  </AgentVaultSetupBranch>

  <AgentVaultSetupBranch building="platform" runs="e2b">
    The orchestrator creates a new E2B sandbox for the task, gives E2B the session token as the proxy's password, and starts the agent in the sandbox. E2B holds the token on its servers, so the agent can't read it and doesn't need `infisical agent-vault run`.
  </AgentVaultSetupBranch>

  <AgentVaultSetupBranch building="platform">
    The orchestrator stays out of the agent's environment because the machine identity it uses can create sessions for every access bundle it's granted. If an agent read those credentials, it could reach every service in those access bundles.
  </AgentVaultSetupBranch>

  <AgentVaultSetupBranch building="scheduled,platform" agent="claude-code">
    Nobody is at the terminal while the agent runs, so Claude Code runs in its [non-interactive mode](https://code.claude.com/docs/en/headless): `claude -p "<prompt>"`.
  </AgentVaultSetupBranch>

  <AgentVaultSetupBranch building="scheduled,platform" agent="codex">
    Nobody is at the terminal while the agent runs, so Codex runs in its [non-interactive mode](https://developers.openai.com/codex/noninteractive): `codex exec "<prompt>"`.
  </AgentVaultSetupBranch>

  <AgentVaultSetupBranch building="scheduled,platform" agent="opencode">
    Nobody is at the terminal while the agent runs, so OpenCode runs in its [non-interactive mode](https://opencode.ai/docs/cli/#run-1): `opencode run "<prompt>"`.
  </AgentVaultSetupBranch>

  <AgentVaultSetupBranch building="scheduled,platform" agent="hermes">
    Nobody is at the terminal while the agent runs, so Hermes runs in its [non-interactive mode](https://hermes-agent.nousresearch.com/docs/user-guide/cli): `hermes chat -q "<prompt>"`.
    
    <Note> Hermes won't start without the API keys in `~/.hermes/.env`, so that file holds [placeholder values](/documentation/platform/agent-vault/guides/hermes#step-2-launch-your-agent), and the proxy attaches the real keys.</Note>
  </AgentVaultSetupBranch>

  <AgentVaultSetupBranch building="scheduled,platform" agent="openclaw">
    Nobody is at the terminal while the agent runs, so OpenClaw runs in its [non-interactive mode](https://docs.openclaw.ai/cli/agent): `openclaw agent --agent <agent-id> --message "<prompt>" --local`. OpenClaw holds a [placeholder](/documentation/platform/agent-vault/guides/openclaw#step-2-launch-your-agent) instead of your model provider's key, and the proxy attaches the real key.
  </AgentVaultSetupBranch>
</AgentVaultSetupStep>

<AgentVaultSetupStep step="request">
  The agent calls an API the same way it always does, but the request is intercepted by the proxy.

  <ul>
    <AgentVaultSetupBranch building="personal,scheduled" runs="container">
      <li>The agents' containers can't read the proxy token</li>
    </AgentVaultSetupBranch>
    <AgentVaultSetupBranch runs="ci">
      <li>The CI runner has to reach the proxy, so if the proxy is on a private network, the job runs on a [self-hosted runner](https://docs.github.com/en/actions/hosting-your-own-runners) in that network</li>
    </AgentVaultSetupBranch>
  </ul>

  <AgentVaultSetupBranch building="personal,scheduled">
    <Note>
      The proxy [runs on a different machine](/documentation/platform/agent-vault/proxies#choose-where-to-run-the-proxy) from the agent, on the same private network. If the proxy ran on the agent's machine, the agent could read the proxy token.
    </Note>
  </AgentVaultSetupBranch>

  <AgentVaultSetupBranch building="platform" runs="none,server">
    <Note>
      The proxy [runs on a different machine](/documentation/platform/agent-vault/proxies#choose-where-to-run-the-proxy) from the agent, on the same private network. If the proxy ran on the agent's machine, the agent could read the proxy token.
    </Note>
  </AgentVaultSetupBranch>

  <AgentVaultSetupBranch building="platform" runs="container,kubernetes,modal,daytona">
    <Note>
      The proxy runs outside the agent's environment, and the agent's network only reaches the proxy. The agent can't read the proxy token or connect to an API without going through the proxy.
    </Note>
  </AgentVaultSetupBranch>

  <AgentVaultSetupBranch building="platform" runs="e2b">
    <Note>
      E2B sends the sandbox's connections to the proxy from its own servers, so the proxy runs on a public machine with its SOCKS5 port turned on. Nothing in the sandbox is set up to use the proxy, and the agent can't send traffic that skips it.
    </Note>
  </AgentVaultSetupBranch>

  <AgentVaultSetupBranch building="platform" runs="cursor">
    <Note>
      The proxy runs in its own namespace, and workers can't read the proxy token. Each worker needs a direct connection to Cursor, so the agent's commands can still reach other public hosts unless you [limit where workers connect](/documentation/platform/agent-vault/guides/cursor#workers’-outgoing-connections).
    </Note>
  </AgentVaultSetupBranch>
</AgentVaultSetupStep>

<AgentVaultSetupStep step="fetch">
  The credentials go from Infisical to the proxy, never to the agent. The proxy checks Infisical for updated values every [poll interval](/documentation/platform/agent-vault/proxies#poll-interval) (60 seconds by default).
</AgentVaultSetupStep>

<AgentVaultSetupStep step="forward">
  The [real credential](/documentation/platform/agent-vault/http-apis#credential-types) is added to the request at the proxy, so it never passes through the agent. The request appears in the session's [logs](/documentation/platform/agent-vault/session-logs).

  The proxy only attaches credentials for the services in the access bundle. Requests to any other host go out without a credential, unless the proxy's [traffic policy](/documentation/platform/agent-vault/proxies#traffic-policy) blocks them.

  <AgentVaultSetupBranch building="platform" runs="cursor">
    Cursor doesn't report when a worker exits, so the session lasts until its `ttl` runs out; [keep the `ttl` as short as your runs allow](/documentation/platform/agent-vault/guides/cursor#sessions-that-outlive-their-workers).
  </AgentVaultSetupBranch>
</AgentVaultSetupStep>

<AgentVaultSetupStep step="revoke">
  <AgentVaultSetupBranch building="scheduled">
    From then on, the session token stops working. If the machine shuts down before the CLI can revoke the session, the session keeps working until its `--ttl` runs out.
  </AgentVaultSetupBranch>

  <AgentVaultSetupBranch building="platform">
    The orchestrator revokes the session through the [Infisical API](/api-reference/endpoints/agent-vault-sessions/revoke).
  </AgentVaultSetupBranch>

  <AgentVaultSetupBranch building="platform" runs="container,kubernetes,modal,daytona,e2b">
    The orchestrator also deletes the agent's environment, so nothing from one task carries over to the next.
  </AgentVaultSetupBranch>
</AgentVaultSetupStep>

</AgentVaultSetupLayout>
