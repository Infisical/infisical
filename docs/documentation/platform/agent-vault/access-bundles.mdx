---
title: "Access bundles and connections"
description: "What a connection sends and where, how bundles group connections, and who can run agents with them."
---

An access bundle is what you hand an agent: everything it needs for a job, granted and revoked as one unit. Today a bundle holds connections, each mapping an external service to the credential the proxy applies to requests bound for it, and names who may run agents with them. You grant bundles and mint sessions over them; the proxy brokers the connections inside.

## Connections

Each connection has a name, the hosts it covers, and a credential. Open a bundle from **Access Bundles** and select **Add Connection** to add one.

### Credential types

| Type             | What the proxy sends                                                                                 | When to use it                                                                              |
| ---------------- | ---------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------- |
| **Bearer**       | One header, `<header name>: <prefix> <value>`. Defaults to `Authorization: Bearer <value>`.          | Most APIs. Set the header name to `X-API-Key` and clear the prefix for APIs that take a bare key. |
| **Basic**        | `Authorization: Basic <base64 of username:password>`. Either half can be blank.                      | APIs behind HTTP basic auth, including ones that put the whole key in the username.         |
| **Pass-through** | Nothing. The request is forwarded unchanged.                                                         | To make a host reachable on a proxy that denies unmatched hosts. See [Unmatched hosts](/documentation/platform/agent-vault/proxies#unmatched-hosts). |

The first step offers a **Template** for common services, which fills in the hosts and the header. Choose **Custom** to set them yourself.

If the agent's request already carries a header with the same name, the proxy replaces it with the connection's credential.

### Host patterns

A host pattern is a comma-separated list of hosts, each with an optional port:

```text
api.github.com, uploads.github.com
*.atlassian.net
internal-api.example.com:8443
```

- A host without a port means port `443`. Credentials are attached to HTTPS traffic only.
- `*.` at the start matches exactly one label. `*.example.com` covers `api.example.com`, not `a.b.example.com` or `example.com`.
- Paths aren't allowed. A connection covers a host, not a route on it.

Keep patterns as narrow as the API allows. A wildcard covers every host under it, and the credential goes to all of them. Some templates carry a placeholder such as `<your-tenant>.atlassian.net` for this reason; replace it with your own tenant before saving.

### When two connections cover one host

Within one bundle, two connections can't cover the same host with the same pattern. Infisical rejects the save and names the connection that already covers it. An exact host and a wildcard that includes it can both exist, and the exact one wins: if one connection covers `api.example.com` and another `*.example.com`, requests to `api.example.com` get the first connection's credential.

Different bundles can cover the same host with different credentials. An agent gets the credential from the bundle its session carries.

## Access bundles

A bundle has a name, an optional description, its connections, and its members. Granting a bundle to a user, machine identity, or group lets them mint sessions over it. The grantee has to be a member of Agent Vault first: Agent Vault is organization-wide, and its **Access Control** page decides who is an admin, who is a member, and which machine identities and groups belong. A group that's in Agent Vault is granted as a group, and each of its members mints sessions as themselves.

Bundles are how you scope access. An agent for on-call work gets a bundle with the incident tooling, an agent for code review gets a bundle with GitHub, and neither reaches the other's hosts.

Removing a member from a bundle, or from Agent Vault, takes effect on their running agents within one poll interval of the proxy. Deleting a bundle removes its connections from every session that carries it. See [Sessions](/documentation/platform/agent-vault/sessions#what-a-running-agent-can-reach).
