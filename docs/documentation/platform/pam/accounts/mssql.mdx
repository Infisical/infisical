A Microsoft SQL Server [account](/documentation/platform/pam/accounts/overview) stores the credentials for one SQL Server login or Windows user. Members connect to the database in the browser or through the Infisical CLI, and Infisical records every query they run.

## Prerequisites

- The Admin [role](/documentation/platform/pam/concepts/access-control) on the [folder](/documentation/platform/pam/folders/overview) you'll add the account to
- A [gateway](/documentation/platform/gateways/overview) that can reach the database
- A Microsoft SQL Server [account template](/documentation/platform/pam/templates/overview)

## Create the account

<Steps>
  <Step>
    Go to **Privileged Access Management** > **Accounts** and select **Add Account**.
  </Step>
  <Step>
    Select the **Folder** and a Microsoft SQL Server **Account Template**, then select **Next**.
  </Step>
  <Step>
    Enter a **Name** and the connection details:

    | Field | Description |
    | --- | --- |
    | **Host** | The server's hostname or IP address |
    | **Port** | The server's port (defaults to `1433`) |
    | **Database** | The database that sessions connect to (defaults to `master`) |
    | **SSL Enabled** | Whether to connect over TLS |
    | **Reject Unauthorized** | Whether to reject a server certificate that can't be verified (shown when **SSL Enabled** is on) |
    | **SSL Certificate** | The CA certificate that signed the server's certificate (shown when **SSL Enabled** is on) |
  </Step>
  <Step>
    Select the **Auth Method** and enter the credentials:

    <Tabs>
      <Tab title="SQL Server Authentication">
        | Field | Description |
        | --- | --- |
        | **Username** | The SQL Server login |
        | **Password** | The login's password |
      </Tab>
      <Tab title="Windows Authentication (NTLM)">
        | Field | Description |
        | --- | --- |
        | **Username** | The Windows user |
        | **Password** | The user's password |
        | **Domain** | The user's Windows domain |
      </Tab>
      <Tab title="Windows Authentication (Kerberos)">
        | Field | Description |
        | --- | --- |
        | **Username** | The Windows user |
        | **Password** | The user's password |
        | **Realm** | The Kerberos realm, such as `CORP.EXAMPLE.COM` |
        | **KDC Address** | The address of the key distribution center (optional) |
        | **SPN** | The service principal name of the SQL Server instance, such as `MSSQLSvc/sql01.corp.example.com:1433` |
      </Tab>
    </Tabs>
  </Step>
  <Step>
    Select **Create**.
  </Step>
</Steps>

## Connect

To open a session, follow [Connect to an account](/documentation/platform/pam/accounts/connect).

<Tabs>
  <Tab title="Browser">
    The browser session has a table browser, where you can view, filter, edit, and export rows, and a SQL editor for running queries. In the SQL editor, you can separate batches with `GO` lines, as you would in SQL Server Management Studio.

    The SQL editor shows one result set per script: the last one, or a stored procedure's first one. It lists `PRINT` output, other server messages, and errors under the results. Limits:

    - A script can run for up to 30 seconds
    - If a query returns more than 1,000 rows or 16 MB of data, the SQL editor shows the rows up to that limit and cancels the script. By then SQL Server may already have run the statements after that query in the same batch. Later `GO` batches don't run.
    - If a `GO` batch fails, the batches after it don't run, and the error says which batches completed

    SQL Server keeps running a batch after most statement errors, such as a duplicate key, so a later `COMMIT` in the batch commits the statements that succeeded. Add `SET XACT_ABORT ON` at the start of a script to roll back the whole transaction on any error instead.

    If a statement fails or you cancel a script, an open transaction stays open. Commit it or roll it back before you close the tab.
  </Tab>
  <Tab title="CLI">
    Start the local proxy:

    ```bash
    infisical pam access analytics/reporting-db
    ```

    The proxy keeps running in that terminal and prints its port. In a second terminal, connect your SQL Server client, such as `sqlcmd` or Azure Data Studio, to that port:

    ```bash
    sqlcmd -S localhost,<port> -d analytics
    ```

    The proxy signs in for you, so the client doesn't need a password.
  </Tab>
</Tabs>
