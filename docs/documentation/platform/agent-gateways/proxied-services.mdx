A proxied service tells an [Agent Gateway](/documentation/platform/agent-gateways/overview) how to apply
credentials to traffic bound for an external service. It names the hosts it covers and the secrets to apply, and
one service can be brokered by several Agent Gateways.

Create one under **Secrets Management → Agentic → Proxied Services**. The editor walks through details, header
rewrites, secret substitution, and a review step, and starts from a template for around 35 common APIs.

A service applies each secret through a [header rewrite](#header-rewrites), a
[secret substitution](#secret-substitution), or both.

<Note>
  A proxied service on its own brokers nothing. It has to be
  [connected](/documentation/platform/agent-gateways/configuration#connected-services) to an Agent Gateway
  before any traffic reaches it.
</Note>

## Configuration

Every service has these core fields, plus one or more credential rules.

<ParamField path="Service Name" type="string" required>
  A slug (lowercase letters, numbers, hyphens) that identifies the service, such as `github`. Names are unique
  within a project.
</ParamField>

<ParamField path="Host Pattern" type="string" required>
  One or more comma-separated patterns describing which hosts this service applies to. See
  [Host patterns](#host-patterns).
</ParamField>

<ParamField path="Enabled" type="boolean" optional default="true">
  Toggle a service off without deleting it. A disabled service is skipped entirely: its placeholder environment
  variables are not set, no credentials are applied, and traffic to its hosts falls back to the
  [unmatched host policy](/cli/commands/agent-gateway#unmatched-hosts).
</ParamField>

![The Details step of the proxied service editor with the name and host pattern](/images/platform/agent-gateways/service-details.png)

Each credential additionally names **where its secret lives**: an environment and a secret path, chosen per
credential. One service can therefore combine a token from `prod:/payments` with a tenant id from
`dev:/shared`, with no secret imports or references in between. The editor defaults every credential to the
environment and path you opened it with, so the common case is still one choice.

## Host patterns

A host pattern routes requests to the right service. Each pattern is a `host[:port][/path]`, and multiple
patterns can be combined with commas:

```bash
api.github.com                            # exact host
*.github.com                              # wildcard: matches api.github.com, not a.b.github.com
api.github.com:443                        # specific port
api.github.com/repos/*                    # path prefix
internal.corp.com:3000/api/*              # port and path
api.github.com, uploads.github.com        # multiple patterns, matches either
```

A few rules to keep in mind:

- A `*.` wildcard matches exactly **one** label: `*.github.com` matches `api.github.com` but not
  `a.b.github.com` or bare `github.com`.
- Host matching is case-insensitive. A pattern without a port matches any port.
- Do not include a scheme (`https://`); patterns are hosts, not URLs.

When a request could match more than one of an Agent Gateway's connected services, the best match wins:

1. Exact host beats wildcard host.
2. A pattern with a specific port beats one that matches any port.
3. The longest matching path prefix wins.
4. If still tied, the service listed higher on the Agent Gateway wins.

<Warning>
  Host patterns are the allowlist that decides where a credential may be sent. A pattern broader than the API
  needs is what turns a brokered credential into one an agent can aim somewhere else, so keep them narrow.
</Warning>

## Header rewrites

A header rewrite adds or replaces an HTTP header on the outbound request. The agent does not need to send any
credential; if it sends a made-up one, the header is overwritten with the real value. This covers most APIs:

| Auth style | Configuration | Resulting header |
| --- | --- | --- |
| Bearer token | Header name `Authorization`, prefix `Bearer`, one secret | `Authorization: Bearer <secret>` |
| API key header | Header name `x-api-key`, no prefix, one secret | `x-api-key: <secret>` |
| Basic auth | One secret as **Username**, and optionally a second as **Password** | `Authorization: Basic base64(username:password)` |
| Custom | Any header name and optional prefix | `<name>: <prefix> <secret>` |

The password is optional for basic auth. Many APIs pass an API key as the username with an empty password;
omitting the password produces `Authorization: Basic base64(username:)`.

![A header rewrite setting x-api-key to a secret](/images/platform/agent-gateways/header-rewrites.png)

A service can rewrite several distinct headers, for example an API key header plus a tenant header, but each
header name can only be set by one credential. To build one header value out of several secrets, point the
credential at a secret whose value is a [secret reference](/documentation/platform/secret-reference) expression.

## Secret substitution

With secret substitution, the agent is handed a dummy placeholder value, and the broker swaps it for the real
credential wherever it appears in the request. It is useful in two situations:

- The API carries the credential somewhere other than a header. Telegram, for example, puts the bot token in the
  URL path: `api.telegram.org/bot<token>/sendMessage`.
- The agent has to see a value before it will make the call at all, headers included. Some HTTP clients
  validate that a credential is set, and agents often refuse to attempt a request without a real-looking key.
  The placeholder satisfies them, and the broker swaps in the real value on the way out.

The placeholder is delivered for you: both `run` and `connect` set it as an environment variable in the agent's
environment, so there is nothing to hand out.

![A secret substitution rule swapping a placeholder for the real secret](/images/platform/agent-gateways/secret-substitution.png)

<ParamField path="Environment Variable" type="string" required>
  The environment variable name the agent receives, such as `TELEGRAM_BOT_TOKEN`. The CLI sets it to the
  placeholder, so the agent uses it like a normal credential.
</ParamField>

<ParamField path="Placeholder Value" type="string" required>
  The dummy value the agent sends in its requests. A distinctive random string is generated for you, but you can
  override it, for example when the agent's HTTP client validates the credential's format.
</ParamField>

<ParamField path="Replace In" type="string[]" required>
  The request surfaces scanned for the placeholder: `path`, `query`, `header`, and `body`. Scoping is the
  boundary: substitution only happens in the surfaces you list.
</ParamField>

<ParamField path="Secret" type="string" required>
  The secret whose real value replaces the placeholder, along with the environment and path it lives in.
</ParamField>

## Using dynamic secrets

A credential can reference a [dynamic secret](/documentation/platform/dynamic-secrets/overview) instead of a
static secret. Rather than applying a fixed value, the broker holds a short-lived lease and applies one of its
output fields, for example a GCP access token, a GitHub App token, or a Kubernetes service-account token.

The lease belongs to the agent's [session](/documentation/platform/agent-gateways/sessions): one lease per
credential, minted when the session opens, reused for every request in the run, and revoked when it ends.

<Warning>
  Use a TTL of at least a few minutes on a dynamic secret you broker, so its lease outlives the agent's startup.
</Warning>

## Who has to be able to read the secret

Saving a proxied service checks two things: that you may create or modify proxied services, and that you can
actually read every secret you attach. A reference you cannot read is rejected there and then, with the secret
named, rather than failing later as a request the broker could not credential.

That check is deliberately the **only** place secret access is examined. Connecting a service to an Agent
Gateway does not re-ask it, because connecting is a wiring decision about which broker may serve an
already-validated service. What matters at request time is whose permissions resolve the value, and that is the
person who last saved the service. See
[Who can read what](/documentation/platform/agent-gateways/overview#who-can-read-what).

<Note>
  Re-saving a service re-stamps you as its configurer, and re-validates every credential it holds, including the
  ones you did not touch. If the person who set it up has left, re-save it to re-authorize its credentials; the
  broker's error message tells you exactly this.
</Note>

## Example: API request

Proxied services can also be managed via the
[API](/api-reference/endpoints/proxied-services/create). Creating the Telegram service described above:

```bash
curl -X POST https://app.infisical.com/api/v1/proxied-services \
  -H "Authorization: Bearer <your-access-token>" \
  -H "Content-Type: application/json" \
  -d '{
    "projectId": "<project-id>",
    "name": "telegram-bot-api",
    "hostPattern": "api.telegram.org",
    "credentials": [
      {
        "environment": "dev",
        "secretPath": "/coding-agent",
        "secretKey": "TELEGRAM_BOT_TOKEN",
        "role": "credential-substitution",
        "placeholderKey": "TELEGRAM_BOT_TOKEN",
        "placeholderValue": "placeholder_tg_bot",
        "substitutionSurfaces": ["path"]
      }
    ]
  }'
```

Header-rewrite credentials use `"role": "header-rewrite"` with `headerName` and an optional `headerPrefix`, or
`headerPurpose` (`username` / `password`) for basic auth.

To reference a dynamic secret, replace `secretKey` with `dynamicSecretName` and `dynamicSecretField`:

```json
{
  "environment": "dev",
  "secretPath": "/coding-agent",
  "dynamicSecretName": "github-app-token",
  "dynamicSecretField": "TOKEN",
  "role": "header-rewrite",
  "headerName": "Authorization",
  "headerPrefix": "Bearer"
}
```
