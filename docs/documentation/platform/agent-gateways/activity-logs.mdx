Activity logs are the broker's per-request trail: which agent called which host, and which credential was
applied. They are how you answer "why was this request not brokered", and they complement
[audit logs](/documentation/platform/audit-logs), which record the resolutions and configuration changes on the
Infisical side.

Both modes produce the same records. Only where they are written differs, so
[Where the records go](#where-the-records-go) has a section for each.

<Note>
  Only requests that reach the forwarding stage are logged. Requests rejected earlier, such as an invalid
  `CONNECT` target or a TLS failure, never reach it. A request the broker could not resolve credentials for is
  still logged, as an `error`.
</Note>

## What's in a record

Each request is logged with these fields, plus the standard `time`, `level`, and `message`:

| Field | Meaning |
| --- | --- |
| `event` | Always `agent-gateway.request`, so activity is easy to filter from other logs |
| `decision` | `brokered`, `passthrough`, `blocked`, `canceled`, or `error` |
| `agentGateway` | The Agent Gateway whose services were brokered |
| `sessionId` | The [session](/documentation/platform/agent-gateways/sessions) the request belonged to, which is what ties a record to an audit-log resolution |
| `actorName` | Who the session was opened by: an email, or a machine identity's name |
| `serviceName` / `serviceId` | The matched proxied service, omitted when none matched |
| `method` / `host` / `port` / `path` | The request line, before substitution, so `path` shows the placeholder |
| `status` | Upstream status on `brokered` and `passthrough`; `403` on `blocked`; `502` on `error`; omitted on `canceled`, where no response was returned |
| `credentials` | What was applied: each entry's secret key (or a dynamic secret's name and output field), and the header or surfaces it landed in |

Written out, two records look like this:

```text
2026-08-12T14:32:09 INF agent request  event=agent-gateway.request decision=brokered agentGateway=prod-agents actorName=dev@acme.com serviceName=github method=POST host=api.github.com path=/repos/acme/app/issues status=201 credentials=[{"key":"GITHUB_PAT","role":"header-rewrite","header":"Authorization"}]
2026-08-12T14:32:12 WRN agent request  event=agent-gateway.request decision=blocked agentGateway=prod-agents actorName=dev@acme.com host=evil.example.com method=GET status=403
```

<Warning>
  A record never contains a real secret. Requests are logged as the agent sent them, before the swap, so `path`
  shows only the placeholder; `credentials` lists secret **names**, not values; header values and request bodies
  are never logged.
</Warning>

## Log levels

Each decision is logged at a level, so `--log-level` doubles as the activity filter. The default `info` hides
passthrough and canceled requests, `debug` shows everything, and `warn` shows only blocked requests and errors.

| decision | level |
| --- | --- |
| `passthrough` | debug |
| `canceled` | debug |
| `brokered` | info |
| `blocked` | warn |
| `error` | error |

`canceled` means the agent hung up before the request finished, which happens when you interrupt a prompt or the
agent exits mid-request. Nothing failed and there was nobody left to answer, so these stay at debug and off your
terminal. A request that really failed, an unreachable upstream or credentials that could not be resolved, is
still an `error`.

## Where the records go

<Tabs>
  <Tab title="Local mode">
    Nothing is written unless you pass `--log-file`, since the agent owns your terminal and a file you did not
    ask for is one you cannot find:

    ```bash
    infisical secrets agent gateway run --name prod-agents --log-file=/tmp/broker.log -- claude

    # in another terminal
    tail -f /tmp/broker.log
    ```

    Without the flag you still see problems: warnings and errors print to your terminal, including a credential
    the broker had to skip. What you lose is the per-request trail.

    The file is appended to on every run and never rotated for you, so use `logrotate` with `copytruncate` if
    you keep one around.
  </Tab>
  <Tab title="Remote mode">
    Records are written by the [Gateway](/documentation/platform/gateways/overview) hosting the broker, to its
    **stderr**, so whatever supervises the Gateway collects them. Nothing is written on the agent's machine,
    because nothing is brokered there.

    Forward that output with a collector such as Fluent Bit or the OpenTelemetry Collector to your logging
    platform. In a container, let the platform rotate the stream.

    <Note>
      This is the one operational cost of remote mode: the decision trail lives on the Gateway host, which is
      not necessarily the machine of the person asking why their agent's request was not brokered. When
      debugging a single request, `run` against the same Agent Gateway reproduces the matching locally.
    </Note>
  </Tab>
</Tabs>
