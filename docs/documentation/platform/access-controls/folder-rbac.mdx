Folder-level access controls assign a role to a user or machine identity on a single [folder](/documentation/platform/folder). Inside that folder, the grant replaces whatever their project roles would otherwise allow, so it can widen access or narrow it. On the root folder of an environment, you can also apply the role to every folder below it.

<Info>
  Folder-level access controls are a paid feature.

If you're using Infisical Cloud, then they're available under the **Pro plan**.
If you're self-hosting Infisical, contact sales@infisical.com to purchase a license.

</Info>

## How folder access works

When you give a single user or machine identity a role on a folder, that role takes precedence over their [project role](./role-based-access-controls). You can use folder access to:

- Give someone access to a single folder their project role doesn't reach
- Hold someone to a lower role inside a sensitive folder
- Give someone one role across a whole environment
- Hand out short-lived access for an incident or a one-off task

A folder role only applies to the exact folder you set it on, unless you set it on the root folder `/` and [apply it to subfolders](#applying-access-to-subfolders).

## Folder access roles

There are five different folder access roles, listed here from least to most privileged. Each role includes everything the roles before it allow.

| Role            | What it allows                                                                                                                                                        |
| --------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **List**        | See secret names and metadata without their values. Read secret imports, tags, and the configuration of secret syncs, secret rotations, and honey tokens.             |
| **Read**        | Everything in List, plus reading secret values, viewing commit history, generating dynamic secret leases, and subscribing to secret events.                           |
| **Edit**        | Everything in Read, plus creating, editing, and deleting secrets and secret imports.                                                                                  |
| **Manage**      | Everything in Edit, plus managing secret rotations, dynamic secret root credentials, honey tokens, and secret syncs, including reading the credentials they generate. |
| **Full Access** | Everything in Manage, plus deleting subfolders of this folder and granting or revoking access to it. This role doesn't grant access to delete the folder itself, because deleting a folder is authorized on its parent.                                     |

If you [apply a role to subfolders](#applying-access-to-subfolders), Edit, Manage, and Full Access also let someone create and edit folders anywhere in the environment. With Full Access, they can also delete any folder in the environment.

<Warning>
  If you move or rename a folder, it keeps the same role. Deleting the folder removes the role permanently.
</Warning>

## Granting folder access

<Steps>
  <Step>
    Navigate to your project's **Secrets** page and select an environment. You can set access on the folder you're currently viewing, or on any folder in the list. To set access on the current folder, select **Manage Access** at the right end of the folder path, above the secrets table.

    ![Open folder access from the environment view](/images/platform/access-controls/folder-rbac/open-folder-access-from-environment.png)

    To set access on a folder in the list, hover over its row and select the members icon that appears.

    ![Open folder access from a folder row](/images/platform/access-controls/folder-rbac/open-folder-access-from-folder-row.png)

  </Step>
  <Step>
    Review the **Manage Permissions** sheet. The list shows users and machine identities with folder grants or access through their project roles. To override project access in this folder, open the role menu with the **Project** badge and choose a folder role.

    ![Manage Permissions sheet](/images/platform/access-controls/folder-rbac/manage-permissions-sheet.png)

    To change an existing grant, open the row's role menu, then open the current role's submenu and choose a new role. Project admins have full access on all folders and can't receive a folder grant.

    ![Folder role dropdown](/images/platform/access-controls/folder-rbac/folder-role-dropdown.png)

  </Step>
  <Step>
    Search for a user or machine identity, or expand **No Access**. Select **Grant Access** beside the member, then choose a role. Changes save automatically.

    ![Grant folder access from search results](/images/platform/access-controls/folder-rbac/grant-folder-access.png)

    If you can add project members, the **In Organization, Not in Project** subsection also lists organization members outside the project. Granting access from this subsection adds the member to the project with the **No Access** project role before granting folder access.

  </Step>
  <Step>
    Confirm that the member appears in the access list with the role you chose. If the grant replaces access from a project role, the row shows an **Override** badge.

  </Step>
</Steps>

## Applying access to subfolders

A folder role on the root folder (`/`) of an environment can also apply to every folder below it, including folders created later. Use this to give someone one role across a whole environment, or to hold them to a lower role everywhere in it. You can't apply a role on any other folder to its subfolders.

To apply a role to subfolders, or to change or remove a role that applies to them, you need a role that can manage access on `/` and every folder below it, such as the Admin project role or Full Access on `/` applied to subfolders. Full Access on `/` alone isn't enough, because it covers only `/`.

<Steps>
  <Step>
    On your project's **Secrets** page, select an environment. On the environment's root folder (`/`), select **Manage Access** at the right end of the folder path.
  </Step>
  <Step>
    Find the member in the list, then:

    - If the member has no folder role, select **Grant Access**, select **Apply to Subfolders**, then choose a role
    - If the member already has a folder role on `/`, open their role menu and select **Apply to Subfolders** (the change saves right away)

    If the row only shows a **Project** badge, choose a folder role from its role menu first, then open the menu again and select **Apply to Subfolders**.

  </Step>
  <Step>
    Confirm that the member's row shows a **Recursive** badge.
  </Step>
</Steps>

To stop applying the role to subfolders, select **Apply to Subfolders** in the row's role menu again. The role stays on `/`. You can also apply a role to subfolders from a member's detail page, as [Reviewing folder access](#reviewing-folder-access) describes.

### Combining with a role on a nested folder

If someone also has a role on a nested folder, that role applies inside that folder only, and it can be higher or lower than the role from `/`. The folders below the nested folder use the role from `/` again. For example, if someone has Read on `/` applied to subfolders and Edit on `/payments`:

- In `/payments`, they can edit secrets
- In `/` and `/payments/keys`, they can only read secrets

### Seeing inherited access in a subfolder

In a subfolder's **Manage Permissions** sheet, the member's row shows the role from `/` with a `/` badge. You can't change or remove that role from the subfolder. Instead, open the row's role menu and:

- Select **Manage on /** to open the root folder's sheet, where you can change or remove the role
- Choose a role under **Add a Role on This Folder** to set a different role on this folder only

## Setting temporary access

To set an expiration, open an existing folder grant's role menu and select **Add Temporary Access** or **Edit Temporary Access**. Enter a duration, such as `4h`, then select **Apply**.

![Set a duration in the Temporary Access dialog](/images/platform/access-controls/folder-rbac/temporary-access-dialog.png)

The row shows the time remaining. Once the grant expires, the user or machine identity falls back to their project roles, or to their role on `/` if that role applies to subfolders.

<Note>
  Full Access can't be temporary. A Full Access holder can grant folder
  access to other people, and those accesses would outlive their own expiration.
  Grant Full Access permanently, or use Manage for time-bound access.
</Note>

## Reviewing folder access

To see every folder a user or machine identity has been granted access to, go to your project's **Access Control** page and open the user or machine identity. The **Folder Access** section lists each grant with its folder, environment, role, and duration, and lets you change or revoke it.

If a grant applies to subfolders, its row shows a **Recursive** badge. To apply a grant on `/` to subfolders, or to stop applying it, turn **Apply to subfolders** on or off in the **Grant Folder Access** or **Edit Folder Access** sheet.

![Folder access on a user's detail page](/images/platform/access-controls/folder-rbac/user-folder-access-details.png)
