## Overview

Infisical's project permissions system follows a role-based access control (RBAC) model built on a subject-action-object framework. At the project level, these permissions determine what actions users/machines can perform on various resources within a specific project.

Each permission consists of:

- **Subject**: The resource the permission applies to (e.g., secrets, members, settings)
- **Action**: The operation that can be performed (e.g., read, create, edit, delete)

Some project-level resources support conditional permissions and permission inversion for more granular access control: `secrets`, `secret-folders`, `secret-imports`, `dynamic-secrets`, `secret-syncs`, `secret-rotation`, `honey-tokens`, `identity`, `app-connections`, `pam-accounts`, `agent-vault-access-bundles`, `agent-vault-services`, and `agent-vault-skills`. Conditions allow you to specify criteria (like environment, secret path, tags, app connection ID, identity ID, resource name, endpoint name, or the ID of an Agent Vault access bundle, service, or skill) that must be met for the permission to apply.

### Agent Vault

A [role](/documentation/platform/agent-vault/access-control#roles) in an Agent Vault project uses the following subjects and some [shared subjects](#shared-subjects-in-agent-vault-projects). On a role's page, the **JSON** tab shows the role's rules in this format.

In rules for access bundles, services, and skills:

- `use` also lets a member view the access bundle, service, or skill, so a rule with `use` doesn't need `read`
- A condition's value is one ID, `$eq` with one ID, or `$in` with a list of IDs (Infisical refuses any other operator, such as `$glob`)
- `create` can't take a condition, so put `create` in a rule of its own

#### Subject: `agent-vault-sessions`

Supports conditions and permission inversion. Without a condition, `read`, `edit`, and `revoke` cover every session in the project. To limit one of them, add the condition key `actorId`, which is the user or machine identity that created the session (a session created [on behalf of a user](/documentation/platform/agent-vault/sessions-on-behalf-of-users) counts as the machine identity's). `actorId` only takes `{{identity.id}}`, which Infisical replaces with the ID of the member who makes the request:

- `{ "$eq": "{{identity.id}}" }` covers only the sessions the member created
- `{ "$ne": "{{identity.id}}" }` covers only the sessions that other users and machine identities created

A rule with `actorId` can only hold `read`, `edit`, and `revoke`, so put the other session actions in a rule of their own.

| `edit`                        | Change the [label and metadata](/documentation/platform/agent-vault/sessions#label-a-session-and-add-metadata) of sessions                                                           | `actorId`      |
| `revoke`                      | Revoke sessions                                                                                                                                                                      | `actorId`      |
| `create-with-inline-services` | Create sessions with [inline services](/documentation/platform/agent-vault/inline-services), which bring their own hosts and credentials (also needs `create`)                       |                |
| `create-with-inline-skills`   | Create sessions with [skills sent along with the session](/documentation/platform/agent-vault/skills#send-skills-with-a-session) (also needs `create`)                               |                |

## Condition operators

When defining conditions for permissions, you can use the following operators to match values:

| Operator | Description | Type |
|----------|-------------|------|
| `$eq` | Equals (exact string match) | `string` |
| `$ne` | Not equals | `string` |
| `$in` | In array (matches any value in list) | `string[]` |
| `$glob` | [Glob pattern](https://www.malikbrowne.com/blog/a-beginners-guide-glob-patterns/) matching (supports `*`, `**`, `?`, and `{a,b}` wildcards) | `string` |
| `$elemMatch` | Element match for nested objects/arrays | `object` |

<Note>
When using `$glob`, note that `*` doesn't match across `/` boundaries. Use `**` to match across multiple path segments.

A trailing `/*` also doesn't match the folder itself: `/app/*` matches secrets in `/app/config` but not secrets directly in `/app`. To grant access to a folder and everything under it, use a trailing `/**`.

| Pattern | Matches | Doesn't match |
|---------|---------|----------------|
| `/app/*` | `/app/config`, `/app/secrets` | `/app` (the folder itself), `/app/config/db` |
| `/app/**` | `/app`, `/app/config`, `/app/config/db/primary` | `/other/config` |
| `/{dev,staging}/*` | `/dev/secrets`, `/staging/config` | `/prod/secrets` |
</Note>

## Condition keys reference

The following condition keys can be used to restrict permissions. Each key is available only for specific subjects as indicated in the tables above.

| Condition key | Description | Type |
|---------------|-------------|------|
| `environment` | The environment slug (e.g., dev, staging, prod) | `string` |
| `secretPath` | The path within an environment (e.g., /app/config) | `string` |
| `secretName` | The name of a specific secret | `string` |
| `secretTags` | Tags associated with secrets | `string[]` |
| `metadata` | Key-value metadata pairs (use with `$elemMatch`) | `object` |
| `connectionId` | Connection identifier for rotations/syncs | `string` |
| `identityId` | Machine identity identifier | `string` |
| `name` | Resource name | `string` |
| `resourceName` | PAM resource name | `string` |
| `accountName` | PAM account name | `string` |
| `resourceType` | PAM resource type (e.g., `postgres`, `mysql`, `rdp`, `ssh`, `windows`, `active-directory`, `redis`, `mssql`, `kubernetes`, `aws-iam`) | `string` |
| `accessBundleId` | The ID of an Agent Vault access bundle | `string` |
| `serviceId` | The ID of an Agent Vault service | `string` |
| `skillId` | The ID of an Agent Vault skill | `string` |
| `userEmail` | User email - The email address of the user whose roles are being updated | `string` |
| `groupName` | Group name - The name of the group whose roles are being updated | `string` |
| `assignableRole` | Assignable roles - The roles that can be assigned to other members | `string` |
| `assignableSubject` | Assignable subjects - The permission subjects that can be granted in additional privileges | `string` |

## Usage examples

These permission objects are used when creating or updating [custom project roles](/api-reference/endpoints/project-roles/create) via the API. Each permission in the `permissions` array defines what actions a role can perform on which resources.

### Creating a role with production-only secret access

Create a custom role that can only read secrets in the production environment:

```bash
curl --request POST \
  --url https://app.infisical.com/api/v1/projects/{projectId}/roles \
  --header 'Authorization: Bearer <token>' \
  --header 'Content-Type: application/json' \
  --data '{
    "slug": "production-reader",
    "name": "Production Reader",
    "permissions": [
      {
        "subject": "secrets",
        "action": ["describeSecret", "readValue"],
        "conditions": {
          "environment": { "$eq": "production" }
        }
      }
    ]
  }'
```

### Creating a role with path-scoped access

Create a role that can only manage secrets under `/app/config/`:

```bash
curl --request POST \
  --url https://app.infisical.com/api/v1/projects/{projectId}/roles \
  --header 'Authorization: Bearer <token>' \
  --header 'Content-Type: application/json' \
  --data '{
    "slug": "config-manager",
    "name": "Config Manager",
    "permissions": [
      {
        "subject": "secrets",
        "action": ["describeSecret", "readValue", "edit"],
        "conditions": {
          "secretPath": { "$glob": "/app/config/**" }
        }
      }
    ]
  }'
```

### Creating a role for PAM access to specific resources

Create a role that grants PAM access only to specific database resources:

```bash
curl --request POST \
  --url https://app.infisical.com/api/v1/projects/{projectId}/roles \
  --header 'Authorization: Bearer <token>' \
  --header 'Content-Type: application/json' \
  --data '{
    "slug": "db-readonly-access",
    "name": "Database Read-Only Access",
    "permissions": [
      {
        "subject": "pam-accounts",
        "action": ["read", "access"],
        "conditions": {
          "resourceName": { "$in": ["prod-db-1", "prod-db-2"] },
          "accountName": { "$glob": "readonly-*" }
        }
      }
    ]
  }'
```

### Creating a role for Agent Vault sessions with one access bundle

Create a role in an Agent Vault project whose members can create sessions with one access bundle, and view, change, and revoke the sessions they created:

```bash
curl --request POST \
  --url https://app.infisical.com/api/v1/projects/<project-id>/roles \
  --header 'Authorization: Bearer <token>' \
  --header 'Content-Type: application/json' \
  --data '{
    "slug": "release-engineer",
    "name": "Release Engineer",
    "permissions": [
      {
        "subject": "agent-vault-access-bundles",
        "action": ["use"],
        "conditions": {
          "accessBundleId": { "$eq": "<access-bundle-id>" }
        }
      },
      {
        "subject": "agent-vault-sessions",
        "action": ["create"]
      },
      {
        "subject": "agent-vault-sessions",
        "action": ["read", "edit", "revoke"],
        "conditions": {
          "actorId": { "$eq": "{{identity.id}}" }
        }
      }
    ]
  }'
```

## Auditing a user's effective permissions

A member can hold a direct role, a group-inherited role, and additional privileges at the same time, so what they can actually do isn't always obvious. The **Permission Audit** view resolves every source into one effective answer per subject and action.

Open **Access Control**, select the **Users** tab, select the member, then select **Permission Audit** in the page header.

<Frame caption="Permission Audit for a project member, grouped by resource.">
  <img src="/images/internals/permissions/permission-audit-sheet.png" alt="Permission Audit sheet showing effective access per resource" />
</Frame>

Each action reads as **Allow**, **Conditional**, or **Forbid**. Hover over a conditional action to see the conditions that have to match. A red icon means an explicit forbid, and a muted dash means nothing grants the action at all. The **Granted by** column names every source that contributes: the direct role, the group-inherited role, or the additional privilege.

Use the search box to filter by resource, action, or source, and the **All** dropdown to show only allowed, conditional, or forbidden actions. Select the **Export CSV** icon next to the search box to download the full list.
