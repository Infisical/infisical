---
title: "Migrate to .infisical.yaml"
description: "The Infisical CLI now reads project settings from `.infisical.yaml` instead of `.infisical.json`, and creates `.infisical.yaml` from an existing `.infisical.json`."
---

## What changed

The CLI is moving away from `.infisical.json`. It now reads [project settings](/cli/project-config) from `.infisical.yaml`. The CLI still reads `.infisical.json` for now, but a future release will stop reading it.

Starting with version 0.44.3, if you run a command in a directory that has `.infisical.json`, the CLI creates `.infisical.yaml` in the same directory with the same settings. The CLI leaves `.infisical.json` in place for you to delete.

## Who is affected

You're affected if you use an `.infisical.json` file anywhere, including:

- Repositories with a committed `.infisical.json`
- Container images that copy `.infisical.json` into the image

## Prerequisites

- Infisical CLI 0.43.145 or later on every machine that reads the file, including developer machines, CI pipelines, and container images ([upgrade the CLI](/cli/upgrade))

Older versions of the CLI don't read `.infisical.yaml`, so after you delete `.infisical.json`, those versions can't find the project linked to the directory.

## Migration steps

Let the CLI create `.infisical.yaml` from `.infisical.json`, or create `.infisical.yaml` by hand.

<Tabs>
  <Tab title="Let the CLI create the file">
    <Note>
      The CLI creates `.infisical.yaml` for you in version 0.44.3 and later. If your CLI is older, [upgrade it](/cli/upgrade) or create `.infisical.yaml` by hand.
    </Note>

    <Steps>
      <Step>
        In the directory that holds `.infisical.json`, run any `infisical` command, such as:

        ```bash
        infisical sm secrets
        ```

        The CLI creates `.infisical.yaml` and prints the path of the new file, followed by a warning that both files exist:

        ```
        Created /home/user/my-app/.infisical.yaml from the legacy /home/user/my-app/.infisical.json (commit it if this project is under version control).
        Warning: Both .infisical.yaml and .infisical.json exist in /home/user/my-app. .infisical.yaml takes precedence, so the legacy /home/user/my-app/.infisical.json is no longer used and you can remove it.
        ```
      </Step>
      <Step>
        Delete `.infisical.json`, then commit the new file and the deletion:

        ```bash
        rm .infisical.json
        git add .infisical.yaml .infisical.json
        git commit -m "Migrate Infisical CLI config to .infisical.yaml"
        ```
      </Step>
    </Steps>

    If your repository has more than one `.infisical.json`, such as one per package in a monorepo, run a command in each directory that holds one.

  </Tab>
  <Tab title="Edit the file by hand">
    <Steps>
      <Step>
        In the directory that holds `.infisical.json`, create a file named `.infisical.yaml`. The CLI doesn't read a file named `.infisical.yml`.
      </Step>
      <Step>
        Copy each field from `.infisical.json` to its key in `.infisical.yaml`:

        | `.infisical.json` field | `.infisical.yaml` key |
        | --- | --- |
        | `workspaceId` | `secrets-management.project-id` |
        | `defaultEnvironment` | `secrets-management.default-environment` |
        | `gitBranchToEnvironmentMapping` | `secrets-management.mappings.git-branch-to-environment` |
        | `defaultSecretPath` | `secrets-management.default-secret-path` |
        | `domain` | `general.domain` |

        <Note>
          `workspaceId` is the old name for the project ID, so copy its value into `project-id` as is.
        </Note>


        For example, this `.infisical.json`:

        ```json .infisical.json
        {
            "workspaceId": "<project-id>",
            "defaultEnvironment": "dev",
            "gitBranchToEnvironmentMapping": {
                "main": "prod",
                "staging": "staging"
            },
            "defaultSecretPath": "/backend",
            "domain": "https://eu.infisical.com"
        }
        ```

        becomes this `.infisical.yaml`:

        ```yaml .infisical.yaml
        general:
            domain: https://eu.infisical.com
        secrets-management:
            project-id: <project-id>
            default-environment: dev
            default-secret-path: /backend
            mappings:
                git-branch-to-environment:
                    main: prod
                    staging: staging
        ```

        The CLI ignores keys it doesn't recognize, so if you misspell a key, the CLI drops that setting without reporting an error.
      </Step>
      <Step>
        Delete `.infisical.json`, then commit both changes.
      </Step>
    </Steps>

  </Tab>
</Tabs>

If a Dockerfile or CI script refers to `.infisical.json` by name, such as in a `COPY` instruction, change it to `.infisical.yaml`.

## Verify the migration

In the directory that holds `.infisical.yaml`, run a command that reads the file, such as:

```bash
infisical sm secrets
```

Check that the command lists the secrets from the project and environment you expect. If it reports that the project ID is missing, compare the keys in `.infisical.yaml` with the [field mapping](#migration-steps).

## FAQ

<AccordionGroup>
  <Accordion title="What if .infisical.json and .infisical.yaml are in the same directory?">
    The CLI reads `.infisical.yaml` and ignores `.infisical.json`, so changes
    you make to `.infisical.json` don't apply. Make any changes in
    `.infisical.yaml`.

    In version 0.44.3 and later, each time you run a command, the CLI also
    prints a warning that both files exist. To stop the warning, delete
    `.infisical.json`.

  </Accordion>
  <Accordion title="Can I run infisical init instead?">
    `infisical init` writes a new `.infisical.yaml` that holds only the project
    ID, so you lose the environment, branch mapping, folder, and instance
    settings from `.infisical.json`. To keep those settings, let the CLI create
    `.infisical.yaml` from `.infisical.json`, or create `.infisical.yaml` by
    hand.

  </Accordion>
  <Accordion title="What if the CLI can't create .infisical.yaml?">
    If the CLI can't write `.infisical.yaml` the command still runs with the settings in
    `.infisical.json`, and the CLI tries again the next time you run a command.
    At most once a day, the CLI also prints a deprecation notice that names the
    directory it couldn't write to.

    To finish the migration, make the directory writable and run a command
    again, or follow the steps in the **Edit the file by hand** tab.

  </Accordion>
  <Accordion title="How do I hide the deprecation notice?">
    The notice stops once `.infisical.yaml` exists. To hide the notice before
    then, set the `INFISICAL_DISABLE_WORKSPACE_CONFIG_MIGRATION_NOTICE`
    environment variable to any value, such as `true`. Neither the variable nor
    `--silent` hides the warning that both files exist. To stop that warning,
    delete `.infisical.json`.

    The CLI writes the notice, the warning, and the message about creating
    `.infisical.yaml` to standard error, so they don't change the output of
    commands like `infisical export`.

  </Accordion>
</AccordionGroup>
