The `InfisicalStaticSecretPush` CRD pushes native Kubernetes Secrets from your cluster to one or more paths in Infisical and keeps them in sync.
It replaces the v1alpha1 `InfisicalPushSecret` CRD with a cleaner design: authentication and connection details are defined as separate reusable resources ([InfisicalAuth](/integrations/platforms/kubernetes/infisical-auth-crd) and [InfisicalConnection](/integrations/platforms/kubernetes/infisical-connection-crd)) instead of inline blocks.

### Prerequisites

Before creating an `InfisicalStaticSecretPush`, you need:
1. An [InfisicalConnection](/integrations/platforms/kubernetes/infisical-connection-crd) resource configured with your Infisical host and TLS settings.
2. An [InfisicalAuth](/integrations/platforms/kubernetes/infisical-auth-crd) resource configured with your machine identity authentication method. The machine identity needs permission to read, create, edit, and delete secrets at each target, and to create folders when `createMissingFolders` is enabled.

### Examples

Each example below contains every resource you need to apply: the credential `Secret`, `InfisicalConnection`, `InfisicalAuth`, the `Secret` to push, and `InfisicalStaticSecretPush`.
Copy the one that matches your environment, replace the placeholder values, and `kubectl apply -f` it.

For more details on each resource, see the [InfisicalConnection](/integrations/platforms/kubernetes/infisical-connection-crd) and [InfisicalAuth](/integrations/platforms/kubernetes/infisical-auth-crd) documentation or access our [samples](https://github.com/Infisical/kubernetes-operator/tree/main/examples/v1beta1/infisicalstaticsecretpush).

  <Accordion title="Kubernetes Auth (Recommended)">
    Best for workloads already running in Kubernetes.

    This example uses **short-lived service account tokens**. If you prefer to use a Gateway as the token reviewer instead, see the [Kubernetes Auth guide](/documentation/platform/identities/kubernetes-auth) for alternative setup options.

    ```yaml complete-kubernetes-auth.yaml
    # 1. Service account used by the operator for token review
    apiVersion: v1
    kind: ServiceAccount
    metadata:
      name: infisical-service-account
      namespace: default
    ---
    # 2. Bind the service account to system:auth-delegator so it can
    #    validate tokens via the Kubernetes TokenReview API
    apiVersion: rbac.authorization.k8s.io/v1
    kind: ClusterRoleBinding
    metadata:
      name: infisical-service-account-role-binding
    roleRef:
      apiGroup: rbac.authorization.k8s.io
      kind: ClusterRole
      name: system:auth-delegator
    subjects:
      - kind: ServiceAccount
        name: infisical-service-account
        namespace: default
    ---
    # 3. Kubernetes secret holding the machine identity ID
    apiVersion: v1
    kind: Secret
    metadata:
      name: kubernetes-credentials
      namespace: default
    type: Opaque
    stringData:
      identityId: <your-machine-identity-id>
    ---
    # 4. Connection to the Infisical instance
    apiVersion: secrets.infisical.com/v1beta1
    kind: InfisicalConnection
    metadata:
      name: my-infisical-connection
      namespace: default
    spec:
      address: https://app.infisical.com
    ---
    # 5. Auth using a Kubernetes service account token
    apiVersion: secrets.infisical.com/v1beta1
    kind: InfisicalAuth
    metadata:
      name: my-infisical-auth
      namespace: default
    spec:
      infisicalConnectionRef:
        name: my-infisical-connection
        namespace: default
      method: kubernetes
      kubernetes:
        identityIdRef:
          name: kubernetes-credentials
          namespace: default
          key: identityId
        serviceAccountRef:
          name: infisical-service-account
          namespace: default
    ---
    # 6. Kubernetes Secret to push to Infisical
    apiVersion: v1
    kind: Secret
    metadata:
      name: app-credentials
      namespace: default
    type: Opaque
    stringData:
      DB_PASSWORD: <your-db-password>
      API_KEY: <your-api-key>
    ---
    # 7. Push the Kubernetes Secret to Infisical
    apiVersion: secrets.infisical.com/v1beta1
    kind: InfisicalStaticSecretPush
    metadata:
      name: my-static-secret-push
      namespace: default
    spec:
      infisicalAuthRef:
        name: my-infisical-auth
        namespace: default
      syncOptions:
        refreshInterval: 60s
      sources:
        secrets:
          - name: app-credentials
            namespace: default
      targets:
        - projectId: <your-project-id>
          environmentSlug: dev
          secretPath: /app
    ```
  </Accordion>

## CRD properties

<Accordion title="infisicalAuthRef">
  A reference to the `InfisicalAuth` resource that defines how to authenticate with Infisical. The connection to the Infisical instance is resolved through the `InfisicalAuth` resource's `infisicalConnectionRef` field.

  | Field       | Required | Description                                           |
  | ----------- | -------- | ----------------------------------------------------- |
  | `name`      | Yes      | The name of the `InfisicalAuth` resource.             |
  | `namespace` | Yes      | The namespace of the `InfisicalAuth` resource.        |

  See the [InfisicalAuth CRD](/integrations/platforms/kubernetes/infisical-auth-crd) documentation for details.
</Accordion>

<Accordion title="syncOptions">
  Controls the synchronization behavior.

  | Field                  | Required | Description                                                                 |
  | ---------------------- | -------- | --------------------------------------------------------------------------- |
  | `refreshInterval`      | No       | How often to push again (e.g. `60s`, `5m`, `1h`). The minimum is `5s`. When omitted, the operator pushes only when a source Secret or the `InfisicalStaticSecretPush` changes. |
  | `updatePolicy`         | No       | Whether keys that already exist in Infisical are updated. Must be `Replace` or `None`. Defaults to `Replace`. |
  | `deletionPolicy`       | No       | Whether the operator deletes the secrets it pushed. Must be `Delete` or `None`. Defaults to `Delete`. |
  | `createMissingFolders` | No       | Whether to create the target folder, and any missing parent folders, when it doesn't exist. Defaults to `true`. |

  Behavior of each `updatePolicy`:
  - `Replace`: The operator keeps existing keys in sync with the sources. It also takes over keys that already exist at a target but were created outside this resource, and manages them from then on like the keys it created.
  - `None`: The operator only creates missing keys. It never changes a key that already exists, including the keys this resource created, so later changes to the sources don't reach Infisical.

  Behavior of each `deletionPolicy`:
  - `Delete`: The operator deletes a pushed secret from Infisical when its key is removed from the sources, when its target is removed, or when the `InfisicalStaticSecretPush` is deleted.
  - `None`: The operator never deletes secrets from Infisical.

  ```yaml
  syncOptions:
    refreshInterval: 60s
    updatePolicy: Replace
    deletionPolicy: Delete
    createMissingFolders: true
  ```
</Accordion>

<Accordion title="sources">
  The Kubernetes Secrets to push. Every key of every Secret is pushed to every target, except to a target with a [template](#templating), which pushes what its template renders instead.

  When multiple Secrets contain the same key, the **first occurrence wins**: Secrets listed earlier in the array take precedence over later ones.

  | Field     | Required | Description                                                           |
  | --------- | -------- | --------------------------------------------------------------------- |
  | `secrets` | Yes      | The Kubernetes Secrets to push, each with a `name` and a `namespace`. |

  If a source Secret doesn't exist, the sync fails and nothing is deleted from Infisical.

  ```yaml
  sources:
    secrets:
      - name: db-credentials
        namespace: default
      - name: api-keys
        namespace: default
  ```

  <Warning>
    An `InfisicalStaticSecretPush` can push any Secret the operator can read, including Secrets in other namespaces, and a template can write a source value into Infisical or into the resource's status, for example as a key name in `status.managedSecrets`. Treat permission to create or edit `InfisicalStaticSecretPush` resources like permission to read those Secrets.
  </Warning>
</Accordion>

<Accordion title="targets">
  An array of Infisical paths to push the secrets to.

  | Field             | Required | Description                                                   |
  | ----------------- | -------- | ------------------------------------------------------------- |
  | `projectId`       | No       | The Infisical project ID.                                     |
  | `projectSlug`     | No       | The Infisical project slug.                                   |
  | `environmentSlug` | Yes      | The environment slug (e.g. `dev`, `staging`, `prod`).         |
  | `secretPath`      | Yes      | The folder to push the secrets to. Root is `/`.               |
  | `template`        | No       | Optional templating configuration (see [Templating](#templating) below). |

  <Note>You have to provide either `projectId` or `projectSlug`. If none or both are set, the sync fails.</Note>

  Each target is synced separately. If a target fails, the operator still pushes to the other targets, but it doesn't delete secrets from any target until every target succeeds.

  ```yaml
  targets:
    - projectId: <your-project-id>
      environmentSlug: dev
      secretPath: /app
    - projectSlug: <your-project-slug>
      environmentSlug: staging
      secretPath: /app/backend
  ```
</Accordion>

## Templating

Pushing the keys of your Kubernetes Secrets as-is may not be enough. This is where templating functionality may be helpful.
Using Go templates, you can format, combine, and create new key-value pairs from the source keys before pushing them to Infisical.

When a target has a template, only the keys defined in `template.data` are pushed to that target.
When no template is set, all source keys are pushed as-is.

Each source key is available in the template context as `.KEY`, which is an object with two accessors:

- `.Value`: the value of the key in the source Secret.
- `.SecretPath`: the target's `secretPath`.

### Key/value template map

```yaml
targets:
  - projectId: <your-project-id>
    environmentSlug: dev
    secretPath: /app
    template:
      engineVersion: v1
      data:
        DATABASE_URL: "postgres://{{ .DB_USER.Value }}:{{ .DB_PASS.Value }}@{{ .DB_HOST.Value }}:5432/app"
        REDIS_URL: "redis://{{ .REDIS_HOST.Value }}:6379"
```

### Bulk string template with a loop

```yaml
targets:
  - projectId: <your-project-id>
    environmentSlug: dev
    secretPath: /app
    template:
      engineVersion: v1
      data: |
        {{- range $key, $secret := . }}
        {{ $key }}: "{{ $secret.Value }}"
        {{- end }}
```

### How templates are applied

- A key that the template stops rendering is deleted from the target according to `deletionPolicy`, like a key removed from the sources.
- If a template fails, only its target fails, and nothing is deleted from Infisical until the template is fixed.
- When a template fails while running, the status shows where it failed but not why, because the reason can contain secret values. Syntax errors are shown in full.
- A template whose `data` is empty or only contains whitespace is rejected, because it would delete every secret pushed to the target.
- Only the values pushed to Infisical must be valid UTF-8, so a template can leave out a binary source value or encode it with `encodeBase64`.

<Note>
  `secretFrom` looks up secrets fetched from Infisical, so it doesn't work in an `InfisicalStaticSecretPush` template.
</Note>

To help transform your secrets further, the operator provides a set of built-in functions that you can use in your templates.

## Managing pushed secrets

The operator records the ID of every secret it pushes to Infisical in the resource's `status.managedSecrets`, and it only ever deletes those secrets.

<AccordionGroup>
  <Accordion title="Keys that already exist in Infisical">
    With `updatePolicy: Replace`, the operator takes over a key that already exists at a target: it writes the source value and records the secret in `status.managedSecrets`, so the key is deleted with the resource when `deletionPolicy` is `Delete`. With `updatePolicy: None`, the operator leaves the key unchanged and never deletes it.

    If the operator stops right after creating a secret, before it records the secret's ID, the next sync takes the key over again when `updatePolicy` is `Replace`. When `updatePolicy` is `None`, the key isn't recorded, so the operator never deletes it.
  </Accordion>

  <Accordion title="Keys pushed by another InfisicalStaticSecretPush">
    Two resources that push the same key to the same path would overwrite each other on every sync. The operator never changes or deletes a key that another `InfisicalStaticSecretPush` pushed, even while that resource is being deleted. The resource that didn't push the key first reports an error that names the keys it left unchanged.

    Push each key from only one `InfisicalStaticSecretPush`.
  </Accordion>

  <Accordion title="Secret values">
    Infisical stores secret values as text, so every value pushed must be valid UTF-8. To push binary data, store it base64-encoded in the source Secret, or encode it with `encodeBase64` in a [template](#templating).

    Infisical removes whitespace at the start and end of a value, and keeps a single trailing newline when the value ends with one.
  </Accordion>

  <Accordion title="Approval workflows">
    If an [approval policy](/documentation/platform/pr-workflows) covers a target, Infisical turns the operator's changes into an approval request instead of applying them, and the sync of that target fails with an explanation. Once the request is approved, the operator takes over the secrets when `updatePolicy` is `Replace`.

    The operator doesn't track approval requests yet, so every sync submits a new request. To let the operator push without approval, enable **Bypass Approval for Machine Identities** in the approval policy.
  </Accordion>

  <Accordion title="Deleting the resource">
    When `deletionPolicy` is `Delete`, Kubernetes keeps the `InfisicalStaticSecretPush` until the operator has deleted every secret in `status.managedSecrets` from Infisical. If the operator can't delete them within 5 minutes, for example because Infisical is unreachable, it lets Kubernetes delete the resource, leaves the secrets in Infisical, and logs their IDs.

    <Warning>
      To delete the pushed secrets, the operator needs the `InfisicalAuth`, its `InfisicalConnection`, and their credential Secrets. If you delete them together with the `InfisicalStaticSecretPush`, for example by deleting their namespace or by running `kubectl delete -f` on a file that contains all of them, the operator can't log in, and the pushed secrets stay in Infisical after the 5 minutes.

      Delete the `InfisicalStaticSecretPush` first and wait until it's gone, or keep the `InfisicalAuth` and `InfisicalConnection` outside the namespaces of your applications.
    </Warning>

    If you change `infisicalAuthRef` to an `InfisicalAuth` that connects to another Infisical instance, the secrets pushed to the previous instance stay there. To remove them, delete the `InfisicalStaticSecretPush` before you change the `InfisicalAuth`, or delete them in Infisical.
  </Accordion>
</AccordionGroup>

## Applying the CRD

```bash
kubectl apply -f infisical-static-secret-push.yaml
```

Verify the secrets were pushed:

```bash
kubectl get infisicalstaticsecretpush -n <namespace>
```

When the `SYNCED` column shows `True`, the secrets are in Infisical at every target.

## Migrating from InfisicalPushSecret

If you push secrets with the v1alpha1 [InfisicalPushSecret CRD](/integrations/platforms/kubernetes/infisical-push-secret-crd), an `InfisicalStaticSecretPush` can take over the secrets that the `InfisicalPushSecret` pushed. The secrets aren't deleted or recreated in Infisical during the migration.

The `InfisicalStaticSecretPush` spec is different from the `InfisicalPushSecret` spec:

- It authenticates through an [InfisicalAuth](/integrations/platforms/kubernetes/infisical-auth-crd) resource, which connects to Infisical through an [InfisicalConnection](/integrations/platforms/kubernetes/infisical-connection-crd) resource
- `push.secret` becomes an entry in `sources.secrets`, and `destination` becomes an entry in `targets`, with `secretsPath` renamed to `secretPath`
- `resyncInterval` becomes `syncOptions.refreshInterval`, and `updatePolicy` and `deletionPolicy` move under `syncOptions`
- `updatePolicy` defaults to `Replace` and `deletionPolicy` defaults to `Delete`, while both default to `None` on an `InfisicalPushSecret`
- Its templates use the [v1 template syntax](#templating), which has no `includeAllSecrets` option. To push every source key along with the keys a template adds, use a bulk template that ranges over `.`
- It doesn't support generators (`push.generators`)

<Steps>
  <Step>
    Upgrade the operator to v0.11.17 or later. Earlier versions don't include `InfisicalStaticSecretPush`.
  </Step>
  <Step>
    On the `InfisicalPushSecret`, remove `deletionPolicy` or set it to `None`, and apply the change.

    <Warning>
      If you skip this step, deleting the `InfisicalPushSecret` at the end of the migration deletes the secrets from Infisical.
    </Warning>
  </Step>
  <Step>
    Create an `InfisicalStaticSecretPush` that pushes the same Secret to the same project, environment, and path as the `InfisicalPushSecret`. Keep `updatePolicy` set to `Replace`, so the `InfisicalStaticSecretPush` takes over the secrets that already exist in Infisical.
  </Step>
  <Step>
    Check that the `SYNCED` column shows `True` for the `InfisicalStaticSecretPush`:

    ```bash
    kubectl get infisicalstaticsecretpush <static-secret-push-name> -n <namespace>
    ```
  </Step>
  <Step>
    Delete the `InfisicalPushSecret`:

    ```bash
    kubectl delete infisicalpushsecret <infisical-push-secret-name> -n <namespace>
    ```

    The secrets stay in Infisical, and the `InfisicalStaticSecretPush` manages them from now on.
  </Step>
</Steps>

## Troubleshooting

You can check the status of your `InfisicalStaticSecretPush` resource by inspecting its conditions:

```bash
kubectl get infisicalstaticsecretpush my-static-secret-push -o jsonpath='{.status.conditions}' | jq
```

When reconciliation is successful, the `secrets.infisical.com/LastReconcileStatus` condition will have `Status: "True"`, `Reason: "OK"`, and `Message: "Reconciliation successful"`.

If reconciliation fails, `Status` will be `"False"`, `Reason` will be set to `Error`, and `Message` will contain details about what went wrong. While the operator deletes the pushed secrets from Infisical, `Reason` is set to `Deleting`.

The `ObservedGeneration` field indicates which generation of the resource spec the operator has last processed. If `ObservedGeneration` is less than `metadata.generation`, the operator hasn't yet reconciled the latest changes to the resource.
